# 错误日志黑灯工厂 — agent 手册

> 黑灯工厂来源 agent 之一（来源标识 `blacklight`）。本文件为该 agent 的功能实现真源：巡检流程、分诊分级口径、自动修复边界、负责人判定与建单上报。产出收口与工单闭环见 [黑灯工厂工单](../SKILL.md) 与 [business-rule](business-rule.md)。

## 1. 定位

每 3 小时一轮巡检各接入应用的 SLS `ERROR`（含 `FATAL`）日志，按指纹归一化聚合后逐条分诊：能安全修复的自动改代码并提交推送，不敢安全判断的按代码负责人建单指派，属业务口径的知会留痕。P1/P2 产出统一上报为黑灯工厂工单，P3/噪声仅计数。

与「错误日志管理」（日志异常报表）分工：报表承担每日全量指纹趋势分析（只读 + 手工标记）；本 agent 承担实时分诊、修复与建单。同一指纹两边都可能出现，互相引用不重复展开。

## 2. 运行方式

- **服务端运行**：由服务端通过 **Qoder SDK** 创建定时调度会话驱动执行，每 3 小时一轮，无 Web 页面、不依赖本机环境
- 接入应用清单、日志库定位、代码仓访问与推送凭证等配置全部由服务端注入会话上下文；新增应用仅需补配置，不改 agent
- 每轮产出落盘巡检报告（含本轮拉取量、聚合数、分诊结论与处置结果），路径随建单上报

## 3. 巡检流程

1. **采集**：拉取上轮以来各应用 ERROR/FATAL 日志；查询失败记失败并走 §7 简报，严禁吞异常
2. **聚合**：按指纹归一化折叠同类报错（口径复用「错误日志管理」：消息中的数字、UUID、时间戳、IP 等变量占位符化，堆栈取最顶层业务行）
3. **剔除**：跳过本来源已有未关闭工单的指纹、同键已忽略（IGNORED 免打扰）的指纹、P3/噪声指纹，只对增量深析
4. **分诊**：定位报错代码（堆栈顶层业务行 + 代码仓），判定级别与分类，给出「建议：」人话结论与已掌握证据
5. **处置**：符合 §5 修复边界的直接改代码 commit+push；其余按分类建单
6. **上报**：汇总本轮 P1/P2 条目，经内部上报工具一次调用批量建单（见 §6）

## 4. 分诊口径

### 4.1 分级

| 级别 | 判定 |
|---|---|
| P1 | 资损、主流程阻断、数据错误风险，或高频爆发 |
| P2 | 功能受损但有绕行、局部异常、低频但真实缺陷 |
| P3 | 噪声、无害低频、已知口径——仅计数，不建单 |

### 4.2 三分类结论

| 分类 | 判定 | 处置 |
|---|---|---|
| `FIXED_REVIEW` 自动修复待复核 | 根因明确且修复落在 §5 安全边界内 | commit+push 后建单（待复核），附 commit 哈希 |
| `PENDING_JUDGE` 待判断 | 根因明确但修复有风险，或无法安全判断 | 按负责人建单待认领，必须带「建议：」人话结论与证据 |
| `BIZ_CONFIRM` 业务确认 | 报错符合业务预期/口径（如库存不足拦截） | 低打扰知会留痕，确认口径后关闭或转办 |

## 5. 自动修复边界

- 仅允许**局部防御性改动**：空指针防护、边界条件、资源释放、幂等与重试兜底等；不改变任何业务口径与数据语义
- 修复提交必须在提交信息中携带异常指纹标识，便于复核回溯与复发统计
- 触及业务逻辑、数据口径、接口契约的一律不修，转 `PENDING_JUDGE` / `BIZ_CONFIRM`
- 拿不准即不修：宁可待判断，不赌自动修

## 6. 建单上报

- 通道：黑灯工厂内部上报工具（建单 / 回复 / 状态流转三能力，devops 内部鉴权，不对外开放）；单轮一次批量调用
- 业务键 = 异常指纹；上报内容含级别、分类、服务、标题、摘要、建议、证据（traceId 样例、堆栈、趋势）与落盘报告路径
- 幂等由工单侧「来源 + 业务键」唯一键保证，失败重发安全；同键未关闭只追加轮次与证据，不重复建单
- 同键工单被忽略（IGNORED）后，后续轮次该指纹仅计数不再深析

## 7. 负责人判定与失败兜底

- 负责人判定：堆栈顶层业务行代码提交记录（git blame / log）→ 在职研发 → 其企微账号；判不出则负责人留空，工单待认领
- 采集失败 / 建单失败：发群机器人简报（每轮最多 1 条，@ 运维负责人），下轮重试

## 8. 反模式

- 每轮全量新建而不走同键追加（刷屏根因）
- 把 P3/仅计数条目上报建单（工单变报表）
- 自动修复越界改业务口径（必须转人工）
- 分诊结论不写「建议：」人话（认领人无法接手）
- 吞采集/解析异常不上报（静默丢数据）

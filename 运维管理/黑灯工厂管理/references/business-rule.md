# 黑灯工厂工单 — 业务规则字典

## 1. 定位与边界

黑灯工厂工单是** agent 巡检产出与缺陷分流的流程闭环层**,不是通用工单系统:

- 建单方四类:错误日志黑灯工厂(来源 `blacklight`)、大SQL结果集修复(来源 `bigsqlfix`)、服务端bug扫描(来源 `bugscan`,见 §10)三个 agent + 需求管理缺陷分流(来源 `reqdefect`,需求类型=缺陷修复审批通过后自动建单)
- Web 端不提供手工新建;**人工报 bug 走「排期管理/需求管理」**提交缺陷修复单据,审批通过后自动分流本模块(见 §4/§8)
- P3/噪声不建单(agent 侧仅计数);只有 P1/P2 进工单
- 错误日志管理(日志异常报表)承担每日全量指纹趋势分析,工单不替代它

## 2. 工单三分类(category)

| category | 来源动作 | 建单状态 | 说明 |
|---|---|---|---|
| `FIXED_REVIEW` 自动修复待复核 | agent 已 commit+push | `REVIEW` | 带 commit 哈希;复核通过→RESOLVED,打回→REOPENED |
| `PENDING_JUDGE` 待判断 | unknown / keep-risk(不敢自动修) | `OPEN` | 必须带「建议:」人话结论与已掌握证据 |
| `BIZ_CONFIRM` 业务确认 | business / keep-business | `OPEN`(低打扰) | 知会留痕;处理人确认口径后关闭或转办 |

服务端bug扫描的「评估是否需人为确认或直接修复」落为同一三分类:能安全直接修复 → `FIXED_REVIEW`;需技术负责人裁决 → `PENDING_JUDGE`;修不修属业务口径问题 → `BIZ_CONFIRM`(见 §10)。需求管理缺陷分流建单固定为 `PENDING_JUDGE`(已经人工审批确认真伪,无需再判业务口径)。

## 3. 状态机

```
                 ┌─────────────────────────────────────────┐
                 │                                         │
OPEN(待认领/已指派) ──认领──▶ CLAIMED(处理中) ──解决──▶ RESOLVED(已解决)
 │    │                                              ▲
 │    └──无需处理(备注必填)──▶ IGNORED(已关闭)      │复核通过
 │                                                  │
REVIEW(待复核) ──复核通过──▶ RESOLVED ──────────────┘
REVIEW ──复核打回(备注必填)──▶ REOPENED(≡OPEN,重新进入待认领)
RESOLVED/IGNORED 之后同源复发(新轮仍命中) ──原单重开(复发次数+1)──▶ 分类初始态(OPEN/REVIEW)
```

规则:

- `CLAIMED` 只能由认领人本人或研发负责人执行「解决/转办」
- `IGNORED` 必须填原因(噪声/口径如此/三方问题);IGNORED 的单参与「免打扰」——agent 侧同键问题此后各轮仅计数
- `REVIEW` 超过 72h 未复核,按 P2 升级规则提醒(见 §6)

## 4. 建单幂等(防刷屏核心)

业务唯一键 = 来源 + 业务键,同键只保留一张工单:

| 来源 | 业务键构成 |
|---|---|
| `blacklight` 错误日志黑灯工厂 | 异常指纹(16 位十六进制,与错误日志黑灯工厂采集侧指纹口径一致) |
| `bigsqlfix` 大SQL结果集修复 | 服务名 + mapper 全限定名 |
| `bugscan` 服务端bug扫描 | 异常指纹(与错误日志管理同一归一化口径;来源不同故与 `blacklight` 同指纹不冲突) |
| `reqdefect` 需求管理缺陷分流 | 需求编号(一单一号;驳回重提沿用原编号,重提再次通过后向原未关闭单追加证据) |

upsert 规则(agent 每轮上报时执行):

1. 同业务键存在**未关闭**工单(OPEN/CLAIMED/REVIEW/REOPENED)→ **不新建**:出现次数累加本轮次数、出现轮次 +1、最近出现时间更新为本轮、证据追加本轮 traceId / SQL 样例(各 ≤3 条,滚动覆盖最旧)、摘要 / 建议若本轮有更新则覆盖
2. 同业务键工单已关闭(RESOLVED/IGNORED)后同源复发 → **原单复发重开**,不另开新单、不建立父子单关联:状态回到分类初始态(FIXED_REVIEW 为 REVIEW,其余为 OPEN),认领 / 处理 / 复核信息清空重新起算,复发次数 +1,出现轮次续增,上轮关闭信息记入处理记录时间线
3. agent 侧「仅计数」条目(P3)不上报;上报内容要求见 §8

## 5. 负责人指派与改派

- agent 建单时给出负责人,判定口径:代码提交记录(git blame / log)→ 在职研发 → 其企微账号;判不出来 → 负责人为空,状态 = OPEN 待认领
- 级别由 agent 落单时给定(P1/P2),Web 端展示不可改;分级口径变更只走 agent 手册
- Web 端支持**改派**(研发负责人角色):更新负责人(含姓名与企微账号)并记操作日志;改派后即时触发一次 §6 提醒
- 负责人离职同步:每日与人员主数据对账 → 工单未关闭且负责人已离职 → 清空负责人、置 OPEN 待认领,提醒研发负责人

## 6. 通知规则

通道 = 企微**应用消息**(复用公共功能「企微应用消息发送」,按负责人企微账号点对点);群机器人仅保留 agent 侧采集失败 / 建单失败简报。

| 时机 | 内容 | 频控 |
|---|---|---|
| 新单创建(含合并上报后出现次数环比翻倍以上的复发单) | 「黑灯工厂新工单 [级别] 标题 | 来源服务 | 点链接处理」 | 同一接收人每轮(3h)最多 1 条,多单合并为「新工单 N 条:P1×a P2×b」 |
| 改派 | 「你有工单被改派过来」 | 即时,不频控 |
| REVIEW 超 72h 未复核 | 提醒复核人 | 每日 09:30 合并 1 条 |
| OPEN/CLAIMED 超 SLA(§7) | 提醒负责人,抄送其直属上级 | 每日 09:30 合并 1 条 |
| 采集失败 / 建单失败(agent 侧) | 群机器人简报 @ chenguojian | 每轮最多 1 条 |

## 7. SLA 与统计

| level | 响应 SLA(OPEN→CLAIMED/IGNORED) | 闭环 SLA(建单→RESOLVED/IGNORED) |
|---|---|---|
| P1 | 8 个工作小时 | 24h |
| P2 | 24h | 72h |
| FIXED_REVIEW | — | 72h(复核时限) |

- 超时列表行标红 + §6 提醒;工作小时 = 09:00~21:00
- 列表 KPI 与导出支撑:修复率(FIXED_REVIEW 复核通过率)、平均响应/闭环时长、复发率(复发次数 ≥1 的单占比)、负责人维度分布
- 工单保留 180 天,超期由独立清理任务每日删除(与错误日志管理保留期机制一致)

## 8. agent 接入规范

三个 agent 每轮落盘完成后,经内部上报工具向 devops 服务批量建单(单轮一次调用;走 devops 内部鉴权,不对外开放):

- 上报内容:来源 + 问题条目清单,每条含业务键、级别、分类、服务、标题等,负责人以邮箱标识;字段契约以代码仓为准
- 服务端职责:按负责人邮箱匹配在职研发,取得负责人、姓名与企微账号(匹配不到则负责人留空、待认领)→ 按 §4 upsert → 按 §6 触发提醒
- 幂等由业务唯一键 + upsert 保证,agent 失败重发安全
- 内部上报工具同时提供工单回复(追加备注到处理记录时间线)与状态流转(认领 / 解决 / 忽略 / 复核通过 / 复核打回 / 改派)能力,均为写操作,操作人沿用调用方登录身份
- 采集失败或建单失败时,agent 发群机器人简报(见 §6)

需求管理缺陷分流建单复用同一内部上报通道:来源 `reqdefect`、业务键 = 需求编号,级别按需求优先级映射(P0/P1→P1、P2/P3→P2),负责人留空时按代码归属判定、判不出则待认领;建单失败在需求管理侧记事件审计并告警重发,幂等同 §4。

## 9. RBAC 与操作日志

- 菜单:运维管理 → 黑灯工厂工单(二级),菜单权限码 `MENU:RND:OPS:BLACKLIGHT_TICKET`,仅 WEB
- 按钮权限:`BUTTON:RND:OPS:BLACKLIGHT_TICKET:CLAIM`(认领/解决/忽略)、`BUTTON:RND:OPS:BLACKLIGHT_TICKET:REVIEW`(复核通过/打回)、`BUTTON:RND:OPS:BLACKLIGHT_TICKET:REASSIGN`(改派,研发负责人)、`BUTTON:RND:OPS:BLACKLIGHT_TICKET:EXPORT`(导出)
- 「研发负责人」以持有改派按钮权限判定
- 操作日志六要素覆盖:认领/解决/忽略/复核/打回/改派(与统一操作日志口径一致);操作日志独立留存并渲染为详情页处理记录时间线,同时写入应用日志

## 10. 服务端 bug 扫描 agent(bugscan)

第三个黑灯 agent,在「报错分诊」之上叠加「需求口径对照」,回答两个问题:**这算不算缺陷、能不能直接修**。

- **巡检节奏**:与既有 agent 同频(每 3 小时一轮),产出统一走 §8 上报
- **错误提取**:从 SLS 拉取本轮 ERROR 日志,按指纹归一化聚合(口径复用「错误日志管理」),剔除已有未关闭工单与同键已忽略的指纹,只深析增量
- **项目定位**:按「项目映射配置」生效数据(研发报告·项目进度报告维护)把应用名映射到对应项目的 harness 工程与代码仓清单;映射缺失的应用仅计数不建单,并记审计
- **对照评估**:读取该项目 harness 工程(需求/规则文档)与报错路径相关业务代码,对照「文档期望行为 vs 代码实际行为」,产出三态结论:

  | 结论 | 建单分类 | 说明 |
  |---|---|---|
  | 确为缺陷且修复方案安全明确 | `FIXED_REVIEW` | 直接修复:agent commit+push 后建单待复核 |
  | 确为缺陷但修复有风险,或需技术负责人裁决 | `PENDING_JUDGE` | 人为确认:按代码负责人指派待认领 |
  | 行为与文档冲突、修不修是业务口径问题 | `BIZ_CONFIRM` | 人为确认:知会留痕,业务确认后关闭或转办 |

- **非缺陷收口**:评估为口径如此/噪声的仅计数不建单(同 P3 口径),防刷屏
- 级别、负责人指派、幂等、通知、SLA 均复用 §4~§7 既有口径,不另立规则

## 11. 反模式

- 手工页面建单(绕过 agent 分诊,破坏幂等键)
- agent 每轮全量新建而不走 upsert(刷屏根因)
- 把 P3/仅计数条目也建单(工单变报表)
- 复核打回不填备注(打回即 REOPENED,没有上下文认领人无法接手)
- 关闭单时不同步 agent 跨轮状态(IGNORED 后 agent 仍重复深析)
- bugscan 跳过 harness 对照直接按堆栈改代码(把「口径如此」当缺陷修,产生回归)

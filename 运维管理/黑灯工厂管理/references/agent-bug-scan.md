# 服务端bug扫描 — agent 手册

> 黑灯工厂来源 agent 之三（来源标识 `bugscan`）。本文件为该 agent 的功能实现真源：错误提取、项目定位、harness/代码对照评估与建单上报。产出收口与工单闭环见 [黑灯工厂管理](../SKILL.md) 与 [business-rule](business-rule.md)（三态结论落分类口径见其 §10）。

## 1. 定位

在「报错分诊」之上叠加「需求口径对照」，回答两个问题：**这算不算缺陷、能不能直接修**。

- 错误日志黑灯工厂针对**报错本身**分诊修复（让错误消失）
- 本 agent 针对**报错背后的需求口径偏差**：从 SLS 日志提取错误后，读取对应项目的 harness 工程（需求/规则文档）与业务代码，对照「文档期望行为 vs 代码实际行为」——报错消除了不代表行为正确，行为符合文档才不算缺陷

同一指纹两个 agent 可能各自建单（视角不同），证据区互相引用，不重复展开。

## 2. 运行方式

- **服务端运行**：由服务端通过 **Qoder SDK** 创建定时调度会话驱动执行，每 3 小时一轮，与既有 agent 同频，无 Web 页面、不依赖本机环境
- SLS 日志库定位、项目映射、harness 工程与代码仓的访问与推送凭证等配置全部由服务端注入会话上下文
- 每轮产出落盘扫描报告（含本轮提取指纹数、深析数、三态结论分布与处置结果），路径随建单上报

## 3. 扫描流程

1. **错误提取**：从 SLS 拉取本轮各应用 ERROR 日志，按指纹归一化聚合（口径复用「错误日志管理」）
2. **剔除**：跳过本来源已有未关闭工单、同键已忽略（免打扰）的指纹，只深析增量
3. **项目定位**：按功能排期项目配置生效数据（项目映射唯一真源）把应用名映射到该项目的 harness 工程与代码仓清单；映射缺失的应用仅计数不建单，并记审计
4. **对照评估**：读取该项目 harness 工程中报错路径相关的需求/规则文档，与业务代码实际实现对照，产出三态结论（§4）
5. **处置与上报**：结论为缺陷的按分类建单，经内部上报工具一次调用批量上报（见 §5）

## 4. 对照评估三态结论

| 结论 | 建单分类 | 处置 |
|---|---|---|
| 确为缺陷且修复方案安全明确 | `FIXED_REVIEW` | 直接修复：commit+push 后建单待复核，附 commit 哈希 |
| 确为缺陷但修复有风险，或需技术负责人裁决 | `PENDING_JUDGE` | 人为确认：按代码负责人指派待认领，带「建议：」人话结论与证据（含文档依据与代码位置） |
| 行为与文档冲突、修不修是业务口径问题 | `BIZ_CONFIRM` | 人为确认：低打扰知会留痕，业务确认口径后关闭或转办 |

- **非缺陷收口**：评估为口径如此 / 噪声的仅计数不建单（同 P3 口径），防刷屏
- 分级沿用既有口径（P1/P2 建单；级别、负责人指派、幂等、通知、SLA 均复用工单侧既有规则，不另立）

## 5. 建单上报

- 通道：黑灯工厂内部上报工具（建单 / 回复 / 状态流转三能力，devops 内部鉴权）；单轮一次批量调用
- 业务键 = 异常指纹（与错误日志管理同一归一化口径；来源不同故与错误日志黑灯工厂同指纹不冲突）
- 上报内容除常规字段外，证据必须含**文档依据**（harness 文档条目）与**代码位置**，否则人无法复核「口径对照」结论
- 幂等由工单侧「来源 + 业务键」唯一键保证，失败重发安全；同键工单被忽略后，后续轮次该指纹仅计数不再深析

## 6. 负责人判定与失败兜底

- 负责人判定：报错路径代码提交记录（git blame / log）→ 在职研发 → 其企微账号；判不出则留空待认领
- 采集失败 / 建单失败：发群机器人简报（每轮最多 1 条，@ 运维负责人），下轮重试

## 7. 反模式

- 跳过 harness 对照直接按堆栈改代码（把「口径如此」当缺陷修，产生回归）
- 建单证据缺文档依据或代码位置（口径对照结论无法复核）
- 文档缺失时按自己理解判定为缺陷并自动修复（应转 `PENDING_JUDGE` 或 `BIZ_CONFIRM`）
- 对映射缺失的应用强行建单（定位不到项目则无对照真源，仅计数 + 审计）

# 服务端bug扫描 — agent 手册

> 黑灯工厂来源 agent 之三（来源标识 `bugscan`）。本文件为该 agent 的功能实现真源：错误提取、项目定位、harness/代码对照评估与建单上报。产出收口与工单闭环见 [黑灯工厂管理](../SKILL.md) 与 [business-rule](business-rule.md)（三态结论落分类口径见其 §10）。

## 1. 定位

在「报错分诊」之上叠加「需求口径对照」，回答两个问题：**这算不算缺陷、能不能直接修**。

- 错误日志黑灯工厂针对**报错本身**分诊与建单，按项目开关决定是否修复（让错误消失）
- 本 agent 针对**报错背后的需求口径偏差**：从 SLS 日志提取错误后，读取对应项目的 harness 工程（需求/规则文档）与业务代码，对照「文档期望行为 vs 代码实际行为」——报错消除了不代表行为正确，行为符合文档才不算缺陷

同一指纹两个 agent 可能各自建单（视角不同），证据区互相引用，不重复展开。

## 2. 运行方式

- **服务端运行**：由服务端通过 **Qoder SDK** 创建定时调度会话驱动执行，每 3 小时一轮，与既有 agent 同频并按项目拆分执行单元，无 Web 页面、不依赖本机环境
- 基础域项目引用[项目管理 · 清单](../../../研发管理/项目管理/references/business-rule.md#source)，项目到实现仓与确认路径引用其[执行映射](../../../研发管理/项目管理/references/business-rule.md#execution-mapping)；执行/自动修复开关仍归黑灯工厂配置。SLS 云日志坐标与访问、推送凭证仍由服务端按已确认执行范围注入，SLS Project 不是业务项目；同仓多项目不扩大扫描到全部仓路径
- 每个项目独立产出落盘扫描报告（含本轮提取指纹数、深析数、三态结论分布与处置结果），路径随建单上报；单项目失败不阻塞其他项目

## 3. 扫描流程

1. **项目定位**：每轮读取项目管理生效项目与黑灯工厂执行配置，仅执行已开启且已配置代码服务仓的启用中项目；仅维护 harness 工程、未配置代码服务仓的项目直接跳过并记审计
2. **错误提取**：从 SLS 拉取当前已确认执行范围本轮 ERROR 日志，按指纹归一化聚合（口径复用「错误日志管理」）；无项目证据只保留已确认域级范围，不把共享仓全部归某项目或套项目修复开关。无法确认对应 harness 对照依据的应用仍仅计数与审计，不强行建项目单
3. **剔除**：跳过本来源已有未关闭工单、同键已忽略（免打扰）的指纹，只深析增量
4. **对照评估**：读取当前项目 harness 工程中报错路径相关的需求/规则文档，与代码服务仓实际实现对照，产出三态结论（§4）
5. **处置与上报**：默认只读分诊、仅提工单；项目开启自动修复后才允许按 §4 提交修复。当前项目结果经内部上报工具一次调用批量上报（见 §5）

## 4. 对照评估三态结论

| 结论 | 建单分类 | 处置 |
|---|---|---|
| 确为缺陷、修复方案安全明确，且项目已开启自动修复 | `FIXED_REVIEW` | 直接修复：commit+push 后建单待复核，附 commit 哈希 |
| 确为缺陷，但自动修复未开启、修复有风险或需技术负责人裁决 | `PENDING_JUDGE` | 默认处置：只读代码与文档，按代码负责人建单待认领，带「建议：」人话结论、修复建议与证据（含文档依据与代码位置），不修改或推送代码 |
| 行为与文档冲突、修不修是业务口径问题 | `BIZ_CONFIRM` | 人为确认：低打扰知会留痕，业务确认口径后关闭或转办 |

- **默认仅提工单**：项目自动修复开关默认关闭；关闭时不得创建分支、修改代码、commit 或 push，修复方案安全明确也按 `PENDING_JUDGE` 建单
- **非缺陷收口**：评估为口径如此 / 噪声的仅计数不建单（同 P3 口径），防刷屏
- 分级沿用既有口径（P1/P2 建单；级别、负责人指派、幂等、通知、SLA 均复用工单侧既有规则，不另立）

## 5. 建单上报

- 通道：黑灯工厂内部上报工具（建单 / 回复 / 状态流转三能力，devops 内部鉴权）；单项目单轮一次批量调用，单项目失败不阻塞其他项目
- 业务键 = 异常指纹（与错误日志管理同一归一化口径；来源不同故与错误日志黑灯工厂同指纹不冲突）
- 上报内容除常规字段外，证据必须含**文档依据**（harness 文档条目）与**代码位置**，否则人无法复核「口径对照」结论
- 幂等由工单侧「来源 + 业务键」唯一键保证，失败重发安全；同键工单被忽略后，后续轮次该指纹仅计数不再深析

## 6. 负责人判定与失败兜底

- 负责人候选只读引用[项目管理 · 身份](../../../研发管理/项目管理/references/business-rule.md#identity)与[项目管理 · 责任关系](../../../研发管理/项目管理/references/permission-rules.md#boundaries)，结合报错路径提交记录按稳定身份确认；无项目证据只域级，歧义不取首人、不猜姓名。选人与历史快照保护规则见[工单责任规则](business-rule.md#5-负责人指派与改派)，判不出则留空待认领
- 采集失败 / 建单失败：通知开关开启时发群机器人简报（每轮最多 1 条，@ 运维负责人）；默认仅记录日志与审计，下轮重试

## 7. 反模式

- 项目未开启自动修复仍修改代码或推送（默认仅提工单红线）
- 跳过 harness 对照直接按堆栈改代码（把「口径如此」当缺陷修，产生回归）
- 建单证据缺文档依据或代码位置（口径对照结论无法复核）
- 文档缺失时按自己理解判定为缺陷并自动修复（应转 `PENDING_JUDGE` 或 `BIZ_CONFIRM`）
- 绕过项目管理另建项目仓库映射，或执行未配置代码服务仓的项目
- 对映射缺失的应用强行建单（定位不到项目则无对照真源，仅计数 + 审计）

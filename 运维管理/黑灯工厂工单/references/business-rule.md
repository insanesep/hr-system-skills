# 黑灯工厂工单 — 业务规则字典

## 1. 定位与边界

黑灯工厂工单是** agent 巡检产出与缺陷分流的流程闭环层**,不是通用工单系统:

- 建单方四类:[错误日志黑灯工厂](agent-error-log.md)(来源 `blacklight`)、[大SQL结果集修复](agent-bigsql-fix.md)(来源 `bigsqlfix`)、[服务端bug扫描](agent-bug-scan.md)(来源 `bugscan`,见 §10)三个 agent + 需求管理缺陷分流(来源 `reqdefect`,需求类型=缺陷修复审批通过后自动建单)
- Web 端不提供手工新建;**人工报 bug 走「需求管理」**提交缺陷修复单据,审批通过后自动分流本模块(见 §4/§8)
- P3/噪声不建单(agent 侧仅计数);只有 P1/P2 进工单
- 错误日志管理(日志异常报表)承担每日全量指纹趋势分析,工单不替代它

### 1.1 分项目执行与配置

- **项目真源**：基础仓、域、项目只读引用[域及项目管理 · 清单](../../../研发管理/域及项目管理/references/business-rule.md#source)，项目到实现仓与确认路径引用其[执行映射](../../../研发管理/域及项目管理/references/business-rule.md#execution-mapping)，消费去重见[消费规则](../../../研发管理/域及项目管理/references/business-rule.md#consumption)。本模块不另建基础真源，只保存工单及执行、自动修复和通知配置。
- **归属证据**：实现仓可服务多个项目，按确认路径和本次证据限定项目，不将共享实现仓全部归给某项目；缺少项目证据时只保留可确认的域级范围，不套项目自动修复开关，不据推测启动写操作。已有来源问题仍按原幂等键聚合，不因多项目引用重复建单。
- **执行单元**：每轮按项目拆分三个 agent 的执行单元，只注入当前项目的仓库范围、配置与凭证；各项目独立落盘报告、上报与失败重试，单项目失败不阻塞其他项目。每轮开始时读取生效配置，运行中的配置调整于下一轮生效。
- **巡检总开关**：服务端定时巡检总开关默认关闭，需在环境配置中显式启用；总开关启用后，项目执行开关才参与调度，避免代码发布即自动产生扫描与 Credits 消耗。
- **执行开关**：可执行项目的执行开关默认开启；关闭后该项目三个 agent 均不执行，不扫描、不建单。该开关不影响需求管理缺陷分流建单，也不影响存量工单处理。
- **自动修复开关**：每个项目独立配置，默认关闭。关闭时 agent 只读分诊、仅提工单，不创建分支、不修改代码、不 commit、不 push；即使修复方案符合安全边界，也建 `PENDING_JUDGE` 工单并附修复建议。仅项目显式开启后，符合安全边界的修复才可提交推送；服务端还须按已确认执行映射核验 commit 属于该项目实现仓与确认路径、未越界到共享仓其他项目且不早于本轮开始，核验通过才建 `FIXED_REVIEW` 工单，否则按 `PENDING_JUDGE` 建单。
- **通知开关**：黑灯工厂全局通知与项目通知均默认关闭；仅两级开关同时开启时才发送该项目的工单通知，代码层默认值不得依赖企微公共开关恰好关闭。需求管理缺陷分流无项目归属时仅由黑灯工厂全局通知开关控制，默认同样不通知。
- **默认口径**：新进入执行范围的项目默认「执行开启、自动修复关闭、通知关闭」，即默认只提工单且不发送通知。
- **跳过规则**：仅维护 harness 工程、代码服务仓为空的项目直接跳过，不创建执行会话、不扫描、不建单，记录跳过原因与轮次审计，不按执行失败告警；域及项目管理已停用项目也不进入执行范围。
- **配置联动**：无代码服务仓或执行已关闭的项目不能开启自动修复；关闭执行开关时同步关闭自动修复。开关只影响后续轮次，不对存量待判断工单补做自动修复，存量待复核工单继续完成复核闭环。

## 2. 工单三分类(category)

| category | 来源动作 | 建单状态 | 说明 |
|---|---|---|---|
| `FIXED_REVIEW` 自动修复待复核 | 项目已开启自动修复，agent 已 commit+push 且服务端核验通过 | `REVIEW` | 带本轮项目仓 commit 哈希;复核通过→RESOLVED,打回→REOPENED |
| `PENDING_JUDGE` 待判断 | 默认仅提工单；unknown / keep-risk，或自动修复未开启 | `OPEN` | 必须带「建议:」人话结论、修复建议与已掌握证据 |
| `BIZ_CONFIRM` 业务确认 | business / keep-business | `OPEN`(低打扰) | 知会留痕;处理人确认口径后关闭或转办 |

服务端bug扫描的「评估是否需人为确认或直接修复」落为同一三分类：能安全直接修复且项目已开启自动修复 → `FIXED_REVIEW`；自动修复未开启、修复有风险或需技术负责人裁决 → `PENDING_JUDGE`；修不修属业务口径问题 → `BIZ_CONFIRM`（见 §10）。需求管理缺陷分流建单固定为 `PENDING_JUDGE`（已经人工审批确认真伪，无需再判业务口径），不受项目自动修复开关影响。

## 3. 状态机

```
                 ┌─────────────────────────────────────────┐
                 │                                         │
OPEN(待认领/已指派) ──认领──▶ CLAIMED(处理中) ──解决──▶ RESOLVED(已解决)
 │    │                                              ▲
 │    └──无需处理(备注必填)──▶ IGNORED(已关闭)      │复核通过
 │                                                  │
REVIEW(待复核) ──复核通过──▶ RESOLVED ──────────────┘
REVIEW ──复核打回(备注必填)──▶ REOPENED(≡OPEN,重新进入待认领)
RESOLVED/IGNORED 之后同源复发(新轮仍命中) ──原单重开(复发次数+1)──▶ 本轮分类初始态(OPEN/REVIEW)
```

规则:

- `CLAIMED` 只能由认领人本人或研发负责人执行「解决/转办」
- `IGNORED` 必须填原因(噪声/口径如此/三方问题);IGNORED 的单参与「免打扰」——agent 侧同键问题此后各轮仅计数
- `REVIEW` 超过 72h 未复核,按 P2 升级规则提醒(见 §6)

## 4. 建单幂等(防刷屏核心)

业务唯一键 = 来源 + 业务键,同键只保留一张工单:

| 来源 | 业务键构成 |
|---|---|
| `blacklight` 错误日志黑灯工厂 | 异常指纹(16 位十六进制,与错误日志黑灯工厂采集侧指纹口径一致) |
| `bigsqlfix` 大SQL结果集修复 | 服务名 + mapper 全限定名 |
| `bugscan` 服务端bug扫描 | 异常指纹(与错误日志管理同一归一化口径;来源不同故与 `blacklight` 同指纹不冲突) |
| `reqdefect` 需求管理缺陷分流 | 需求编号(一单一号;驳回重提沿用原编号,重提再次通过后向原未关闭单追加证据) |

upsert 规则(agent 每轮上报时执行):

1. 同业务键存在**未关闭**工单(OPEN/CLAIMED/REVIEW/REOPENED)→ **不新建**:出现次数累加本轮次数、出现轮次 +1、最近出现时间更新为本轮、证据追加本轮 traceId / SQL 样例(各 ≤3 条,滚动覆盖最旧)、摘要 / 建议若本轮有更新则覆盖
2. 同业务键工单已关闭(RESOLVED/IGNORED)后同源复发 → **原单复发重开**,不另开新单、不建立父子单关联：按本轮分诊结果与项目自动修复开关重定分类及初始状态，仅本轮实际完成自动修复提交时才以 `FIXED_REVIEW` 进入 REVIEW 并记录新 commit；其余按本轮结论以 `PENDING_JUDGE` / `BIZ_CONFIRM` 进入 OPEN，旧 commit 不得作为本轮修复凭证。认领 / 处理 / 复核信息清空重新起算,复发次数 +1,出现轮次续增,上轮关闭信息记入处理记录时间线
3. agent 侧「仅计数」条目(P3)不上报;上报内容要求见 §8

## 5. 负责人指派与改派

- 新建或改派的产研责任候选只读引用[产研人员管理 · 身份](../../../研发管理/产研人员管理/references/business-rule.md#identity)、[参与关系](../../../研发管理/产研人员管理/references/business-rule.md#membership)及[域及项目管理 · 责任关系](../../../研发管理/域及项目管理/references/business-rule.md#responsibility)，在有效职责范围内结合代码提交证据判定。无明确项目证据只使用已确认域范围，稳定门户 ID 与已确认跨源别名匹配，不取首人、不猜名；判不出则负责人为空、OPEN 待认领。业务责任身份不自动取得操作或 MCP 权限，边界见[产研人员管理 · 权限](../../../研发管理/产研人员管理/references/permission-rules.md#boundaries)
- 级别由 agent 落单时给定(P1/P2),Web 端展示不可改;分级口径变更只走 agent 手册
- Web 端支持**改派**(研发负责人角色):更新负责人(含姓名与企微账号)并记操作日志;处理中工单改派给非当前认领人时转为 REOPENED 并清空认领信息,旧认领人不得继续处理;改派后按 §6 在通知开启时提醒
- 负责人离职同步仍按门户人员主数据对账：未关闭且负责人已离职时按原流程清空当前负责人、置 OPEN 待认领，通知仍受原开关控制；操作与变更前责任信息留痕，不回写历史责任、认领、处理、复核或经办快照。产研业务禁用、域项目负责人变化只影响后续候选，不等同离职或自动重派存量工单

## 6. 通知规则

通知默认关闭。黑灯工厂全局通知开关与项目通知开关均开启后，通道 = 企微**应用消息**（复用公共功能「企微应用消息发送」，按负责人企微账号点对点）；群机器人仅保留 agent 侧采集失败 / 建单失败简报。任一级开关关闭时不发送个人或群通知，只保留工单与审计记录；需求管理缺陷分流无项目归属时仅受黑灯工厂全局通知开关控制。

| 时机 | 内容 | 频控 |
|---|---|---|
| 新单创建(含合并上报后出现次数环比翻倍以上的复发单) | 「黑灯工厂新工单 [级别] 标题 | 来源服务 | 点链接处理」 | 同一接收人每轮(3h)最多 1 条,多单合并为「新工单 N 条:P1×a P2×b」 |
| 改派 | 「你有工单被改派过来」 | 即时,不频控 |
| REVIEW 超 72h 未复核 | 提醒复核人 | 每日 09:30 合并 1 条 |
| OPEN/CLAIMED 超 SLA(§7) | 提醒负责人,抄送其直属上级 | 每日 09:30 合并 1 条 |
| 采集失败 / 建单失败(agent 侧) | 群机器人简报 @ chenguojian | 每轮最多 1 条 |

## 7. SLA 与统计

| level | 响应 SLA(OPEN→CLAIMED/IGNORED) | 闭环 SLA(建单→RESOLVED/IGNORED) |
|---|---|---|
| P1 | 8 个工作小时 | 24h |
| P2 | 24h | 72h |
| FIXED_REVIEW | — | 72h(复核时限) |

- 超时列表行标红 + §6 提醒;工作小时 = 09:00~21:00
- 列表 KPI 与导出支撑:修复率(FIXED_REVIEW 复核通过率)、平均响应/闭环时长、复发率(复发次数 ≥1 的单占比)、负责人维度分布
- 工单保留 180 天,超期由独立清理任务每日删除(与错误日志管理保留期机制一致)

## 8. agent 接入规范

三个 agent 按 §1.1 分项目执行并落盘完成后，经内部上报工具向 devops 服务批量建单（单项目单轮一次调用；走 devops 内部鉴权，不对外开放）：

- 上报内容：来源 + 当前项目问题条目清单，每条含业务键、级别、分类、服务、标题等，负责人以邮箱标识；字段契约以代码仓为准
- 服务端职责：按 §5 当前有效责任候选与已确认跨源别名将负责人邮箱唯一关联稳定门户身份，取得当时姓名与企微账号（缺失或歧义则留空待认领，不取首人）→ 按 §4 upsert → 按 §6 原通知开关触发提醒；调用方经办身份与历史责任快照不因基础真源变化改写
- 幂等由业务唯一键 + upsert 保证，agent 失败重发安全；单项目采集或上报失败不阻塞其他项目
- 内部上报工具同时提供工单回复（追加备注到处理记录时间线）与状态流转（认领 / 解决 / 忽略 / 复核通过 / 复核打回 / 改派）能力，均为写操作，操作人沿用调用方登录身份
- 采集失败或建单失败时，agent 按 §6 在通知开启时发群机器人简报，默认仅记录日志与审计；无代码服务仓导致的项目跳过只记审计，不发失败简报

需求管理缺陷分流建单复用同一内部上报通道:来源 `reqdefect`、业务键 = 需求编号,级别按需求优先级映射(P0/P1→P1、P2/P3→P2),负责人留空时按代码归属判定、判不出则待认领;建单失败在需求管理侧记事件审计并告警重发,幂等同 §4。

- 菜单:运维管理 → 黑灯工厂工单(二级),菜单权限码 `MENU:RND:OPS:BLACKLIGHT_TICKET`,仅 WEB
- 按钮权限:`BUTTON:RND:OPS:BLACKLIGHT_TICKET:CLAIM`(认领/解决/忽略)、`BUTTON:RND:OPS:BLACKLIGHT_TICKET:REVIEW`(复核通过/打回)、`BUTTON:RND:OPS:BLACKLIGHT_TICKET:REASSIGN`(改派,研发负责人)、`BUTTON:RND:OPS:BLACKLIGHT_TICKET:CONFIG`(项目执行、自动修复与通知开关,研发负责人)、`BUTTON:RND:OPS:BLACKLIGHT_TICKET:EXPORT`(导出)
- 「研发负责人」以持有改派按钮权限判定
- 操作日志覆盖:认领/解决/忽略/复核/打回/改派(与统一操作日志口径一致);工单操作日志独立留存并渲染为详情页处理记录时间线,同时写入应用日志
- 项目执行、自动修复与通知开关调整记录配置审计，包含项目、操作人、操作时间与变更前后值；开启自动修复须二次确认，服务端校验配置权限与项目可执行状态

## 10. 服务端 bug 扫描 agent(bugscan)

第三个黑灯 agent，在「报错分诊」之上叠加「需求口径对照」，回答两个问题：**这算不算缺陷、能不能直接修**。评估不等于默认修复，处置仍受 §1.1 项目自动修复开关约束。

- **巡检节奏**：与既有 agent 同频（每 3 小时一轮），按 §1.1 分项目执行，产出统一走 §8 上报
- **错误提取**：从 SLS 拉取当前项目本轮 ERROR 日志，按指纹归一化聚合（口径复用「错误日志管理」），剔除已有未关闭工单与同键已忽略的指纹，只深析增量
- **项目定位**：按 §1.1 引用域及项目管理的执行映射与确认路径，不能仅凭实现仓推定单一项目；仅维护 harness、无可执行实现仓的项目跳过。仅能确认域时保持域级证据，不套用项目修复开关；无法确认对应 harness 对照依据的应用仍仅计数与审计，不强行建项目单
- **对照评估**：读取当前项目 harness 工程（需求/规则文档）与报错路径相关业务代码，对照「文档期望行为 vs 代码实际行为」，产出三态结论：

  | 结论 | 建单分类 | 说明 |
  |---|---|---|
  | 确为缺陷、修复方案安全明确，且项目已开启自动修复 | `FIXED_REVIEW` | 直接修复：agent commit+push 后建单待复核 |
  | 确为缺陷，但自动修复未开启、修复有风险或需技术负责人裁决 | `PENDING_JUDGE` | 默认仅提工单：按代码负责人指派待认领，附修复建议与证据，不修改或推送代码 |
  | 行为与文档冲突、修不修是业务口径问题 | `BIZ_CONFIRM` | 人为确认：知会留痕，业务确认后关闭或转办 |

- **默认仅提工单**：项目自动修复开关默认关闭；关闭时不创建分支、不修改代码、不 commit、不 push，修复方案安全明确也按 `PENDING_JUDGE` 建单
- **非缺陷收口**：评估为口径如此/噪声的仅计数不建单（同 P3 口径），防刷屏
- 级别、负责人指派、幂等、通知、SLA 均复用 §4~§7 既有口径，不另立规则

## 11. 反模式

- 手工页面建单(绕过 agent 分诊,破坏幂等键)
- agent 每轮全量新建而不走 upsert(刷屏根因)
- 把 P3/仅计数条目也建单(工单变报表)
- 复核打回不填备注(打回即 REOPENED,没有上下文认领人无法接手)
- 关闭单时不同步 agent 跨轮状态(IGNORED 后 agent 仍重复深析)
- 项目未开启自动修复仍修改代码或推送(违反默认仅提工单)
- 绕过域及项目管理另建项目仓库映射,或把未配置代码服务仓的项目纳入执行
- 单项目失败即中断整轮其他项目执行
- bugscan 跳过 harness 对照直接按堆栈改代码(把「口径如此」当缺陷修,产生回归)

# 实施管理

面向实施 / 测试负责人员的轻量排期工具：每 15 分钟增量任务（夜间 23:40 全量兜底）将「功能排期」中新完成的卡片按功能聚合，每个功能生成一张**实施卡片**（内容 = 根据需求与代码变更生成的变更待测试项），沉淀到 Backup 卡片池；亦可在 Backup 面板「手动选卡」勾选功能排期完成卡即时生成，不必等任务；实施人员拖拽排期到月历、领取实施、点击完成，全程三态跟踪（待实施 / 实施中 / 实施完成）。

## 端

**仅 Web 端**（管理后台 Portal 下「研发管理」分组）。App 端不提供此入口。

## 产品背景

功能排期解决了「研发交付了什么、什么时候交付」，但交付之后的**实施验证环节**（部署、联调、测试、上线确认）没有可视化锚点：

- 功能排期里开发完成的卡片越来越多，哪些已经实施验证、哪些还压着，靠口头同步
- 一个功能往往由多张开发卡组成，实施验证的对象是「功能」而不是单张 commit 卡片
- 变更影响了哪些待测试项，靠实施人员自己翻 commit 记录，容易漏测

本模块提供「功能排期完成卡 → 按功能聚合 → 实施卡片 → 排期日历」的闭环：

1. **聚合即出卡**：15 分钟增量任务（+ 夜间 23:40 全量兜底）扫描功能排期中新变为「开发完成」的卡片，按功能分组，每个功能生成一张实施卡片；卡片内容根据需求描述与代码变更自动生成「变更待测试项」；亦可在 Backup 面板「手动选卡」即时生成，不必等任务
2. **拖拽即排期**：Backup 卡片池的卡片可拖到月历指定日期，跨天移动亦支持
3. **领取即开工**：状态切到「实施中」自动写入领取人与实施开始日期（= 领取时间）
4. **完成即闭环**：点击「实施完成」自动写入实施结束日期（= 点击完成按钮的时间）

## 实施卡片字段

| 字段 | 说明 |
|------|------|
| 卡片编号 | `IS-{YYYYMMDD}-{NNN}`，生成时按创建日期分配，全局唯一、不回收 |
| 创建日期 | 生成时间（15 分钟增量任务 / 夜间兜底任务 / 手动拉取；系统写入，不可修改） |
| 实施开始日期 | = 领取时间，状态切到「实施中」自动写入；取消领取清空 |
| 实施结束日期 | = 点击「实施完成」的时间；回退清空 |
| 标题 | 默认 = 功能名概括，≤ 30 字，可手改 |
| 内容 | 变更待测试项：根据需求描述与代码变更自动生成，可人工补充修正 |
| 领取人 | 状态切到「实施中」时自动填入当前操作人；从「待实施」直接点完成时自动回填当前操作人 |
| 排期日期 | 通过拖拽改变；为空表示卡片在 Backup 池 |
| 来源功能排期卡 | 聚合来源的功能排期卡号集合（只读，便于回溯） |
| 所属模块 | 功能标识由「模块 · 子模块 · 功能」三段组成，取首段为所属模块；无该结构的标识（直接引用功能排期卡号或为空）归「未归类」。实时派生，不单独存储 |
| 业务对接人 | 生成时写入快照：功能排期卡手工值优先；无手工值取关联需求单（REQ）提交人（内部单取提交人的系统用户姓名，外部单取外部提交人姓名）；均无则空（显示「—」）。只读，维护入口在功能排期侧（功能排期在排期保存时做必填校验：无需求单关联且非技术支持卡排期前必须补录，有需求单关联的卡预填提交人、可修改——进入排期的功能卡原则上必有对接人取值来源） |

数据模型、编号分配与生成任务调度等实现细节以代码仓为准，不内嵌；状态机 / 权限 / 校验规则详见 [references/business-rule.md](references/business-rule.md)。

## 状态机

```
                ┌─────────────────────┐
 任务生成/手动 ─►│  PENDING（待实施）  │ 白底灰框
   拉取         └──────────┬──────────┘
                 领取实施   │  ▲
               (领取人=   ▼  │ 取消领取（清空领取人 + 实施开始日期）
                当前用户)     │
                ┌─────────────────────┐
                │ IN_PROGRESS（实施中）│ 紫底 + 左侧紫色色条
                └──────────┬──────────┘
                           │ 点击「实施完成」（写入实施结束日期）
                           ▼
                ┌─────────────────────┐
                │   DONE（实施完成）   │ 绿底 + 左侧绿色色条
                └──────────┬──────────┘
                           │  ▲
                回退待实施 ▼  │ 回退实施中
                ┌─────────────────────┐
                │  PENDING / IN_PROGRESS
                └──────────┬──────────┘
                 手动移入   │  ▲
                           ▼  │ 恢复为待实施
                ┌─────────────────────┐
                │ NON_IMPL（非实施需求）│ 黄底 + 左侧黄色色条
                └─────────────────────┘
                约束：清空排期/领取人/实施起止日期，不进 Backup 与月历
                来源二态：人工移入 / 技术类自动划入
  生成任务（来源功能排期卡需求性质 = 技术支持）──► NON_IMPL（标注「技术类」，来源 = 技术类自动划入）
```

- 四态：`PENDING`（待实施）/ `IN_PROGRESS`（实施中）/ `DONE`（实施完成）/ `NON_IMPL`（非实施需求）
- **领取实施**：`PENDING → IN_PROGRESS`，写入领取人与实施开始日期，记「领取」操作记录
- **取消领取**：`IN_PROGRESS → PENDING`，清空领取人与实施开始日期，记「取消领取」操作记录
- **点击完成**：`PENDING / IN_PROGRESS → DONE`，写入实施结束日期；若来自待实施且无领取人，自动回填当前操作人为领取人、实施开始日期 = 完成时间；记「标记完成」操作记录
- **回退**：`DONE → PENDING`（清空实施结束日期、领取人与实施开始日期）或 `DONE → IN_PROGRESS`（仅清空实施结束日期），记「回退」操作记录
- **DONE 卡片锁定**：不可拖拽改期，也不可拖回 Backup；如需改期必须先回退
- **NON_IMPL 旁路态（双来源）**：
  - **人工移入**：抽屉内点击「移入非实施需求」手动触发，任意状态可移入；移入时清空排期日期、领取人、实施开始/结束日期，来源记为人工移入；**同步回写来源功能排期卡需求性质为技术支持**，使次日聚合同类卡自动分流，避免每日重复移入；记「移入非实施」操作记录（附「已回写功能排期卡需求性质」）
  - **技术类自动划入**：来源功能排期卡需求性质为技术支持时，生成任务生成即落 `NON_IMPL`，来源记为技术类自动划入（卡片标注「技术类」），不进 Backup / 月历 / 四状态计数、不触发未领取提醒；记「生成」操作记录（附「技术类需求，自动划入非实施区」）
  - 两类卡共用非实施弹层（来源标识可区分），均仅允许编辑标题/内容，均可「恢复为待实施」；恢复只回 `PENDING` 并清除非实施来源标记，**不回写功能排期卡需求性质**（需求性质跟随功能粒度，恢复单张实施卡不改变功能性质——性质仍为技术支持的该功能次日新完成卡聚合仍自动分流）

## Tips

- 卡片编号只对内部生效；同一功能同一天只生成一张实施卡片（同功能同日唯一保底），删除后当天不再生成，次日功能排期仍有新完成卡时才再次聚合生成
- **实施卡生成三通道**：①15 分钟增量任务（较上次成功运行时间前推 5 分钟重叠扫描至当前，水位持久化、仅整轮成功后推进，同功能同日唯一保证幂等）；②夜间 23:40 全量兜底（扫当天完成卡，专收增量通道停机 / 中断期间的漏网卡）；③Backup 面板「手动选卡」即时生成。三通道共用聚合 / 技术类分流 / 对接人快照逻辑与同功能同日唯一幂等——开发完成后 15 分钟内实施卡即落 Backup，手动通道覆盖「等不及」与「补拉救援」场景
- **「超 12 小时未领取」提醒**：计时起点为实施卡生成时间（开发完成后 15 分钟内生成），白天完成的卡当天晚间即可触发提醒；提醒对象为功能负责人
- 手动选卡候选不含技术支持卡：技术类完成卡由生成任务自动划入非实施区留痕、无需实施，不提供手选；误标为技术支持的卡请在功能排期侧改回业务功能，待下一轮任务自动聚合
- 聚合分组键 = 功能标识：功能排期卡片关联的需求 / 模块决定归属；无需求关联的完成卡按来源模块兜底分组
- 「变更待测试项」由任务根据需求描述 + 完成卡关联的 commit message 汇总生成，实施人员可在抽屉中补充修正（记「编辑」操作记录）
- 「只看自己」只按领取人过滤月历与统计，Backup 池保持全员可见 —— 未领取卡片需要被所有人看到才能被领取
- Backup 池默认按创建日期倒序（最新生成的排最上）；页面保持打开 24h 以上建议刷新以获得准确相对时间
- 一张实施卡片在时间上只能排到一天；跨多日实施请在内容中备注
- 权限最小授予：仅将 `MENU:DEV:IMPL_SCHEDULE` 授予实施 / 测试负责人与研发管理员
- 模块标识与筛选均由功能标识首段实时派生，不单独存储、不回填；无「模块 · 子模块 · 功能」结构的功能标识（直接引用功能排期卡号或为空）属存量兜底形态，归「未归类」
- 业务对接人是**生成时快照**：生成后功能排期侧再改对接人不影响既有实施卡；需修正请在功能排期卡维护后等次日新卡生效，或直接忽略（展示性字段）
- 需求性质为技术支持的卡生成即落 NON_IMPL：不占 Backup / 月历 / 状态计数、不触发「超 12 小时未领取」企微提醒——提醒降噪是该分流的核心收益之一
- 「移入非实施」回写功能排期卡性质是闭环关键：只改实施卡不回写源头时，同功能次日新完成卡会再次聚合成业务卡，造成「每日重复移入」；回写后次日自动分流
- 「超 12 小时未领取」企微提醒对象为**功能负责人**，不抄送业务对接人

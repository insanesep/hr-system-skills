# 需求管理业务规则

本文件为需求管理模块的规则真源。SKILL.md 仅作导航，具体判定以本文件为准。数据模型、接口契约与定时任务配置等实现细节以代码仓为准。

---

## 1. 业务流程总览

需求从提出到进入研发排期共 5 步，前 3 步在需求管理模块内闭环，第 4 步交接产品经理，第 5 步由 [功能排期](../../功能排期/SKILL.md) 承接。

> **审批链驱动模式**：内部提交**先选定提交对象（产品经理）**，系统按该对象的专属审批链（级次由配置决定，1~3 级）流转；外部提交无提交对象，固定走「产品线 × 业务线 × 需求类型 × 优先级」四维**默认链**。规则真源见 §3。

| 步骤 | 名称 | 执行角色 | 产出 |
|------|------|---------|------|
| 1 | 需求提交 | 业务线员工（内部，**先选定提交对象·产品经理**）/ 外部人员（凭外链，无提交对象） | 生成需求单，编号 `REQ-{YYYYMMDD}-{NNN}`，进入审批链第一级待审 |
| 2 | 前置审批 | 链上前置级次审批人（业务线审批 L1 / 实施确认 L2；级次由命中链决定，未配置的级次直接跳过） | 判定需求合理性、实施可行性并归集同类需求，通过则流转链上下一级，驳回则回提交人 |
| 3 | 产品确认 | 提交对象（产品经理，L3；外部单为默认链 L3 配置的产品经理） | 终审需求价值与方案，通过则需求进入待关联排期 |
| 4 | 产品提交 | 提交对象（产品经理） | 完成需求打磨并关联排期卡片，需求进入 LINKED 终态 |
| 5 | 研发开发 | 研发 | 在 功能排期 中领取卡片开发，状态回传需求详情页 |

> **缺陷分流**：需求类型为「缺陷修复」的单据即**人工报 bug 的唯一入口**，前 3 步审批不变（确认缺陷真伪、责任归属与修复价值），全部审批通过后不走步骤 4/5，自动分流至黑灯工厂自动化修复，规则见 §2.7。
>
> **下游承接**：功能类需求关联排期卡片后，系统按「需求 + 卡片」生成 Qoder 开发会话承接实施（见 §5.2）；缺陷单由黑灯工厂承接（§2.7），不生成开发会话。

### 1.1 产品线与业务线枚举

**产品线**为需求的第一层归属维度，固定 2 值，新增需 DBA 与管理员同步维护审批链配置。

| 枚举值 | 名称 | 业务线取值 | 提交方式 |
|--------|------|-----------|---------|
| `SNACK` | 鸣鸣很忙 | 必选 `OPS`/`FIN`/`SCM`/`DIGITAL` 之一 | 仅内部登录用户（Web / App）|
| `YDTJ` | 有点推荐 | 不区分业务线 | 内部登录用户 + 外部人员凭外链免登录 |

**业务线**仅在 `SNACK` 产品线下生效，固定 4 条，不支持自定义扩展（新增需 DBA 与管理员同步维护审批链配置与企微群映射）。

| 枚举值 | 名称 | 说明 |
|--------|------|------|
| `OPS` | 运营 | 门店营运、店务执行、任务协同相关需求 |
| `FIN` | 财务 | 结算、凭证、对账、税务相关需求 |
| `SCM` | 供应链 | 采购、配送、仓储、库存相关需求 |
| `DIGITAL` | 数字化 | 数据报表、系统集成、硬件与基础能力相关需求 |

- `YDTJ` 的业务线由系统统一记为「不区分」，不向用户展示也不可选，**不得为它新增业务线枚举值**

### 1.2 角色定义

| 角色 | 职责说明 |
|------|---------|
| 业务线员工 | 需求提出方，负责描述业务背景、痛点与期望效果；可撤回与修改草稿 |
| 外部提交人 | 非系统用户（外部伙伴 / 兼职人员等），凭内部人发放的一次性定向外链提交有点推荐需求；无账号、无草稿、无撤回、不可查进度 |
| 邀约人 | 生成外链的内部用户，对所发放链接产生的需求负溯源责任；可撤销自己生成的链接 |
| 业务线负责人 | 各业务线一名（4 条业务线各自独立），L1 审批人，把关本业务线需求的必要性与优先级 |
| 实施负责人 | 全公司统一入口，L2 审批人（默认链与配置了该级的专属链），负责需求归集、去重与可行性判断 |
| 产品经理 | **提交对象**：内部需求提交时由提交人必选；链上末级（L3 产品确认）审批人，负责需求打磨、方案确认与排期卡片关联；外部单由默认链 L3 配置的产品经理承接 |
| 研发 | 不参与审批，在 功能排期 侧领取卡片并推进开发状态 |

### 1.3 流程约束

- 需求必须归属唯一产品线，且归属唯一业务线（`YDTJ` 不区分业务线），提交后两者均不可修改（如需变更需驳回重提）
- **内部提交必须选定提交对象（产品经理）**，提交对象随提交记录并作为排期关联责任人；草稿与驳回重提时可更换提交对象（更换后按新对象重新匹配审批链并生成新快照）
- 同一提交人对同一业务线可并行提交多条需求，无数量限制
- 需求从提交到 LINKED 全链路留痕，任意状态变更写入审批流水与事件审计
- **外部提交单直接走默认审批链第一级待审**，不设待受理初筛池（链接为内部人定向发放，来源天然可信）；外部人无登录态不可选提交对象，固定走默认链（§3.2）；仅 `YDTJ` 产品线开放外链提交

## 2. 状态机

### 2.1 状态流转图

```
DRAFT → SUBMITTED → BU_REVIEWING(L1) → BU_APPROVED
  → IMPL_REVIEWING(L2) → IMPL_CONFIRMED → PM_REVIEWING(L3) → PM_SUBMITTED
  → LINKED（已关联排期卡片）
REJECTED（任意级次驳回）→ 可重新提交回到 SUBMITTED（级次重置为链上第一级）
```

> 上图为完整三级链；**链上未配置的级次直接跳过**，不产生对应状态与流水（如专属链仅配 L3：`SUBMITTED → PM_REVIEWING`）。级次集合由提交时命中的审批链决定（§3.4）。

### 2.2 状态定义

| 状态 | 含义 | 当前级次 | 可执行操作 |
|------|------|---------|-----------|
| `DRAFT` | 草稿，仅提交人可见 | 0 | 编辑 / 提交 / 删除 |
| `SUBMITTED` | 已提交，等待系统匹配审批链（内部单匹配提交对象专属链，外部单匹配默认链） | 1 | 撤回 |
| `BU_REVIEWING` | 业务线负责人审批中 | 1 | L1 通过 / L1 驳回 / 提交人撤回 |
| `BU_APPROVED` | 业务线审批通过（瞬时态） | 1→2 | 自动流转至链上下一已配置级次 |
| `IMPL_REVIEWING` | 实施负责人审批中 | 2 | L2 通过 / L2 驳回 |
| `IMPL_CONFIRMED` | 实施确认完成（瞬时态） | 2→3 | 自动流转至链上下一已配置级次 |
| `PM_REVIEWING` | 产品经理审批中 | 3 | L3 通过 / L3 驳回 |
| `PM_SUBMITTED` | 全部审批通过，待关联排期（缺陷修复单为待系统自动分流黑灯工厂，§2.7） | 链上最大级次 | 关联排期卡片 |
| `LINKED` | 已关联下游承接单（排期卡片或黑灯工厂工单），终态 | 链上最大级次 | 仅查看（排期状态 / 工单状态实时刷新） |
| `REJECTED` | 被驳回，终止态 | 保留驳回时级次 | 内部单：提交人重新提交；外部单：无（真终态）|

### 2.3 级次递进规则

- 当前级次记录当前待审级次：`0`=未提交、`1`=业务线审批、`2`=实施确认、`3`=产品确认
- 最大级次由提交时命中的审批链决定：默认链固定为 3；专属链取其配置的级次集合中的最大值（专属链可仅配部分级次，§3.2）
- 每级审批通过后流转至**链上下一个已配置级次**（非机械 +1，未配置的级次直接跳过）；达到最大级次且通过后状态置 `PM_SUBMITTED`
- `BU_APPROVED` / `IMPL_CONFIRMED` 为同事务内的瞬时中间态，用于流水记录与消息推送打点，前端不单独展示节点；级次被跳过时对应瞬时态不产生

### 2.4 驳回与重提

- 任意级次均可驳回，驳回必填意见（≥ 10 字），意见记为需求驳回原因并写入审批流水
- 驳回后状态置 `REJECTED`，保留驳回发生时的当前级次供统计分析
- 提交人可在 `REJECTED` 状态下修改内容并重新提交：状态回到 `SUBMITTED`，当前级次重置为**链上第一级**，重新生成审批链快照；重提时**可更换提交对象**（默认回填原值），更换后按新对象重新匹配审批链
- 重提沿用原需求编号，不新建需求记录；历史审批流水全部保留，按审批轮次区分
- **仅内部提交单可重提**；外部提交单的 `REJECTED` 为真终态，详见 §2.6

### 2.5 撤回规则

- `SUBMITTED` / `BU_REVIEWING` 状态下提交人可撤回，状态回到 `DRAFT`，审批链快照作废
- 进入 `IMPL_REVIEWING` 及之后不允许撤回，需由审批人驳回
- 撤回记录写入事件审计，不写审批流水
- **外部提交单不支持撤回**（无账号则无撤回主体，且无 `DRAFT` 可回退）

### 2.6 外部提交单的规则差异

外部提交单**不新增任何状态**，完全复用现有 10 态状态机，仅以下规则不适用：

| 不适用规则 | 原因 | 外部单实际表现 |
|-----------|------|---------------|
| `DRAFT` 草稿态（§2.2）| 无登录态无法回取未完成表单 | 提交即生成 `SUBMITTED`，无暂存入口 |
| 驳回重提（§2.4）| 不回传结果，外部人无从得知驳回 | `REJECTED` 即真终态，不提供重提入口 |
| 提交人撤回（§2.5）| 无账号主体 | 无撤回按钮，内部人也不得代撤回 |
| 提交人即审批人自动跳过（§4.2）| 外部人不可能是审批人 | 完整走 L1/L2/L3 三级，不会发生跳级 |
| 提交人结果通知（§6.1）| 无企微身份且不回传 | 仅推送内部审批人与邀约人，不推外部提交人 |

**驳回后的价值回收路径**：外部单被驳回后如内部认为仍有价值，由**实施负责人新建一条内部单**并在描述中引用原需求编号溯源；**不提供「转内部单」功能**，避免状态机分叉与归属变更。

### 2.7 缺陷修复需求的分流规则（人工报 bug 入口）

需求类型为「缺陷修复」（`BUGFIX`）的单据是**人工发现 bug 的唯一入口**（内部 Web/App 与外部 H5 均可提交）；黑灯工厂工单不提供手工新建，人工报障一律经本模块审批后分流。

- **提交与审批**：表单字段、审批链匹配（§3）、状态机流转与非缺陷需求完全一致；审批人职责为确认缺陷真伪、责任归属与修复价值
- **自动分流**：末级审批通过（状态 `PM_SUBMITTED`）后，系统**自动**调黑灯工厂建单接口生成工单——缺陷单不开放「关联排期卡片」入口，缺陷修复不占用功能排期
  - 工单幂等键：需求编号（一单一号；驳回重提沿用原编号故不重复建单，重提再次通过后向原未关闭工单追加证据）
  - 工单分类：`PENDING_JUDGE`（待判断）；级别按需求优先级映射（`P0/P1→P1`、`P2/P3→P2`）；负责人由黑灯工厂侧按代码归属判定，判不出则待认领
  - 建单失败不阻塞审批结果：失败写事件审计并告警，按幂等键重发安全
- **终态与回传**：建单成功需求状态置 `LINKED`（终态），关联对象为黑灯工厂工单（记关联工单号，不占关联卡片编号）；工单级别 / 状态 / 负责人 / 处理进展在需求详情页**只读回传**（与排期卡片状态同区展示），本模块不回写工单任何字段（单向关联口径同 §5）
- **结果通知**：工单关闭（已解决 / 已忽略）时按 §6.1 个人消息推送提交人与产品经理；忽略类关闭（噪声 / 口径如此 / 三方问题）文案须带关闭原因

## 3. 审批链配置规则

> **驱动模式**：审批链由**提交对象（产品经理）**驱动 —— 提交需求与配置审批链时都**先选定产品经理，再根据其设定审批流程**；「产品线 × 业务线 × 需求类型 × 优先级」四维配置为**默认链**，承接外部提交，SNACK 默认链作防御性兜底。

### 3.1 条件维度

审批链按 **提交对象 →（产品线 × 业务线 × 需求类型 × 优先级）** 匹配；「提交对象」为第一优先维度。

| 维度 | 取值 | 是否支持降级 |
|------|------|-------------|
| 提交对象 | 具体产品经理；未指定产品经理的配置即**默认链** | 不支持通配，必须等值命中 |
| 产品线 | `SNACK` / `YDTJ` | 不支持，必须等值命中 |
| 业务线 | `OPS` / `FIN` / `SCM` / `DIGITAL`（`YDTJ` 不区分）| 不支持，必须等值命中 |
| 需求类型 | 新功能 / 功能优化 / 缺陷修复 / 数据报表 / 系统集成 | 支持通配 |
| 优先级 | `P0` / `P1` / `P2` / `P3` | 支持通配 |

四维降级顺序（在确定提交对象维度后执行）：四维全等值 → 优先级通配 → 需求类型通配 → 需求类型与优先级均通配，命中即止。

### 3.2 两类链：PM 专属链与默认链

| 链类型 | 配置特征 | 级次要求 | 承接场景 |
|--------|-----------|---------|---------|
| **PM 专属链** | 指定了产品经理 | L1/L2/L3 的任意**非空子集**（级次由配置决定：如仅 L3 产品确认、L2+L3、完整三级） | 内部提交（唯一通道） |
| **默认链** | 未指定产品经理（四维配置） | `YDTJ` 须配齐 **L1/L2/L3** 三级（L3 承接外部提交，见 §3.4）；SNACK 各业务线配 L1/L2 作防御性兜底 | ① 外部提交（无提交对象，唯一通道）；② SNACK 默认链为防御性兜底，内部单必中专属链，正常不命中 |

- 级次语义固定：`1`=业务线审批、`2`=实施确认、`3`=产品确认；专属链未配置某级 = 流转时跳过该级
- 配置页操作范式：**先选提交对象（产品经理），再配置其审批流程**（级次勾选 + 各级审批人）；选「默认链」则维护四维配置
- 专属链可按四维再细化（同一 PM 下不同类型 / 优先级走不同级次组合）；不细化即通配
- 默认链 L3 配置的产品经理**仅承接外部提交单**；SNACK 默认链无需配置 L3，`YDTJ` 默认链必须配齐 L3（缺级时外链生成与外部提交均被拒）
- **提交对象候选集（配置驱动）**：提交页的提交对象候选按「产品线 × 业务线」过滤，**仅包含在该归属下配有启用中专属链的产品经理**（去重，且须为在职有效的系统用户）；内部提交因此必中专属链，默认链不承接内部单。🚨 **配置页的「指定产品经理」选择器不使用该候选集**，走全员人员搜索——否则没配过链的新 PM 永远无法被配置（循环依赖）

### 3.3 各产品线 / 业务线默认链

每个「产品线 + 业务线」组合独立配置默认链，差异集中在 L1（负责人不同）；L2 实施负责人为全公司统一入口。

| 产品线 | 业务线 | L1 | L2（实施负责人）| L3（产品经理）|
|--------|--------|----|------------------|------------------|
| 鸣鸣很忙 | 运营   | 运营负责人     | 实施负责人 | 无需配置（内部单全走专属链，默认链仅防御兜底） |
| 鸣鸣很忙 | 财务   | 财务负责人     | 实施负责人 | 无需配置（同上） |
| 鸣鸣很忙 | 供应链 | 供应链负责人   | 实施负责人 | 无需配置（同上） |
| 鸣鸣很忙 | 数字化 | 数字化负责人   | 实施负责人 | 无需配置（同上） |
| 有点推荐 | 不区分 | 有点推荐负责人 | 实施负责人 | 默认承接**外部提交单**的产品经理 |

- 有点推荐默认链只需配一套；内部提交走 PM 专属链，默认链仅承接外部提交

### 3.4 匹配顺序（提交时）

**内部提交**（提交对象 = P，必选）：

1. **匹配 PM 专属链**：在提交对象为 P 的专属链中按 §3.1 四维降级命中即止 → 快照级次 = 专属链配置的级次集合，最大级次 = 链上最大级次
2. **未命中专属链 → 提交失败**：候选集仅含本归属有专属链的 PM（§3.2），正常选人必中专属链；仅当专属链在选人后被停用 / 删除时才可能未命中，此时提示「当前归属未配置审批链，请联系管理员」，内部单不落默认链

**外部提交**（无提交对象）：按 §3.1 四维降级匹配默认链，L3 取默认链配置的产品经理（或签）；L3 审批通过时将实际通过人记为该需求的产品经理。**未命中配置时不得暴露内部配置信息**：向外部人统一提示「提交暂时不可用，请联系邀约人」，同时向邀约人推送企微告警（详见 §8.5）。

### 3.5 或签模式

- 各级审批均为**或签**：同一级次配置多名审批人时，任一人通过即视为该级通过，其余人待办自动关闭
- 任一人驳回即整单驳回，不等待其他审批人
- 或签模式参考 任务中心 的待办聚合与关闭逻辑，本模块不引入全员确认（多签）模式

### 3.6 快照机制

- 提交（含驳回重提）时按 §3.4 匹配，将链上各级审批人写入审批链快照；专属链仅写入其配置的级次（未配置的级次不产生快照）
- 流转过程中只读快照，不再回查配置：配置变更不影响在途需求，避免中途换人导致审批断链
- 审批人离职或调岗时，管理员需更新配置并对在途需求执行「审批链重建」：按需求的提交对象重新走 §3.4 匹配（内部单仅匹配专属链；适用于自研通道单，流程中心通道单按 §12.5 第 8 条处置），旧快照作废，审批轮次与级次集合保持不变——**重建只替换审批人，不增减级次**，操作写入事件审计

### 4.2 权限约束

- 审批操作后端二次校验：当前登录人必须存在于审批链快照的**当前级次**审批人清单中，否则拒绝操作
- **流程单豁免**：需求已关联流程中心实例时，上款快照校验**不执行**——页内「通过/驳回」直接以操作人身份代为调用流程中心审批，以流程中心节点快照匹配为唯一闸门（流程中心拒绝即为无权限），避免流程中心侧转审 / 加签 / 管理员跳节点后两侧快照不一致把合法审批人误拦在页内（规则真源：流程中心 business-rule §6.3）；自研通道单维持上款校验
- 提交人不得审批自己提交的需求；若提交人同时为该级审批人，则该级自动跳过并写入流水说明（仅对内部单的自研通道生效，流程中心通道见 §12.4⑥）
- App 端仅开放提交、L1/L2/L3 审批通过与驳回；审批链配置、外链生成与管理、统计导出仅 Web 端可用
- **公开接口不进登录鉴权体系**：外链相关公开接口免登录，仅以 token 有效性 + 图形验证码 + 频率限制作为准入控制（详见 §8.4），**不得复用内部提交接口**

## 5. 排期关联规则

- 🚫 **缺陷修复（`BUGFIX`）需求不适用本节**：审批通过后按 §2.7 自动分流黑灯工厂，无排期关联入口
- 关联入口在全部级次审批通过（状态 `PM_SUBMITTED`）后开放，仅该需求的产品经理（内部单为提交对象，外部单为 L3 实际通过人）与管理员可操作
- 关联方式二选一：输入卡片编号精确搜索，或从「候选排期卡片列表」中选择
- 关联结果记录卡片编号，需求状态置 `LINKED`
- 卡片状态实时展示：详情页实时读取 功能排期 卡片，展示 `PENDING`（待开发）/ `IN_PROGRESS`（开发中）/ `DONE`（开发完成）及排期日期
- **单向关联**：本模块只读取排期卡片信息，不回写卡片任何字段；卡片被删除时需求详情页展示「关联卡片已失效」提示，需重新关联
- 一条需求只能关联一张卡片；一张卡片允许被多条需求关联（同一卡片承载多条同类需求）
- 关联可解除：解除后状态回退至 `PM_SUBMITTED`，关联卡片编号清空，写入事件审计

### 5.1 候选卡片列表（方式二）

候选集为全部有效排期卡片（含已关联），支撑「同类需求同挂一张卡片」场景的卡片定位，并提供「开发人 / 需求提交人」双筛选维度。

- **候选集**：全部有效排期卡片（`PENDING` / `IN_PROGRESS` / `DONE`），**排除非功能旁路卡（`NON_FEATURE`）与已删除卡**；含已被其他需求关联的卡片（规则上本就允许一卡多需求）
- **默认过滤**：按排期日期所属月份（默认当月）；Backup 池卡（无排期日期）不参与月份过滤、不入候选
- **展示字段**：卡片编号 / 标题 / 排期日期 / 开发状态 / 开发人 / 已关联需求数（已关联需求数大于 0 时展示「已关联 N 条需求」角标，附已关联需求的提交人名单）
- **筛选维度**（在月份之上叠加，均为人员选择器单选、可清空）：
  | 筛选 | 匹配逻辑 | 空值口径 |
  |------|---------|---------|
  | 开发人 | 等值匹配卡片开发人（选择器选人后按姓名匹配） | 🚨 `PENDING` 卡尚无开发人（领取开发时才记录），**不参与该筛选**；筛选器旁常驻说明「仅已被领取开发 / 已完成的卡片有开发人」 |
  | 需求提交人 | 反查命中：该卡片已被选中人提交的需求关联；在本模块内反查关联卡片编号集合后过滤候选，不触碰 功能排期 侧（单向关联红线不变） | 🚨 **仅内部提交单参与**（外部单无内部提交人、提交人姓名为自由文本，不参与筛选；其姓名仅在卡片「已关联名单」中正常展示） |
- **同挂确认**：选中「已关联 N 条需求」的卡片提交时，弹窗内二次确认「该卡片已承载 N 条需求（提交人：{名单}），确认将本需求同挂到该卡片？」；确认后按常规关联处理
- **排序**：排期日期升序（近期在前），同日期按卡片编号升序；已关联标识仅作展示、不影响排序

### 5.2 下游承接：Qoder 开发会话生成

- 需求关联排期卡片成功（状态置 `LINKED`）后，系统为该需求变更**生成 Qoder 开发会话**承接实施：服务端创建会话并挂载需求上下文（描述与附件、审批结论、关联卡片）+「项目映射配置」生效数据中该项目的 harness 工程与代码仓清单（映射真源见研发报告·项目进度报告）
- 会话入口挂在需求详情页（排期关联区内），仅产品经理、管理员与卡片开发人可见；解除关联不回收已生成会话，重新关联时生成新会话并保留旧会话链接备查
- 缺陷修复（`BUGFIX`）需求不生成开发会话，其修复实施由黑灯工厂承接（§2.7）

## 6. 通知与企微推送

推送统一在业务事务提交后异步触发，禁止在事务内同步调用，能力复用 企微应用消息发送。

### 6.1 双通道推送

- **个人消息**：推送给下一级审批人（待办提醒）或提交人（结果通知），带需求详情页跳转链接；**外部单的「提交人结果通知」改推邀约人**（外部人无企微身份且不回传）
- **业务群消息**：按需求所属产品线 / 业务线路由到对应企微群（运营群 / 财务群 / 供应链群 / 数字化群 / 有点推荐需求群），用于归属内信息同步

### 6.2 群消息推送规则

| 触发事件 | 推送目标群 | 消息内容 |
|---------|-----------|----------|
| 需求提交 | 所属业务线群 | 「{提交人} 提交了新需求：{标题}，优先级 {P0-P3}」；外部单为「{外部提交人}（外部，邀约人：{邀约人}）提交了新需求：{标题}」 |
| L1审批通过 | 所属业务线群 | 「{需求标题} 已通过业务线审批，流转至实施负责人」 |
| L3审批通过 | 所属业务线群 | 「{需求标题} 已通过全部审批，进入研发排期」；缺陷修复单为「{需求标题} 已通过全部审批，转黑灯工厂自动化修复」 |
| 驳回 | 所属业务线群 | 「{需求标题} 被 {审批人} 驳回，原因：{意见摘要}」 |
| 关联排期 | 所属业务线群 | 「{需求标题} 已关联排期卡片 {卡片编号}，预计 {日期} 开发」 |

- 群消息以企微群机器人方式推送（复用报表群推送体系），产品线 / 业务线与群机器人的映射维护在审批链配置中；新增业务线须同步补齐，否则群消息静默失败（仅记录告警日志，不阻断主流程）
- 驳回意见摘要截取前 50 字，超出以 `…` 省略
- L2 审批通过不推群消息（内部流转节点），仅推个人消息给 L3 产品经理

### 6.3 推送去重与失败处理

- 同一需求同类消息在同一分钟内重复触发只推送一次，防止审批人连点导致重复推送
- 推送失败不回滚业务事务，失败记录写入事件审计供人工重推

## 7. 接口概要

| 操作 | 说明 |
|------|------|
| 提交需求 | 创建或提交需求，生成编号与审批链快照；**内部提交必须携带提交对象**，按 §3.4 匹配生成快照；`DRAFT` 保存不生成快照 |
| 需求列表 | 分页查询，支持业务线 / 状态 / 优先级 / 类型 / 提交人 / 时间区间筛选与 Tab 视角切换 |
| 需求详情 | 返回需求主体 + 审批链快照 + 审批流水 + 关联排期卡片实时状态 |
| 审批通过 | 按当前级次校验审批人，递进至链上下一已配置级次；外部单 L3 通过时将实际通过人记为该需求的产品经理 |
| 驳回 | 校验审批人后置 `REJECTED`，必填驳回意见（≥ 10 字） |
| 撤回 | 仅 `SUBMITTED` / `BU_REVIEWING` 可撤回，回到 `DRAFT` 并作废快照 |
| 关联排期 | 记录关联卡片并置 `LINKED`；支持解除关联回退至 `PM_SUBMITTED` |

**通用约束：**

- 所有接口后端二次校验菜单权限与角色可见范围，不依赖前端按钮控制
- 任何导致状态 / 级次 / 关联关系变更的接口，成功后须写入审批流水与事件审计各一条
- 审批类接口对同一需求同一级次做幂等控制：重复提交视为已处理，返回当前状态而非报错
- 外部提交与内部提交共用同一套审批 / 详情 / 统计接口，仅**提交入口**分离（公开接口独立于内部接口）

### 7.1 外链相关接口

**内部接口**（需登录）：

| 操作 | 说明 |
|------|------|
| 生成外链 | 填写邀约对象备注、有效期天数、提交次数上限、需求类型默认值；**仅返回完整链接，不返回二维码图片**（二维码由前端依链接本地生成，沿用采购邀约范式）|
| 外链台账 | 分页查询，支持状态 / 邀约对象 / 生成人 / 时间区间筛选；非管理员仅可见本人生成的链接（后端强制收口，不依赖前端传参）|
| 撤销外链 | 仅 `GENERATED` 可撤销，必填撤销原因；已提交产生的需求不受影响 |

**公开接口**（免登录）：

| 操作 | 说明 |
|------|------|
| 校验 token | 仅凭 token 校验；返回是否可用 + 邀约对象备注（预填用）+ 需求类型可选项；不可用时返回失效原因 |
| 图形验证码 | 按 token 下发验证码图片，5 分钟有效，一次性消费 |
| 提交需求 | 提交 token、验证码、标题、描述、需求类型、姓名、部门、手机号；成功返回需求编号 |

**公开接口专属约束：**

- 公开接口须在网关白名单中显式声明免登录，**不得与内部接口共用处理入口**
- 返回内容不得包含任何内部人员姓名、审批人信息、业务线枚举、需求列表数据（邀约对象备注除外，因其为邀约人主动填写）
- 所有公开接口调用均写入事件审计，记录来源 IP 与客户端标识

## 8. 外链邀约与外部提交

仅 `YDTJ`（有点推荐）开放。能力范式对齐 采购邀约 的 token 反查模式。

### 8.1 外链形态：一次性定向 token

- 链接由内部人**逐个生成、定向发放**，不提供长期通用链接，不得公开张贴或群发
- **链接中唯一参数为 token**，产品线 / 业务线 / 邀约对象 / 有效期全部由 token 反查
- 生成后同时提供二维码（内容即完整链接），供微信 / 企微发送
- 生成时内部人必填**邀约对象备注**（公司/联系人），仅供内部溯源与台账识别；外部人进页后**仍需手填自己的姓名与部门**（可用备注值预填，允许修改）

### 8.2 「一次性」的精确语义

| 维度 | 口径 |
|------|------|
| 访问次数 | **不限制**，可重复打开（避免误关页即失效），仅计数 |
| 提交次数 | 默认上限 **1 次**，生成时可配；达上限后链接置 `USED` |
| 达上限后访问 | 展现「已提交」提示页（带需求编号），不再展示表单 |
| 有效期 | 默认 30 天，可配 7/15/30/60/90 天；过期后无论是否提交过均置 `EXPIRED` |
| 撤销 | 邀约人与管理员可随时撤销未使用链接，已提交产生的需求不受影响 |

- 因提交后**不可重填也不可修改**，提交前必须弹出**预览确认弹窗**（完整回显标题 / 描述 / 类型 / 姓名 / 部门 / 手机号），文案见 [`public-ui.md`](public-ui.md)

### 8.3 外部提交字段边界

| 字段 | 外部人是否可填 | 说明 |
|------|---------------|------|
| 需求标题 | ✅ 必填 | ≤ 128 字 |
| 需求描述 | ✅ 必填 | ≥ 20 字，≤ 2000 字（高于内部门槛，降低无效单）|
| 需求类型 | ✅ 必选 | 默认值由链接携带，可改 |
| 提交人姓名 | ✅ 必填 | ≤ 64 字 |
| 提交人部门 | ✅ 必填 | **自由文本，不关联系统部门** |
| 手机号 | ✅ 必填 | 仅格式校验，**不发短信不做真实性验证**，仅供内部回访 |
| 业务线 | ❌ 不展示 | 系统固定为不区分 |
| 优先级 | ❌ 不展示 | 统一入库为链接默认值（默认 `P2`），由审批人修正 |
| 附件 | ⚠️ 仅图片 | **仅开放图片上传**（≤ 5MB/张，最多 3 张，单次提交总大小 ≤ 15MB）；文档与视频不开放（免登录上传存在存储滥用与恶意文件风险），详见 §9.5 |

- 外部提交人不建系统账号与系统部门，姓名、部门、手机号以自由文本随需求记录，严禁为外部人建临时账号或临时部门

### 8.4 安全与防刷

因**不回传结果**，手机号无需真实性校验，防刷为下列四道（**不使用短信验证码**）：

| 防线 | 规则 |
|------|------|
| token 有效性 | 非法 / 过期 / 已撤销 / 达提交上限均拒绝，不区分返回时延（防枚举）|
| 图形验证码 | 提交前必填，5 分钟有效、一次性消费；连续错 3 次强制刷新 |
| 提交次数上限 | 单 token 默认 1 次，计数递增与需求写入在同一事务内并加锁 |
| IP 频率限制 | 单 IP 对公开接口 **10 次/分钟**，超限返回统一限流文案并记限流审计事件 |

- 全部公开接口访问记录来源 IP、客户端标识与对应外链，写入事件审计供异常回溯
- 外部提交内容进入内部列表前不做自动审查，但详情页必须显式标识「外部提交」以提醒审批人警惕

### 8.5 单向收口口径

外部提交**完全单向**：除提交成功页展示需求编号外，系统不向外部人回传提交之后的任何信息。

- 不提供进度查询页、不发短信 / 邮件通知、不提供回执码自查
- 需求编号仅作为提交凭证展示，供外部人线下向邀约人查询使用
- 外部单的任何状态变更（通过 / 驳回 / 关联排期）均**只通知邀约人**，由邀约人自行决定是否线下告知外部人
- 外链因未命中审批链配置而提交失败时，向邀约人推送企微告警「您发放的需求外链提交失败：有点推荐审批链未配置」

### 8.6 统计口径

- 需求总量 / 驳回率 / 平均审批时长等现有指标均**默认含外部单**，可按提交来源与产品线下钻
- 外链专属指标：链接生成数 / 访问转化率（已产生提交的链接数 ÷ 生成数）/ 外部单驳回率，用于评估外部需求质量
- 外部单驳回率持续偏高时，应回收对应邀约人的外链生成权限（运营措施，非系统自动）

## 9. 附件管理规则

附件为需求描述的补充证据（截图 / 原型 / 说明文档 / 录屏），文件实体落 OSS，库内只存元信息。

### 9.1 上传限制

| 类型 | 允许扩展名 | 单个大小上限 | 数量上限 | 开放端 |
|------|-----------|-------------|---------|--------|
| 图片 | `jpg` / `jpeg` / `png` / `webp` / `gif` | ≤ 10MB（H5 ≤ 5MB）| 内部端 ≤ 20 张；H5 ≤ 3 张 | Web / App / H5 |
| 文档 | `pdf` / `docx` / `xlsx` / `pptx` / `txt` | ≤ 50MB | ≤ 10 个 | **仅内部端**（Web）|
| 视频 | `mp4` / `mov` | ≤ 200MB | ≤ 3 个 | **仅内部端**（Web）|

- 数量上限**按类型分别计算**，不合并计数（即单条需求最多 20 图 + 10 文档 + 3 视频）
- 校验以**后端为准**：按上传来源端分支强校验扩展名白名单、大小上限与按类型分别计数的数量上限；附件类型由扩展名反推，不信任前端传值；前端限制仅作体验优化，不作为安全边界
- 安全边界为扩展名白名单 + 登录态 / token 约束（内部端附件由前端直传，后端不校验文件内容的 MIME 类型）；`exe` / `sh` / `bat` / `js` 等可执行扩展名不在白名单内，一律拒收
- App 端仅开放图片（相册 / 拍照），**不开放文档与视频**（移动网络下大文件上传成功率低，且缺少文件管理器语义）

### 9.2 存储规则

- 内部端（Web / App）附件由前端取临时凭证**直传 OSS**，后端只接收元信息并按 §9.1 强校验；公开 H5 例外，走后端转存（§9.5）
- 上传不依赖需求已落库：新建表单即可上传，附件元信息随表单提交一并入库；未提交就离开产生的孤儿对象交 Bucket 生命周期规则回收
- OSS 按月分目录存放（具体路径规则以代码仓为准），便于批量回溯与生命周期管理
- 文件名 **UUID 化防重**：原始文件名仅作展示与下载回写，不进存储路径（避开中文 / 特殊字符 / 同名覆盖三类问题）
- 下载 / 预览一律走 **OSS 签名 URL**，由前端自签，有效期以前端实现为准（Web 端为 1 小时）；不暴露 Bucket 直链，不开放公共读；不提供后端中转下载
- 鉴权前置在附件列表查询：无权查看该需求就拿不到附件存储标识，也就无法签出访问链接
- Bucket 名随附件记录，不取运行时配置，保证 Bucket 迁移后历史附件仍可访问

### 9.3 内容安全审核

不做附件内容安全审核（图片 / 视频 / 文档均不过内容安全）：未删除的附件对有权查看该需求的人一律可见，三端不展示任何审核状态；内容风险依靠类型白名单 + 登录态 / token 约束兜底。

### 9.4 审批中追加附件

- 已提交（`SUBMITTED` / `BU_REVIEWING` / `IMPL_REVIEWING` / `PM_REVIEWING`）的需求，**允许提交人追加附件**，用于响应审批人的补材要求，避免为了传一张图而驳回重提；`SUBMITTED` 是提交后到 L1 审批人接手的瞬时过渡态，同样按「追加」放行，避免提交人卡在纯技术状态上
- 追加的附件标记为「审批中追加」，详情页以「审批中追加」角标与提交时附件区分
- 追加成功后**自动通知当前级次全部审批人**（企微个人消息），文案「{提交人} 为需求 {编号} 补充了 {N} 个附件」
- 追加**不重置审批级次、不重建快照、不重算节点停留时长**（不得以追加附件刷新 SLA 计时规避催办，见 §10.1）
- 只能追加不能删除（见 §9.6）；外部单**不支持追加**（无登录主体，且链接已 `USED`）

### 9.5 H5 附件特殊规则

外部免登录提交（公开 H5）的附件能力为**受限开放**，与内部端不同口径。

公开 H5 是**唯一不走前端直传的端**：免登录拿不到临时凭证，且把 OSS 写凭证暴露给公网正是本节要防的存储滥用，故由后端转存——外部人凭 token 上传图片，后端转存 OSS 后**只返回元信息、不落库**，元信息随需求提交在**同一事务**内写入；转存与提交**共用同一 token 校验链与 IP 限流计数**。

| 维度 | H5 口径 |
|------|---------|
| 类型 | **仅图片**（`jpg`/`jpeg`/`png`/`webp`）；文档与视频不开放 |
| 大小 | 单张 ≤ 5MB，**单次提交总大小 ≤ 15MB** |
| 数量 | 最多 3 张 |
| 提交时机 | 图片元信息随表单**一并提交**，需配合图形验证码校验通过；转存须带 token，不存在免验证的独立落库通道 |
| 上传人 | 无系统用户，上传来源记为 H5，上传人姓名取外部提交人手填姓名 |
| 内容安全 | 不做内容审核（§9.3）；风险控制为 token 校验 + 图形验证码 + IP 限流 + 扩展名白名单 |
| 失败降级 | 图片上传失败**不阻塞需求提交**：需求主体先落库，失败图片写入失败审计事件，页面提示「需求已提交，部分图片上传失败」|
| IP 限流 | 与公开提交接口共用同一限流计数（§8.4），不单独放宽 |

- 🚨 开放图片不改变 §8.5 **单向收口口径**：外部人不可查看已上传附件、不可删除、不可补传（提交即终止）

### 9.6 附件删除

附件删除**一律只做逻辑删除，不从 OSS 物理移除**（异步清理失败会以「OSS 报错」形态掩盖业务首因），孤儿对象交 Bucket 生命周期规则回收。

| 需求状态 | 删除行为 |
|---------|---------|
| `DRAFT` 草稿 | 提交人可删，仅逻辑删除 |
| 已提交（审批中 / 终态）| **不提供删除入口**；如内容不当需管理员介入，仅逻辑删除 |
| `REJECTED` 后重提 | 历史附件全部保留且不可删；修改阶段只能新增（保证审批人能看到驳回时的原始材料）|

- 删除一律写事件审计，记录操作人与文件名
- 需求本体软删（草稿删除）时级联逻辑删除其全部附件
- 附件元信息随表单提交做全量同步：不在本次提交清单中的已有附件，**仅 `DRAFT` 态允许逻辑删除**，`REJECTED` 重提**只能新增不能删**（与本表第 3 行一致）

## 10. 审批时效与 SLA 管理

解决「需求提上去就没人理」的治理缺口：以可配置阈值驱动自动催办与升级，并把时效沉淀为可计量指标。

### 10.1 催办触发

- 审批节点停留时长超过催办阈值（默认 48h）仍未操作，系统自动向**当前级次全部审批人**发送企微催办消息（或签模式下同级多人均收到，任一人处理即停止催办）
- **停留时长起算点**：当前审批轮次进入本级的时间（即上一级通过时间；L1 取提交时间），与审批流水记录的节点耗时同源口径
- **自然时间计算**，不扣除周末与法定节假日（阈值本身已含缓冲，引入工作日日历会大幅抬高实现与解释成本）
- 只对**审批中**状态生效：`BU_REVIEWING` / `IMPL_REVIEWING` / `PM_REVIEWING`；`DRAFT` / `SUBMITTED`（瞬时态）/ `PM_SUBMITTED` / `LINKED` / `REJECTED` 均不纳入
- 追加附件、刷新页面、审批人查看详情等行为**均不重置计时**；仅当前级次发生通过 / 驳回 / 撤回才重算

### 10.2 升级触发

- 节点停留超过升级阈值（默认 72h）仍未操作，系统通知**该审批人的直接上级 + 需求提交人**
- 上级取数：审批人所属部门的部门负责人；取不到上级时**降级通知实施负责人**（L2 审批人）兼作治理兼管人，不得静默丢弃
- 外部单的「提交人通知」**改推邀约人**（对齐 §6.1 / §8.5 单向收口，不推外部人）
- 升级**不改变审批权限**：上级仅收到知晓消息，**不获得代审权**（代审会穿透审批链快照，与 §4.2 权限校验冲突）；如确需换人走管理员「审批链重建」（§3.6）
- 升级后**仍继续按催办窗口周期性催办**，直至节点被处理（不因已升级而停止催办）

### 10.3 差异化配置

默认阈值矩阵（初始化写入，管理员可在「SLA 配置」页调整）。🚨 **优先级沿用本模块 `P0/P1/P2/P3` 枚举**，不引入第二套命名：

| 优先级 | 语义 | 催办阈值（小时） | 升级阈值（小时） |
|--------|------|----------------|------------------|
| `P0` | 紧急 | 24 | 48 |
| `P1` | 高 | 48 | 72 |
| `P2` | 中（普通）| 48 | 72 |
| `P3` | 低 | 72 | 120 |

- 三个级次（L1/L2/L3）默认**共用同一套阈值**，但配置支持按级次单独调整（如 L2 实施归集需更长思考时间可单独放宽）
- `P1` 与 `P2` 默认同口径（普通档），避免档位过细导致审批人无法预期
- 约束：升级阈值必须 **大于催办阈值**，且二者均为 1–720 的整数；保存时前后端双校
- 产品线维度必须等值命中，优先级支持通配降级（匹配顺序以代码仓为准）
- **SLA 配置不做快照**（与审批链快照相反）：改后立即对在途需求生效

### 10.4 目标日期预警

- 目标完成日期距今 **≤ 7 天**且需求仍处于审批中（**未达 `LINKED`**）时，推送预警给 **L2 实施负责人**（全公司统一归集入口，最有条件协调资源）
- 预警文案：「需求 {编号}「{标题}」目标完成日 {目标完成日期} 仅剩 {N} 天，当前仍在 {当前节点}，尚未关联排期」
- 同一需求在整个预警窗口内（距目标日 7 天内）**每天最多推 1 次**，按自然日去重
- 目标完成日期已过且仍未 `LINKED` 时**持续日推**，文案改为「已超目标完成日 {N} 天」，直至达 `LINKED` 或 `REJECTED`
- 预警与催办**互不抵消**：两者触发条件与接收人不同，可同时发出
- 目标日期预警**同样纳入静默时段延后**（见 §10.7）：00:00–08:00 命中时延到 08:00 那轮仍属同一自然日，当天照发不丢；静默期内只记延后事件，不占去重窗口

### 10.5 滞留需求看板

- Web 管理端需求列表提供「滞留需求」视角：筛选条件为「**当前级次停留 ≥ 命中的催办阈值且未处理**」
- 默认排序：**停留时长倒序**（滞留最久的在最前）
- 可见范围沿用 §4.1 角色口径：业务线负责人只看本业务线滞留单，实施负责人与管理员看全部；**不为本视角放宽任何可见范围**
- 看板行展示：停留时长（天/小时）/ 当前级次与审批人 / 已催办次数 / 是否已升级，支持导出
- 看板提供「手动催办」按钮（管理员 / 实施负责人）：立即发一次催办，**共用 §10.7 去重窗口**（窗口内已催过则提示已催办时间，不重发）
- 🚨 **手动催办不受静默时段限制**（人在页面上主动点击，抑制发送违背操作意图），只受去重窗口约束

### 10.6 SLA 仪表盘指标

| 指标 | 取数口径 |
|------|---------|
| 各业务线平均审批耗时 | 按审批流水记录的节点耗时聚合均值，**按 L1/L2/L3 拆分**；可按产品线 / 业务线下钻 |
| 端到端平均周期 | **首次提交时间** → 达 `LINKED` 的时间差均值；未达 `LINKED` 的需求**不入分母**（避免在途单拉低均值）|
| 超时率 | **区间内节点实际耗时超过命中催办阈值的节点数** ÷ 区间内受理需求数；以百分数展示 |
| 趋势图 | 上述三项按**周 / 月**聚合；X 轴**按日期正序排列**（最早在左），不用 Top N 排序也不设「其他」汇总柱 |
| 当前滞留条数（实时） | 当前处于审批中且停留 ≥ 命中催办阈值的条数，**实时值，不受时间区间筛选影响**（区间筛选描述的是历史样本，滞留是「此刻」的治理压力）|

- **首次提交时间取自审批流水中的首次提交记录**，而非需求上记录的提交时间——后者在驳回重提时被覆盖，直接用会让端到端周期系统性偏短，恰好掩盖返工成本；流水取不到时退回需求提交时间
- 🚨 **超时率按节点实际耗时实算，不依赖是否发生过催办事件**——否则催办机制生效前的历史数据、静默延后的、推送失败的节点都会被误判为「未超时」
- 统计口径**默认含外部单**（对齐 §8.6），可按提交来源与产品线下钻
- 驳回重提的需求：审批耗时**按轮次分开统计**，端到端周期**取首次提交起算**（不因重提而重置，否则会掩盖来回返工成本）
- 与审批链配置页「区块三 · 审批统计」的分工：后者看**单一归属**的受理量/通过率/驳回率，SLA 仪表盘看**跨归属的时效横向对比与趋势**，指标不重复定义

### 10.7 催办去重

- 同一需求同一级次同一审批轮次在一个催办窗口内（默认 **24h**，可配置）**仅发送一次**催办，避免逐小时骚扰审批人
- 去重维度：事件类型 + 需求 + 审批轮次 + 级次 + 催办窗口序号（停留小时数按窗口时长取整），具体去重标识规则以代码仓为准
- 🚨 **审批轮次必须参与去重**：驳回重提后停留时长归零、级次回到 L1，若不区分轮次，新一轮前几个窗口的去重标识会与上一轮已记录的完全相同，导致新一轮催办被永久去重跳过
- 升级消息（`SLA_ESCALATED`）**独立去重**，不与催办共用窗口计数；同一节点升级同样按 24h 窗口去重
- 级次变更（通过进入下一级）后去重计数**自然重算**；驳回重提靠审批轮次隔离
- 🚨 **静默时段（22:00–08:00）不发送也不占用去重窗口**：命中催办 / 升级条件时只记延后事件（`SLA_DEFERRED`），不记催办（`SLA_REMINDED`）/ 升级（`SLA_ESCALATED`）事件，延后事件不参与去重；静默结束后 08:00 那轮按正常流程重新判定并发送。若静默期占用了去重窗口，08:00 那轮必被去重跳过，催办将永远发不出去
- **手动催办不受静默时段限制**（见 §10.5），只受本节去重窗口约束
- 企微推送失败不重试不回滚，写推送失败审计；**失败也占用去重窗口**（否则企微持续异常时会在恢复后集中重发）
  - ⚠️ 此条**仅适用于真实尝试推送的场景**；静默时段属于「根本没尝试推送」，只记延后事件，**不占用去重窗口**

### 10.8 SLA 定时扫描

- **每小时整点**执行一次扫描，检查全部审批中需求（`BU_REVIEWING` / `IMPL_REVIEWING` / `PM_REVIEWING`）当前节点的停留时长，对比 SLA 配置触发催办 / 升级
- 同一次扫描一并处理 §10.4 目标日期预警，不另起扫描
- 单机执行、并发度 1；幂等依赖 §10.7 去重，**重复执行不会重发**；触发策略与执行细节以代码仓为准
- 🚨 **定时扫描不做业务判定外的任何写入**：不改需求状态、不改审批级次、不自动通过也不自动驳回（时效治理只推人，不代人做决策）；小时级扫描意味着**催办最大延迟 1 小时**，属可接受误差

## 11. AI 方案确认（PM 节点 AI 辅助）

解决「方案确认集中在产品经理个人、吞吐受限」的瓶颈：需求进入**产品确认节点（L3）**后，系统为已开启开关的产品经理自动执行方案分析，产出方案草稿、三段式确认摘要与信息缺口清单；产品经理人工确认后系统代为执行通过动作。AI 只做预填与建议，**审批决策权始终在 PM 本人**——与 §10.8「定时扫描不代人做决策」同一治理哲学。

### 11.1 定位与红线

- AI 产出 = 方案草稿 + 确认摘要 + 信息缺口清单，是审批人的**决策辅助材料**，不构成审批动作本身
- 🚨 **红线一（触达隔离）**：任何 AI 生成内容（方案草稿、补材请求文案、驳回理由草稿）在 PM 人工确认发出前**不得触达提交人**——不发通知、不在提交人可见区域渲染；后端鉴权拦截，仅当前级次审批人与管理员可访问 AI 方案。AI 幻觉直接触达业务方的事故成本远高于多一次人工点击
- 🚨 **红线二（不自动审批）**：系统不自动通过 / 不自动驳回。通过动作必须由 PM 点击「确认并通过」触发，系统仅代为执行：审批流水记为通过、操作人为 PM 本人、审批意见带「【AI方案确认】」前缀（与既有「【AI自动审批】」意见形态对齐）并关联所确认的 AI 方案，审计上可区分「AI 辅助确认」与「纯人工审批」
- 🚨 **红线三（不阻塞人工通道）**：AI 生成中 / 失败 / 任何异常状态下，PM 与其他或签审批人均可照常人工通过 / 驳回，AI 结果自动作废保留只读参考（§11.4）

### 11.2 触发条件

- **触发点**：需求状态进入 `PM_REVIEWING`（L3 产品确认）**且**当前级次审批人快照集合中存在**开启 AI 辅助开关**的产品经理。链上未配置 L3 级次的（专属链为 L1+L2 等子集）无方案确认语义，不触发
- 「提交对象是某 PM」**不等于**触发——前置级次（L1/L2）流转期间不触发；或签集合中仅未开启开关的审批人也不触发
- 开关为 **per-PM 配置**（§11.8），按产品经理维度生效，**禁止把具体人员写死在代码或配置中**
- 每个需求的每个审批轮次自动触发**至多一次**；驳回重提进入新一轮后可再次自动触发；同轮内 PM 可手动「重新生成」（§11.6），版本递增
- 外部提交单同样适用：以默认链 L3 审批人集合中开启开关者为准（§3.4）
- 流程中心通道推进至产品确认节点时同样按本节判定触发（§12.4③）
- 触发后生成一条状态为 `GENERATING`、触发方式为自动的 AI 方案记录

### 11.3 固定分析框架（七步）

「尽可能全面」落成固定清单，每次执行逐项过，保证输出质量不漂移：

| 步骤 | 分析项 | 产出要求 |
|------|--------|---------|
| 1 | 业务诉求还原 | 一句话诉求 + 业务背景 / 痛点 / 期望效果，与提交人原文分离（AI 复述，便于 PM 校对理解偏差） |
| 2 | 存量能力排重 | 对照全模块索引排查是否已有同类 / 可复用模块，命中时给出模块名与差异点，防止重复建设 |
| 3 | 数据源与接口可行性 | 通过 AI 助手的业务查询 Tool **实查验证**关键数据是否可得；查不到的如实标注「未验证」，禁止编造接口结论 |
| 4 | 端型与权限影响 | 涉及端（Web / App / H5）、新增权限点、数据可见范围变化 |
| 5 | 状态机与通知影响 | 对现有单据状态机 / 审批链 / 企微通知的侵入面 |
| 6 | 模块归属与工作量粗估 | 建议归属模块（含新建 vs 并入既有模块判断）与量级粗估（仅分档，不排期） |
| 7 | 信息缺口清单 | 「若业务补充 X，本方案可在 Y 方面更完善」的逐条清单——这是补材请求（§11.6）的预填来源 |

- 执行身份：以开启开关的 PM 本人身份执行数据查询，Tool 权限沿用其角色权限；查不到的数据在方案中标注「未验证」，**不越权、不借用系统账号**
- 执行过程（模型标识 + Tool 调用轨迹）全量留存，供审计回放

### 11.4 执行期间的并发与作废

- 生成期间详情页对**当前级次审批人**展示「AI 方案生成中」标记（提交人不可见，对齐红线一）
- **或签先批作废**：任一级次审批人在 AI 完成前人工通过 / 驳回，进行中的任务置 `OBSOLETED`；已完成的方案保留只读参考，不可再用于「确认并通过」（需求已流转，确认入口随状态关闭）
- **PM 人工直批作废**：PM 不看 AI 结果直接人工通过 / 驳回，同样置 `OBSOLETED`，方案仅留痕
- 需求被撤回 / 删除 / 审批链重建时，在途任务一并 `OBSOLETED`
- **SLA 计时不豁免**：AI 执行为分钟级，远小于催办阈值（默认 24h 起），停留时长照常累计，不设特例（§10.1）

### 11.5 确认摘要与确认并通过

- AI 完成后向该 PM 发企微个人消息（含详情页跳转链接）；**企微消息是单向通知，不提供交互按钮回调，确认动作必须回到 Web / App 详情页完成**
- 详情页「AI 方案」面板展示**三段式确认摘要**（自然语言）：① 业务诉求是什么 ② 本次方案完成了什么 ③ 信息缺口与建议业务补充的内容；方案全文可展开
- PM 点击「确认并通过」：审批意见由 AI 预填（可编辑），提交后系统以 PM 身份执行 L3 通过，意见自动带「【AI方案确认】」前缀；需求按 §2.3 流转，方案状态置 `CONFIRMED`
- 前置校验与人工通过完全一致（§4.2 当前级次审批人校验、§7 幂等）：方案状态非 `READY`、需求已流转、或签已被他人处理时，确认操作返回当前状态而非报错

### 11.6 请求补充材料（第三动作）

审批流程本身只有「通过 / 驳回」两个动作，追加附件是提交人自发行为（§9.4）。AI 检出信息缺口时由「请求补充材料」承接：

- AI 判定信息不足时在信息缺口清单中产出补材清单，PM 可编辑后点「**请求补充材料**」
- **PM 确认发出后**才触达提交人（红线一）：企微个人消息通知提交人（文案为 PM 确认后的终稿）+ 详情页对提交人展示补材清单；补材请求是 AI 内容触达提交人的唯一出口
- 请求补材**不新增需求状态、不改变级次、不重置 SLA 停留计时**（状态保持 `PM_REVIEWING`；不得以补材刷新计时规避催办，口径同 §9.4 追加附件）
- 提交人通过「审批中追加附件」（§9.4）与补充说明响应；PM 可在面板「**重新生成方案**」（触发方式为手动，方案版本递增），形成「补材 → 再分析 → 确认」闭环
- 同轮内重新生成与补材请求不设硬次数上限，全量版本留痕；连续多轮补材仍不足时由 PM 人工驳回（驳回理由可由 AI 预填，同样经 PM 确认才发出）

### 11.7 幂等与失败处理

- 同一需求同一审批轮次内自动触发的方案仅一条；手动重新生成按方案版本递增；唯一性由业务层加锁保证（实现以代码仓为准）
- AI 执行失败（模型超时 / Tool 异常 / 配额耗尽）置 `FAILED` 并写事件审计，企微通知 PM「AI 方案生成失败，请人工审批或重试」——**失败只通知 PM，不通知提交人**
- 失败**不自动重试**（避免模型故障期打爆配额），由 PM 在面板手动「重新生成」
- 确认操作幂等：PM 连点 / 重复提交返回当前状态，不重复执行通过动作（对齐 §7 审批接口幂等）

### 11.8 配置：per-PM 开关

- 开关挂在 PM 专属链配置上：管理员在「审批链配置」页**先选提交对象（PM）再勾选「AI 辅助方案确认」**，对该 PM 全部专属链批量生效
- 生效口径：该 PM 存在任一启用中的专属链且开关开启即视为开启；默认链不设该开关（外部单以 L3 配置审批人自己的专属链开关为准，不继承默认链）
- 开关变更**立即生效**（同 SLA 配置，不做快照）：仅影响变更后进入 `PM_REVIEWING` 的需求，在途生成中任务不受影响

### 11.9 审计与统计

- 审计事件类型：`AI_PLAN_GENERATING` / `AI_PLAN_READY` / `AI_PLAN_FAILED` / `AI_PLAN_CONFIRMED` / `AI_PLAN_OBSOLETED` / `MATERIAL_REQUESTED`
- 审批流水与意见前缀「【AI方案确认】」为「AI 辅助确认」的识别口径，统计时可与纯人工审批区分
- AI 辅助相关仅做事件留痕，SLA 仪表盘（§10.6）不统计 AI 辅助率、确认采纳率、补材请求率等指标

- 业务类型为需求，业务单号为需求编号（驳回重提沿用原编号，与平台「同业务单号防重 / 续审」口径兼容）；每次提交带幂等标识
- 表单数据必须包含链匹配与流转所需的需求编号、提交对象、产品线、业务线、需求类型、优先级、提交来源；同时携带标题、需求类型名称、优先级名称、业务线名称、提交对象姓名、目标完成日期、描述摘要，供审批详情只读展示
- 字段中文名映射须覆盖全部展示字段：需求编号、提交对象ID、产品线、业务线、需求类型、优先级、提交来源、需求标题、需求类型名称、优先级名称、业务线名称、提交对象、目标完成日期、需求描述、需求ID；外部单另补外部提交人、外部提交人部门、邀约人。新增 / 更名表单字段时本清单必须同步（并入 §12.6 镜像纪律）
- 建实例与续审一律在本模块业务事务提交后触发；建实例成功后由本模块补发群消息（§6.2），失败则回退自研通道并补发全量通知
- 驳回重提（§2.4，可更换提交对象）：业务侧修改后对原实例发起续审并携带最新表单数据（提交对象可能已变，平台按新值重新匹配链）；禁止重新建实例

② **外部单邀约人代提**：外部单（仅有点推荐外链）提交落库后，以**邀约人**身份建实例：

- 发起人为外链邀约人，须为在职系统用户；邀约人已离职 / 失效时回退自研通道并告警管理员
- 表单数据同 ① 必带项，但**不带提交对象**（外部单无提交对象）→ 落默认·YDTJ 链；另带提交来源为外部、外部提交人姓名与部门、邀约人姓名供审批详情展示；字段中文名映射同 ① 清单（含外部单三项）
- 语义兼容：外部单驳回即真终态、不可撤回、不可重提（§2.6）——平台驳回策略「退回发起人重提」仅表示允许发起人重提，本模块外部单无重提入口，驳回回写置 `REJECTED` 终态即闭环；平台发起人通知发邀约人，与 §8.5 单向收口天然兼容

③ **双向审批同步**：

| 方向 | 规则 |
|------|------|
| 需求管理页 → 流程中心 | 页内「通过/驳回」命中流程单时，后端以当前操作人身份代为调用流程中心审批，成功后才写本模块审批流水；页内交互不变；权限判定收口平台（§4.2），驳回意见 ≥ 10 字校验保留；流程中心明确拒绝时向操作人透传平台错误文案；页内操作按钮显隐仍按本地快照判定（转审 / 加签受让人由流程中心待办承接） |
| 需求管理页 → 流程中心（撤回） | 页内撤回命中流程单时先代为调用流程中心撤回，失败则阻断本地撤回（防双通道分叉）；实例已回到草稿且为同一发起人时视为撤回成功 |
| 流程中心 → 需求管理 | 订阅本模块模板的流程中心实例事件：节点通过 → 按映射级次推进当前级次与快照节点状态，推进至产品确认节点时按 §11.2 判定 AI 方案触发；流程完成 → 需求置 `PM_SUBMITTED`（等待 PM 关联排期，§5）；驳回 → 置 `REJECTED` 并记录驳回原因；撤回 → 回到 `DRAFT`；本模块当前级次已越过事件级次时跳过（幂等） |
| 并发防撞 | 平台侧幂等，业务侧以平台返回为准；审批流水记录操作来源通道（页内 / 流程中心） |
| 状态机映射 | 平台 6 态 ↔ 本模块 10 态：APPROVING ↔ BU/IMPL/PM_REVIEWING（按节点顺序与链上已配置级次的**有序位置映射**回写，如 L1+L3 子集链第 2 个节点对应 L3）；COMPLETED → PM_SUBMITTED；REJECTED → REJECTED；CANCELLED → 不回写（本模块无对应终态，作废由本模块删除/驳回通道承担）；瞬时态（BU_APPROVED/IMPL_CONFIRMED）不映射（由本模块在节点推进时自行产生） |
| 个人通知让位 | 流程单的个人待办 / 结果通知由流程中心消息模板承担，本模块不再重复发送（防双发）；发送时点重新判断需求是否关联流程实例，回退自研通道的需求个人通知照常发出 |

④ **页内审批进度渲染**：详情页审批进度条 / 时间线（§2.2 按快照级次渲染）读本模块快照，由实例事件回写同步快照节点状态，页内展示与自研通道一致。需求记录所关联的流程实例，未关联即为自研通道单。

⑤ **提交对象候选集过滤**：提交页按所选产品线与业务线（SNACK 必选业务线，YDTJ 不区分）过滤候选，候选为该归属下启用中专属链的 PM 去重（不并入默认链 L3 审批人）；任一归属候选为空时前端阻断提交并提示联系管理员配链（对应 §3.4 第 2 步）。

⑥ **自审处置**：流程单遇提交人即审批人的节点，由本人在流程中心待办或页内自行通过；本模块「提交人即审批人自动跳过」（§4.2）仅作用于自研通道单。

⑦ **总开关与回切**：流程中心接入总开关开启即新单全量走流程中心（外部单含 ② 代提）；回切时关闭总开关即恢复自研引擎接新单，流程中心在途实例继续走完（快照隔离），不回切。前置条件：流程中心系企微消息模板须处于启用状态。

⑧ **审批详情回跳**：流程中心审批详情「查看业务单据」以需求编号为锚点回跳本模块详情页；外部表单模式下审批人不可在流程中心编辑需求字段，修改由提交人在本模块完成（驳回重提语义不变）。

|---|--------------|----------------|------|

| 2 | 外部提交单（无系统账号主体）走默认链三级 | 建实例要求发起人（平台实例以发起人为锚） | 以邀约人身份代提（§12.4②），默认·YDTJ 链原样承接；邀约人失效回退自研并告警 |
| 3 | **AI 方案确认**（§11，L3 PM 节点 AI 面板 / 确认并通过 / 请求补材） | 流程中心审批页无 AI 面板承载位 | AI 流程在本模块详情页操作（PM 回页内「确认并通过」，页内代调平台审批）；**流程中心通道直接通过 = 跳过 AI 确认**，为双通道已知副作用，开启 AI 辅助的 PM 需知悉 |

### 12.6 配置镜像同步纪律

**本模块审批链配置的任何变更，必须同事务考虑流程中心镜像**：新增 / 修改 / 停用专属链或默认链后，同步维护流程模板的链与节点审批人 → 重新发布模板 → 链路预览回归（至少覆盖变更归属的专属链与默认链命中）→ 同步更新 §12.3 配置表。**表单数据契约同理**：新增 / 更名 / 下线表单字段时，必须同事务检查链条件、字段中文名映射清单（§12.4①）与平台快照展示效果。

两侧配置无强制同步机制，镜像滞后会导致需求错落链路、终审错人，本条纪律为唯一防线。

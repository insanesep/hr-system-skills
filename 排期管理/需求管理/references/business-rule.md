# 需求管理业务规则

本文件为需求管理模块的规则真源。SKILL.md 仅作导航，具体判定以本文件为准。

---

## 1. 业务流程总览

需求从提出到进入研发排期共 5 步，前 3 步在需求管理模块内闭环，第 4 步交接产品经理，第 5 步由 [feature-schedule](../../功能排期/SKILL.md) 承接。

> **审批链驱动模式（2026-09-09 起）**：内部提交**先选定提交对象（产品经理）**，系统按该对象的专属审批链（级次由配置决定，1~3 级）流转；未配置专属链时回退「产品线 × 业务线 × 需求类型 × 优先级」四维**默认链**兜底，且末级（产品确认 L3）审批人替换为提交对象本人。外部提交无提交对象，固定走默认链。规则真源见 §3。

| 步骤 | 名称 | 执行角色 | 产出 |
|------|------|---------|------|
| 1 | 需求提交 | 业务线员工（内部，**先选定提交对象·产品经理**）/ 外部人员（凭外链，无提交对象） | 生成需求单，编号 `REQ-{YYYYMMDD}-{NNN}`，进入审批链第一级待审 |
| 2 | 前置审批 | 链上前置级次审批人（业务线审批 L1 / 实施确认 L2；级次由命中链决定，未配置的级次直接跳过） | 判定需求合理性、实施可行性并归集同类需求，通过则流转链上下一级，驳回则回提交人 |
| 3 | 产品确认 | 提交对象（产品经理，L3；外部单为默认链 L3 配置的产品经理） | 终审需求价值与方案，通过则需求进入待关联排期 |
| 4 | 产品提交 | 提交对象（产品经理） | 完成需求打磨并关联排期卡片，需求进入 LINKED 终态 |
| 5 | 研发开发 | 研发 | 在 feature-schedule 中领取卡片开发，状态回传需求详情页 |

### 1.1 产品线与业务线枚举

**产品线（`product_line`）** 为需求的第一层归属维度，固定 2 值，新增需 DBA + 管理员同步维护审批链配置。

| 枚举值 | 名称 | 业务线取值 | 提交方式 |
|--------|------|-----------|---------|
| `SNACK` | 鸣鸣很忙 | 必选 `OPS`/`FIN`/`SCM`/`DIGITAL` 之一 | 仅内部登录用户（Web / App）|
| `YDTJ` | 有点推荐 | 固定 `*`（不区分业务线）| 内部登录用户 + 外部人员凭外链免登录 |

**业务线（`biz_line`）** 仅在 `SNACK` 产品线下生效，固定 4 条，不支持自定义扩展（新增需 DBA + 管理员同步维护审批链配置与企微群映射）。

| 枚举值 | 名称 | 说明 |
|--------|------|------|
| `OPS` | 运营 | 门店营运、店务执行、任务协同相关需求 |
| `FIN` | 财务 | 结算、凭证、对账、税务相关需求 |
| `SCM` | 供应链 | 采购、配送、仓储、库存相关需求 |
| `DIGITAL` | 数字化 | 数据报表、系统集成、硬件与基础能力相关需求 |
| `*` | 不区分 | 仅 `YDTJ` 使用，不向用户展示也不可选 |

### 1.2 角色定义

| 角色 | 职责说明 |
|------|---------|
| 业务线员工 | 需求提出方，负责描述业务背景、痛点与期望效果；可撤回与修改草稿 |
| 外部提交人 | 非系统用户（外部伙伴 / 兼职人员等），凭内部人发放的一次性定向外链提交有点推荐需求；无账号、无草稿、无撤回、不可查进度 |
| 邀约人 | 生成外链的内部用户，对所发放链接产生的需求负溯源责任；可撤销自己生成的链接 |
| 业务线负责人 | 各业务线一名（4 条业务线各自独立），L1 审批人，把关本业务线需求的必要性与优先级 |
| 实施负责人 | 全公司统一入口，L2 审批人（默认链与配置了该级的专属链），负责需求归集、去重与可行性判断 |
| 产品经理 | **提交对象**：内部需求提交时由提交人必选；链上末级（L3 产品确认）审批人，负责需求打磨、方案确认与排期卡片关联；外部单由默认链 L3 配置的产品经理承接 |
| 研发 | 不参与审批，在 feature-schedule 侧领取卡片并推进开发状态 |

### 1.3 流程约束

- 需求必须归属唯一产品线，且归属唯一业务线（`YDTJ` 下业务线固定 `*`），提交后两者均不可修改（如需变更需驳回重提）
- **内部提交必须选定提交对象（产品经理）**，`pm_user_id` 随提交写入并作为排期关联责任人；草稿与驳回重提时可更换提交对象（更换后按新对象重新匹配审批链并生成新快照）
- 同一提交人对同一业务线可并行提交多条需求，无数量限制
- 需求从提交到 LINKED 全链路留痕，任意状态变更写入审批流水与事件审计
- **外部提交单直接走默认审批链第一级待审**，不设待受理初筛池（链接为内部人定向发放，来源天然可信）；外部人无登录态不可选提交对象，固定走默认链（§3.2）；一期仅 `YDTJ` 产品线开放外链提交

## 2. 状态机

### 2.1 状态流转图

```
DRAFT → SUBMITTED → BU_REVIEWING(L1) → BU_APPROVED
  → IMPL_REVIEWING(L2) → IMPL_CONFIRMED → PM_REVIEWING(L3) → PM_SUBMITTED
  → LINKED（已关联排期卡片）
REJECTED（任意级次驳回）→ 可重新提交回到 SUBMITTED（级次重置为链上第一级）
```

> 上图为完整三级链（默认链）；**链上未配置的级次直接跳过**，不产生对应状态与流水（如专属链仅配 L3：`SUBMITTED → PM_REVIEWING`）。级次集合由提交时命中的审批链决定（§3.4）。

### 2.2 状态定义

| 状态 | 含义 | 当前级次 | 可执行操作 |
|------|------|---------|-----------|
| `DRAFT` | 草稿，仅提交人可见 | 0 | 编辑 / 提交 / 删除 |
| `SUBMITTED` | 已提交，等待系统匹配审批链（提交对象专属链 → 默认链兜底） | 1 | 撤回 |
| `BU_REVIEWING` | 业务线负责人审批中 | 1 | L1 通过 / L1 驳回 / 提交人撤回 |
| `BU_APPROVED` | 业务线审批通过（瞬时态） | 1→2 | 自动流转至链上下一已配置级次 |
| `IMPL_REVIEWING` | 实施负责人审批中 | 2 | L2 通过 / L2 驳回 |
| `IMPL_CONFIRMED` | 实施确认完成（瞬时态） | 2→3 | 自动流转至链上下一已配置级次 |
| `PM_REVIEWING` | 产品经理审批中 | 3 | L3 通过 / L3 驳回 |
| `PM_SUBMITTED` | 全部审批通过，待关联排期 | 链上最大级次 | 关联排期卡片 |
| `LINKED` | 已关联排期卡片，终态 | 链上最大级次 | 仅查看（排期状态实时刷新） |
| `REJECTED` | 被驳回，终止态 | 保留驳回时级次 | 内部单：提交人重新提交；外部单：无（真终态）|

### 2.3 级次递进规则

- `current_approval_level` 记录当前待审级次：`0`=未提交、`1`=业务线审批、`2`=实施确认、`3`=产品确认
- `max_approval_level` 由提交时命中的审批链写入：默认链固定为 3；专属链取其配置的级次集合中的最大值（专属链可仅配部分级次，§3.2）
- 每级审批通过后流转至**链上下一个已配置级次**（非机械 +1，未配置的级次直接跳过）；达到 `max_approval_level` 且通过后状态置 `PM_SUBMITTED`
- `BU_APPROVED` / `IMPL_CONFIRMED` 为同事务内的瞬时中间态，用于流水记录与消息推送打点，前端不单独展示节点；级次被跳过时对应瞬时态不产生

### 2.4 驳回与重提

- 任意级次均可驳回，驳回必填意见（≥ 10 字），意见写入 `rejection_reason` 与审批流水
- 驳回后状态置 `REJECTED`，保留驳回发生时的 `current_approval_level` 供统计分析
- 提交人可在 `REJECTED` 状态下修改内容并重新提交：状态回到 `SUBMITTED`，`current_approval_level` 重置为**链上第一级**，重新生成审批链快照；重提时**可更换提交对象**（默认回填原值），更换后按新对象重新匹配审批链
- 重提沿用原需求编号，不新建需求记录；历史审批流水全部保留，按轮次（`approval_round`）区分
- **仅 `submit_source=INTERNAL` 单可重提**；外部提交单的 `REJECTED` 为真终态，详见 §2.6

### 2.5 撤回规则

- `SUBMITTED` / `BU_REVIEWING` 状态下提交人可撤回，状态回到 `DRAFT`，审批链快照作废
- 进入 `IMPL_REVIEWING` 及之后不允许撤回，需由审批人驳回
- 撤回记录写入事件审计，不写审批流水
- **外部提交单不支持撤回**（无账号则无撤回主体，且无 `DRAFT` 可回退）

### 2.6 外部提交单的规则差异

外部提交单（`submit_source=EXTERNAL`）**不新增任何状态**，完全复用现有 10 态状态机，仅以下规则不适用：

| 不适用规则 | 原因 | 外部单实际表现 |
|-----------|------|---------------|
| `DRAFT` 草稿态（§2.2）| 无登录态无法回取未完成表单 | 提交即生成 `SUBMITTED`，无暂存入口 |
| 驳回重提（§2.4）| 不回传结果，外部人无从得知驳回 | `REJECTED` 即真终态，不提供重提入口 |
| 提交人撤回（§2.5）| 无账号主体 | 无撤回按钮，内部人也不得代撤回 |
| 提交人即审批人自动跳过（§4.2 `AUTO_SKIP`）| 外部人不可能是审批人 | 完整走 L1/L2/L3 三级，不会发生跳级 |
| 提交人结果通知（§6.1）| 无企微身份且不回传 | 仅推送内部审批人与邀约人，不推外部提交人 |

**驳回后的价值回收路径**：外部单被驳回后如内部认为仍有价值，由**实施负责人新建一条内部单**并在描述中引用原需求编号溯源；**不提供「转内部单」功能**，避免状态机分叉与归属变更。

## 3. 审批链配置规则

> **驱动模式（2026-09-09 起）**：审批链由**提交对象（产品经理）**驱动 —— 提交需求与配置审批链时都**先选定产品经理，再根据其设定审批流程**；原「产品线 × 业务线 × 需求类型 × 优先级」四维配置保留为**默认链**，承接外部提交与未配专属链时的兜底。

### 3.1 条件维度

审批链按 **提交对象 →（产品线 × 业务线 × 需求类型 × 优先级）** 匹配；「提交对象」为第一优先维度。

| 维度 | 取值 | 是否支持降级 |
|------|------|-------------|
| 提交对象（`pm_user_id`） | 具体产品经理；配置行该列为 NULL 即**默认链** | 不支持通配，必须等值命中 |
| 产品线 | `SNACK` / `YDTJ` | 不支持，必须等值命中 |
| 业务线 | `OPS` / `FIN` / `SCM` / `DIGITAL`（`YDTJ` 固定 `*`）| 不支持，必须等值命中 |
| 需求类型 | 新功能 / 功能优化 / 缺陷修复 / 数据报表 / 系统集成 | 支持 `*` 通配 |
| 优先级 | `P0` / `P1` / `P2` / `P3` | 支持 `*` 通配 |

四维降级顺序（在确定提交对象维度后执行）：`(pl, biz, type, priority)` → `(pl, biz, type, *)` → `(pl, biz, *, priority)` → `(pl, biz, *, *)`，命中即止。

### 3.2 两类链：PM 专属链与默认链

| 链类型 | 配置行特征 | 级次要求 | 承接场景 |
|--------|-----------|---------|---------|
| **PM 专属链** | `pm_user_id` 非空 | `{1,2,3}` 的任意**非空子集**（级次由配置决定：如仅 L3 产品确认、L2+L3、完整三级） | 内部提交且提交对象命中时**优先**使用 |
| **默认链** | `pm_user_id` 为 NULL（原四维配置） | `YDTJ` 须配齐 **L1/L2/L3** 三级（L3 承接外部提交，见 §3.4）；SNACK 各业务线保留 L1/L2 作防御性兜底 | ① 外部提交（无提交对象，唯一通道）；② SNACK 默认链为防御性兜底——2026-10-09 起内部单提交对象收窄为必中专属链（§12.1），正常不再命中 |

- 级次语义固定：`1`=业务线审批（`BU_OWNER`）、`2`=实施确认（`IMPL_OWNER`）、`3`=产品确认（`PM`）；专属链未配置某级 = 流转时跳过该级
- 配置页操作范式：**先选提交对象（产品经理），再配置其审批流程**（级次勾选 + 各级审批人）；选「默认链」则维护四维兜底配置
- 专属链可按四维再细化（同一 PM 下不同类型 / 优先级走不同级次组合）；不细化即 `*` 通配
- 默认链 L3 配置的产品经理**仅承接外部提交单**（~~内部提交走默认链时 L3 恒替换为提交对象本人~~ —— 2026-10-09 起内部单候选集收窄为「本归属有专属链的 PM」，内部单不再到达默认链，替换语义同步废止，见 §12.1）；SNACK 默认链无需配置 L3，`YDTJ` 默认链必须配齐 L3（缺级时外链生成与外部提交均被拒）
- **提交对象候选集（配置驱动，2026-10-09 收窄）**：提交页 `/pm-options` 按「产品线 × 业务线」过滤，**仅返回在该归属下配有启用中（`status=1`）专属链的产品经理**（去重，且须为在职有效的 `sys_user`）——收窄后内部提交必中专属链，默认链不再承接内部单（~~专属链 ∪ 默认链 L3 审批人并集~~，2026-09-09 旧口径废止，见 §12.1）。🚨 **配置页的「指定产品经理」选择器不使用该候选集**，走全员人员搜索——否则没配过链的新 PM 永远无法被配置（循环依赖）

### 3.3 各产品线 / 业务线默认链

每个「产品线 + 业务线」组合独立配置默认链，差异集中在 L1（负责人不同）；L2 实施负责人为全公司统一入口。

| 产品线 | 业务线 | L1 | L2（实施负责人）| L3（产品经理）|
|--------|--------|----|------------------|------------------|
| 鸣鸣很忙 | 运营   | 运营负责人     | 实施负责人 | 无需配置（内部单全走专属链，默认链仅防御兜底） |
| 鸣鸣很忙 | 财务   | 财务负责人     | 实施负责人 | 无需配置（同上） |
| 鸣鸣很忙 | 供应链 | 供应链负责人   | 实施负责人 | 无需配置（同上） |
| 鸣鸣很忙 | 数字化 | 数字化负责人   | 实施负责人 | 无需配置（同上） |
| 有点推荐 | `*`    | 有点推荐负责人 | 实施负责人 | 默认承接**外部提交单**的产品经理 |

- 有点推荐默认链只需配一套（`biz_line=*`）；2026-10-09 起内部提交走 PM 专属链，默认链仅承接外部提交（~~内部与外部提交共用同一套~~）

### 3.4 匹配顺序（提交时）

**内部提交**（提交对象 = P，必选）：

1. **先匹配 PM 专属链**：`pm_user_id = P` 的行集合，按 §3.1 四维降级命中即止 → 快照级次 = 专属链配置的级次集合，`max_approval_level` = 链上最大级次
2. **未命中专属链 → 提交失败**（2026-10-09 起）：候选集已收窄为「本归属有专属链的 PM」（§3.2），正常选人必中专属链；仅当专属链在选人后被停用 / 删除时才可能未命中，此时内部提交提示「当前归属未配置审批链，请联系管理员」——~~未命中回退默认链且 L3 替换为提交对象本人~~（旧口径废止，默认链快照不再承接内部单，见 §12.1）

**外部提交**（无提交对象）：直接按第 2 步匹配默认链，但 **L3 不替换**，取默认链配置的产品经理（或签）；L3 审批通过时将实际通过人写入 `requirement.pm_user_id`。**未命中配置时不得暴露内部配置信息**：向外部人统一提示「提交暂时不可用，请联系邀约人」，同时向邀约人推送企微告警（详见 §8.5）。

### 3.5 或签模式

- 各级审批均为**或签**：同一级次配置多名审批人时，任一人通过即视为该级通过，其余人待办自动关闭
- 任一人驳回即整单驳回，不等待其他审批人
- 或签模式参考 任务中心 的待办聚合与关闭逻辑，本模块不引入全员确认（多签）模式

### 3.6 快照机制

- 提交（含驳回重提）时按 §3.4 匹配，将链上各级审批人写入审批链快照表；专属链仅写入其配置的级次（未配置的级次不产生快照行）
- 流转过程中只读快照，不再回查配置表：配置变更不影响在途需求，避免中途换人导致审批断链
- 审批人离职或调岗时，管理员需更新配置并对在途需求执行「审批链重建」：按需求 `pm_user_id` 重新走 §3.4 匹配（内部单仅匹配专属链，自研通道在途单适用；流程中心通道在途单按 §12.5#8 处置），旧行置 0，`approval_round` 与级次集合保持不变——**重建只替换审批人，不增减级次**，操作写入事件审计

## 4. 权限矩阵

| 角色 | 可执行操作 |
|------|-----------|
| 业务线员工 | 提交/撤回/修改草稿 |
| 邀约人（内部任一拥有外链菜单权限的用户）| 生成外链 / 查看本人生成的外链 / 撤销本人生成的外链 |
| 业务线负责人 | L1 审批/驳回 |
| 实施负责人 | L2 审批/驳回 |
| 产品经理 | L3 审批/驳回/关联排期卡片 |
| 管理员 | 配置审批链/导出统计/查看与撤销全部外链 |
| 外部提交人 | 仅凭有效 token 提交需求（免登录），无任何查询与管理权限 |

### 4.1 数据可见范围

| 角色 | 列表可见范围 |
|------|-------------|
| 业务线员工 | 仅本人提交的需求 |
| 邀约人 | 本人提交的需求 + 由本人生成外链产生的外部单 |
| 业务线负责人 | 本业务线全部需求（含他人提交） |
| 有点推荐负责人 | `product_line=YDTJ` 全部需求（含内部单与外部单）|
| 实施负责人 | 全部产品线与业务线需求 |
| 产品经理 | 提交对象为本人（`pm_user_id`）的需求 + 本人对口归属的需求 |
| 管理员 | 全部需求 + 审批链配置 + 外链台账 + 统计导出 |

- **Tab 取数口径**：「我提交的」按 `submit_by = 当前用户`（外部单 `submit_by` 为 NULL，天然不入该 Tab）；外部单归入新增的「外部提交」 Tab，以 `submit_source=EXTERNAL` 取数，可见范围同本表规则，避免外部单落在所有 Tab 之外

### 4.2 权限约束

- 审批操作后端二次校验：当前登录人必须存在于审批链快照的**当前级次**审批人清单中，否则返回 403
- **流程单豁免（2026-10-12 定稿，D6）**：需求已关联流程实例（`flow_instance_id>0`）时，上款快照校验**不再执行**——页内「通过/驳回」直接以操作人身份代调流程中心 `approve`/`reject`，以平台节点快照匹配为唯一闸门（平台 403 即为无权限；消除转审/加签/跳节点后两侧快照不一致的误拦，规则真源：流程中心 business-rule §6.3）；自研通道在途单（`flow_instance_id=0`）维持上款校验不变
- 提交人不得审批自己提交的需求；若提交人同时为该级审批人，则该级自动跳过并写入流水说明（仅对内部单生效）
- App 端仅开放提交、L1/L2/L3 审批通过与驳回；审批链配置、外链生成与管理、统计导出仅 Web 端可用
- **公开接口不进登录鉴权体系**：外链相关公开接口（`/api/v1/public/requirement/*`）免登录，仅以 token 有效性 + 图形验证码 + 频率限制作为准入控制（详见 §8.4），**不得复用内部提交接口**

## 5. 排期关联规则

- 关联入口在全部级次审批通过（状态 `PM_SUBMITTED`）后开放，仅该需求的产品经理（`pm_user_id`：内部单=提交对象，外部单=L3 实际通过人）与管理员可操作
- 关联方式二选一：输入 `card_no` 精确搜索，或从「候选排期卡片列表」中选择
- 关联结果写入 `linked_card_no`，需求状态置 `LINKED`
- 卡片状态实时展示：详情页通过 `/api/v1/schedule/cards?month=` 查询 feature-schedule 卡片，展示 `PENDING`（待开发）/ `IN_PROGRESS`（开发中）/ `DONE`（开发完成）及排期日期
- **单向关联**：本模块只读取排期卡片信息，不回写卡片任何字段；卡片被删除时需求详情页展示「关联卡片已失效」提示，需重新关联
- 一条需求只能关联一张卡片；一张卡片允许被多条需求关联（同一卡片承载多条同类需求）
- 关联可解除：解除后状态回退至 `PM_SUBMITTED`，`linked_card_no` 置空，写入事件审计

### 5.1 候选卡片列表（方式二）

> 2026-09-16 重定义：候选集由「未关联排期卡片」放宽为「全部有效排期卡片（含已关联）」，支撑「同类需求同挂一张卡片」场景的卡片定位；同步新增「开发人 / 需求提交人」双筛选维度。

- **候选集**：`feat_schedule_card` 全部有效卡片（`PENDING` / `IN_PROGRESS` / `DONE`），**排除 `NON_FEATURE` 旁路卡与已删除卡**；含已被其他需求关联的卡片（规则上本就允许一卡多需求）
- **默认过滤**：按月份（`scheduled_date` 所属月，默认当月）；Backup 池卡（`scheduled_date` 为 NULL）不参与月份过滤、不入候选
- **展示字段**：卡片编号 / 标题 / 排期日期 / 开发状态 / 开发人 / 已关联需求数（`linked_req_count > 0` 时展示「已关联 N 条需求」角标，附已关联需求的提交人名单）
- **筛选维度**（在月份之上叠加，均为人员选择器单选、可清空）：
  | 筛选 | 匹配逻辑 | 空值口径 |
  |------|---------|---------|
  | 开发人 | 等值匹配卡片 `dev_user_name`（选择器选人后按姓名传值） | 🚨 `PENDING` 卡 `dev_user_id` / `dev_user_name` 为 NULL（feature-schedule v1.6+ 领取开发时才写入），**不参与该筛选**；筛选器旁常驻说明「仅已被领取开发 / 已完成的卡片有开发人」 |
  | 需求提交人 | 反查命中：该卡片已被「`submit_by` = 选中人」的需求关联；走 `requirement.idx_submit_by` + `idx_linked_card` 同库反查 `linked_card_no` 集合后过滤候选，不触碰 feature-schedule 侧（单向关联红线不变） | 🚨 **仅内部提交单参与**（外部单 `submit_by` 为 NULL、提交人为自由文本不入 `sys_user`，不参与筛选；其姓名仅在卡片「已关联名单」中正常展示） |
- **同挂确认**：选中「已关联 N 条需求」的卡片提交时，弹窗内二次确认「该卡片已承载 N 条需求（提交人：{名单}），确认将本需求同挂到该卡片？」；确认后走同一 `/link-card`，无额外接口
- **排序**：`scheduled_date` 升序（近期在前），同日期按 `card_no` 升序；已关联标识仅作展示、不影响排序
- 方式一（`card_no` 精确搜索）不受本次变更影响，行为不变

## 6. 通知与企微推送

推送统一在事务提交后通过 `afterCommit` 异步触发，禁止在事务内同步调用，能力复用 企微应用消息发送。

### 6.1 双通道推送

- **个人消息**：推送给下一级审批人（待办提醒）或提交人（结果通知），带需求详情页跳转链接；**外部单的「提交人结果通知」改推邀约人**（外部人无企微身份且不回传）
- **业务群消息**：按需求所属产品线 / 业务线路由到对应企微群（运营群 / 财务群 / 供应链群 / 数字化群 / 有点推荐需求群），用于归属内信息同步

### 6.2 群消息推送规则

| 触发事件 | 推送目标群 | 消息内容 |
|---------|-----------|----------|
| 需求提交 | 所属业务线群 | 「{提交人} 提交了新需求：{标题}，优先级 {P0-P3}」；外部单为「{外部提交人}（外部，邀约人：{邀约人}）提交了新需求：{标题}」 |
| L1审批通过 | 所属业务线群 | 「{需求标题} 已通过业务线审批，流转至实施负责人」 |
| L3审批通过 | 所属业务线群 | 「{需求标题} 已通过全部审批，进入研发排期」 |
| 驳回 | 所属业务线群 | 「{需求标题} 被 {审批人} 驳回，原因：{意见摘要}」 |
| 关联排期 | 所属业务线群 | 「{需求标题} 已关联排期卡片 {card_no}，预计 {日期} 开发」 |

- 业务线 → 群推送目标映射落库在 `requirement_approval_config.wecom_webhook_key`（实现落地：企微群 chatId 能力项目未实现，改用**企微群机器人 Webhook Key**，支持 Nacos KMS 引用名，复用报表群推送体系），新增业务线须同步补齐，否则群消息静默失败（仅记录告警日志，不阻断主流程）
- 驳回意见摘要截取前 50 字，超出以 `…` 省略
- L2 审批通过不推群消息（内部流转节点），仅推个人消息给 L3 产品经理

### 6.3 消息标识

- `bizKey`：`REQUIREMENT_SUBMITTED` / `REQUIREMENT_APPROVED` / `REQUIREMENT_REJECTED` / `REQUIREMENT_LINKED` / `REQUIREMENT_GROUP_NOTIFY`
- `dedupeKey`：`{bizKey}_{requirement_id}_{timestamp_minute}`，同一分钟内重复触发去重，防止审批人连点导致重复推送
- 推送失败不回滚业务事务，失败记录写入事件审计供人工重推

## 7. 接口概要

| 操作 | 方法 | 说明 |
|------|------|------|
| 提交需求 | `POST` | 创建或提交需求，生成编号与审批链快照；**内部提交必传提交对象（`pmUserId`）**，按「专属链 → 默认链」匹配生成快照（§3.4）；`DRAFT` 保存不生成快照 |
| 需求列表 | `GET` | 分页查询，支持业务线 / 状态 / 优先级 / 类型 / 提交人 / 时间区间筛选与 Tab 视角切换 |
| 需求详情 | `GET` | 返回需求主体 + 审批链快照 + 审批流水 + 关联排期卡片实时状态 |
| 审批通过 | `POST` | 按当前级次校验审批人，递进至链上下一已配置级次；外部单 L3 通过时将实际通过人写入 `pm_user_id` |
| 驳回 | `POST` | 校验审批人后置 `REJECTED`，必填驳回意见（≥ 10 字） |
| 撤回 | `POST` | 仅 `SUBMITTED` / `BU_REVIEWING` 可撤回，回到 `DRAFT` 并作废快照 |
| 关联排期 | `PATCH` | 写入 `linked_card_no` 并置 `LINKED`；支持解除关联回退至 `PM_SUBMITTED` |

**通用约束：**

- 所有接口后端二次校验菜单权限与角色可见范围，不依赖前端按钮控制
- 任何导致状态 / 级次 / 关联关系变更的接口，成功后须写入审批流水与事件审计各一条
- 审批类接口对同一需求同一级次做幂等控制：重复提交视为已处理，返回当前状态而非报错
- 外部提交与内部提交共用同一套审批 / 详情 / 统计接口，仅**提交入口**分离（公开接口独立 Controller）

### 7.1 外链相关接口

**内部接口**（需登录，路径前缀 `/api/v1/inner/busyming/requirement/public-link`）：

| 操作 | 方法 | 说明 |
|------|------|------|
| 生成外链 | `POST` | 入参：邀约对象备注、有效期天数、提交次数上限、需求类型默认值；**仅返回完整链接，不返回二维码图片**（二维码由前端依链接本地生成，沿用采购邀约范式）|
| 外链台账 | `POST` | 分页查询，支持状态 / 邀约对象 / 生成人 / 时间区间筛选；非管理员仅可见本人生成的链接（后端强制收口，不依赖前端传参）|
| 撤销外链 | `POST` | 仅 `GENERATED` 可撤销，必填撤销原因；已提交产生的需求不受影响 |

**公开接口**（免登录，路径前缀 `/api/v1/public/requirement`）：

| 操作 | 方法 | 说明 |
|------|------|------|
| 校验 token | `POST` | 入参仅 `token`；返回可用标识 + 邀约对象备注（预填用）+ 需求类型可选项；不可用时返回失效原因码 |
| 图形验证码 | `POST` | 按 token 下发验证码图片，5 分钟有效，一次性消费 |
| 提交需求 | `POST` | 入参：token + 验证码 + 标题 + 描述 + 需求类型 + 姓名 + 部门 + 手机号；成功返回需求编号 |

**公开接口专属约束：**

- 路径必须在 `/api/v1/public/**` 下，在网关 / 拦截器白名单中显式声明免登录，**不得与内部接口共用 Controller**
- 返回体不得包含任何内部人员姓名、审批人信息、业务线枚举、需求列表数据（邀约对象备注除外，因其为邀约人主动填写）
- 所有公开接口调用均写入 `requirement_event_log`，带 `source_ip` + `user_agent`

## 8. 外链邀约与外部提交

仅 `product_line=YDTJ`（有点推荐）开放。能力范式对齐 采购邀约 的 token 反查模式。

### 8.1 外链形态：一次性定向 token

- 链接由内部人**逐个生成、定向发放**，不提供长期通用链接，不得公开张贴或群发
- URL 形式：`https://{host}/public/requirement?token={token}`，**URL 中唯一参数为 token**，产品线 / 业务线 / 邀约对象 / 有效期全部落库反查
- 生成时同时返回二维码（内容即完整链接），供微信 / 企微发送
- 生成时内部人必填**邀约对象备注**（公司/联系人），仅供内部溯源与台账识别；外部人进页后**仍需手填自己的姓名与部门**（可用备注值预填，允许修改）

### 8.2 「一次性」的精确语义

| 维度 | 口径 |
|------|------|
| 访问次数 | **不限制**，可重复打开（避免误关页即失效），仅计数 |
| 提交次数 | 默认上限 **1 次**，生成时可配；达上限后链接置 `USED` |
| 达上限后访问 | 展现「已提交」提示页（带需求编号），不再展示表单 |
| 有效期 | 默认 30 天，可配 7/15/30/60/90 天；过期后无论是否提交过均置 `EXPIRED` |
| 撤销 | 邀约人与管理员可随时撤销未使用链接，已提交产生的需求不受影响 |

- 因提交后**不可重填也不可修改**，提交前必须弹出**预览确认弹窗**（完整回显标题 / 描述 / 类型 / 姓名 / 部门 / 手机号），文案见 [`public-ui.md`](public-ui.md)

### 8.3 外部提交字段边界

| 字段 | 外部人是否可填 | 说明 |
|------|---------------|------|
| 需求标题 | ✅ 必填 | ≤ 128 字 |
| 需求描述 | ✅ 必填 | ≥ 20 字，≤ 2000 字（高于内部门槛，降低无效单）|
| 需求类型 | ✅ 必选 | 默认值由链接携带，可改 |
| 提交人姓名 | ✅ 必填 | 落 `external_submitter_name`，≤ 64 字 |
| 提交人部门 | ✅ 必填 | 落 `external_submitter_dept`，**自由文本不关联 `sys_dept`** |
| 手机号 | ✅ 必填 | 落 `external_submitter_contact`，仅格式校验，**不发短信不做真实性验证**，仅供内部回访 |
| 业务线 | ❌ 不展示 | 系统固定写 `*` |
| 优先级 | ❌ 不展示 | 统一入库为链接默认值（默认 `P2`），由审批人修正 |
| 附件 | ⚠️ 仅图片 | **仅开放图片上传**（≤ 5MB/张，最多 3 张，单次提交总大小 ≤ 15MB）；文档与视频仍不开放（免登录上传存在存储滥用与恶意文件风险），详见 §9.5 |

### 8.4 安全与防刷

因**不回传结果**，手机号无需真实性校验，防刷降级为下列四道（**不使用短信验证码**）：

| 防线 | 规则 |
|------|------|
| token 有效性 | 非法 / 过期 / 已撤销 / 达提交上限均拒绝，不区分返回时延（防枚举）|
| 图形验证码 | 提交前必填，5 分钟有效、一次性消费；连续错 3 次强制刷新 |
| 提交次数上限 | 单 token 默认 1 次，递增与写入同事务 + 行锁 |
| IP 频率限制 | 单 IP 对公开接口 **10 次/分钟**，超限返回统一限流文案并记 `RATE_LIMITED` |

- 全部公开接口访问落 `source_ip` + `user_agent` + `public_link_id` 到 `requirement_event_log`，供异常回溯
- 外部提交内容进入内部列表前不做自动审查，但详情页必须显式标识「外部提交」以提醒审批人警惕

### 8.5 单向收口口径

外部提交**完全单向**：除提交成功页展示需求编号外，系统不向外部人回传任何后续信息。

- 不提供进度查询页、不发短信 / 邮件通知、不提供回执码自查
- 需求编号仅作为提交凭证展示，供外部人线下向邀约人查询使用
- 外部单的任何状态变更（通过 / 驳回 / 关联排期）均**只通知邀约人**，由邀约人自行决定是否线下告知外部人
- 外链因未命中审批链配置而提交失败时，向邀约人推送企微告警「您发放的需求外链提交失败：有点推荐审批链未配置」

### 8.6 统计口径

- 需求总量 / 驳回率 / 平均审批时长等现有指标均**默认含外部单**，可按 `submit_source` 与 `product_line` 下钻
- 外链专属指标：链接生成数 / 访问转化率（`submit_count>0` 链接数 ÷ 生成数）/ 外部单驳回率，用于评估外部需求质量
- 外部单驳回率持续偏高时，应回收对应邀约人的外链生成权限（运营措施，非系统自动）

## 9. 附件管理规则

附件为需求描述的补充证据（截图 / 原型 / 说明文档 / 录屏），文件实体落 OSS，库内只存元信息（字段真源见 `data-model.md` §7）。

> **实现落地差异（2026-08-19，已随代码实现确认）**：本章有 4 处规则发生变更，逐节已标注，汇总如下：
> 1. 🚨 **§9.3「内容安全审核」整节本期不实现**（用户裁决）：库表不建 `content_check_status` / `content_check_at`，三端 UI 一律不渲染审核角标；连带 `rejected` 不展示 / `pending` 仅上传人可见 / §9.5「强制过审」均失效。
> 2. **附件改为前端 OSS STS 直传**（用户裁决）：前端持临时凭证直传 OSS，后端只收元信息；因此 §9.2 的「未保存的全新表单不开放上传」前置不再需要，OSS 路径改按月分目录，签名 URL 改前端自签。**公开 H5 是唯一不走直传的端**（免登录拿不到 STS）。
> 3. **§9.4 追加态补 `SUBMITTED`**：它是提交后到 L1 审批人接手的瞬时过渡态，禁止追加会让提交人卡在纯技术状态上（原文已列入但推论只提三个 `*_REVIEWING`，此处明确）。
> 4. **§9.6 草稿态删除不清 OSS**：统一为只逻辑删除，不做 OSS 物理移除。

### 9.1 上传限制

| 类型 | 允许扩展名 | 单个大小上限 | 数量上限 | 开放端 |
|------|-----------|-------------|---------|--------|
| 图片 `image` | `jpg` / `jpeg` / `png` / `webp` / `gif` | ≤ 10MB（H5 ≤ 5MB）| 内部端 ≤ 20 张；H5 ≤ 3 张 | Web / App / H5 |
| 文档 `document` | `pdf` / `docx` / `xlsx` / `pptx` / `txt` | ≤ 50MB | ≤ 10 个 | **仅内部端**（Web）|
| 视频 `video` | `mp4` / `mov` | ≤ 200MB | ≤ 3 个 | **仅内部端**（Web）|

- 数量上限**按类型分别计算**，不合并计数（即单条需求最多 20 图 + 10 文档 + 3 视频）
- 校验以**后端为准**：按 `upload_source` 分支校验类型白名单、大小与张数，前端限制仅作体验优化，不作为安全边界
  - 🚨 **落地确认（2026-08-19）**：改为前端直传后这条仍然成立。后端按 `upload_source` 强校验上报的 `file_ext`（白名单）/ `file_size`（大小上限）/ 张数上限（按类型分别计数），且 `file_type` 由扩展名**反推，不信前端传值**
- 扩展名与 MIME 双校：二者不一致直接拒收（防止改后缀绕过白名单）；`exe` / `sh` / `bat` / `js` 等可执行文件一律拒收
  - ⚠️ **落地差异（2026-08-19）**：前端直传后后端拿不到文件流，**MIME 校验本期无法实施**，安全边界退为扩展名白名单 + 登录态 / token 约束；可执行扩展名仍在白名单外，一律拒收
- App 端仅开放图片（相册 / 拍照），**不开放文档与视频**（移动网络下大文件上传成功率低，且缺少文件管理器语义）

### 9.2 存储规则

> **实现落地差异（2026-08-19，已随代码实现确认）**：
> 1. **OSS 路径改为 `requirement/{yyyyMM}/{uuid}.{ext}`**（不含 `requirement_id`）：前端直传发生在需求落库之前，拿不到需求 ID；按月分目录同样满足批量回溯与生命周期管理。⚠️ App 端实测复用既有 `buildOssKey(dir, fileName)` 会多产生一层日期目录，实际 key 形如 `requirement/202608/2026-08-19/{ts}.{ext}`；前缀 `requirement/{yyyyMM}` 仍命中生命周期规则，不作修正。
> 2. **「未保存的全新表单不开放上传」本期不实现**：直传不依赖需求已存在，`ossKey` 先存前端组件 state，随表单提交一并入库；因此 Web 新增页不再置灰上传区，App 也不需要「临时暂存区」概念。未提交就离开产生的孤儿对象交 Bucket 生命周期规则回收。
> 3. 🚨 **签名 URL 有效期不是 5 分钟**：下载 / 预览改由**前端用自有 `keyToUrl(ossKey)` 自签**，有效期取前端实现值（Web 侧当前为 **1 小时**，沿用既有 OSS 封装）；阿里云 STS `DurationSeconds` **下限本身是 15 分钟，5 分钟在平台层面就不可达**。鉴权因此前移到 `attachment/list`：看不到该需求就拿不到 `ossKey`，也就无法自签。

- OSS 路径固定：~~`requirement/{requirement_id}/{uuid}.{ext}`，按需求 ID 分目录~~ → **`requirement/{yyyyMM}/{uuid}.{ext}`，按月分目录**，便于批量回溯与生命周期管理
- 文件名 **UUID 化防重**：原始文件名仅落 `file_name` 供展示与下载回写，不进 OSS 路径（避开中文 / 特殊字符 / 同名覆盖三类问题）
- ~~草稿阶段上传时 `requirement_id` 已存在（草稿先落库再传附件）；**未保存的全新表单不开放上传**~~ —— **本期不实现**（直传不依赖需求已存在，元信息随表单提交）
- 下载 / 预览一律走 **OSS 签名 URL**（~~默认有效期 5 分钟~~ → **由前端自签，有效期取前端实现值，当前 1 小时；阿里云 STS 下限 15 分钟，5 分钟不可达**），不暴露 Bucket 直链，不开放公共读
- Bucket 名随附件落库（`oss_bucket`），不取运行时配置，保证 Bucket 迁移后历史附件仍可访问

### 9.3 内容安全审核（🚨 本期整节不实现）

> **实现落地差异（2026-08-19，用户裁决）**：**不做图片 / 视频内容安全审核，本节全部规则本期不实现**。下方原文保留供后续启用时直接参照，当前靠类型白名单 + 登录态 / token 约束兼内容风险。连带失效项：
> - 库表**不建** `content_check_status` / `content_check_at`，`RequirementAttachmentVO` 不回这两个字段（data-model §7）。
> - `rejected` 附件不展示 / 不可下载、`pending` 仅上传人可见两条可见性规则**不存在**；未删除附件对有权看该需求的人一律可见（api-spec §5.2）。
> - 三端 UI **一律不渲染审核角标**：Web 详情页 / 编辑页的「审核中」橙标与「未通过」红标、编辑页「审核不阻塞提交」灰字、App 的 `pending` 置灰 + 「审核中」文字 + Toast、H5 的审核信息隔离说明，均不存在。
> - 事件类型 `ATTACHMENT_CHECK_REJECTED` 枚举保留但**无写入方**。

- 图片与视频上传成功后**异步**提交阿里云内容安全 API 审核，不阻塞上传响应（同步审核会把上传耗时拉到秒级以上）
- 状态流转：`pending`（初始）→ `passed` / `rejected`；回调写入 `content_check_status` 与 `content_check_at`
- `pending` 期间附件**可展示给上传人本人**（否则体验上像上传失败），列表项带「审核中」角标
- `rejected` 的附件：详情页**不展示、不可预览、不可下载**，上传人侧展示「内容审核未通过，请删除后重新上传」；记录与 OSS 文件**保留供审计**，不物理删除
- 文档类附件不过内容安全（无成熟文本文档审核能力），仅依靠类型白名单 + 内部端登录态约束
- 内容安全接口调用失败（超时 / 限流）时保持 `pending` 并重试，**不自动置 `rejected`**，避免基础设施故障误封正常附件

### 9.4 审批中追加附件

- 已提交（`SUBMITTED` / `BU_REVIEWING` / `IMPL_REVIEWING` / `PM_REVIEWING`）的需求，**允许提交人追加附件**，用于响应审批人的补材要求，避免为了传一张图而驳回重提
  - **落地明确（2026-08-19）**：`SUBMITTED` **同样按「追加」放行**（它是提交后到 L1 审批人接手的瞬时过渡态，禁止追加会让提交人卡在纯技术状态上），同样落 `is_appended=1` 并通知当前级次审批人
- 追加的附件 `is_appended=1`，详情页以「审批中追加」角标与提交时附件区分
- 追加成功后**自动通知当前级次全部审批人**（企微个人消息，~~`bizKey=REQUIREMENT_ATTACHMENT_APPENDED`~~ → **落地为 `REQUIREMENT.ATTACHMENT_APPENDED`**），文案「{提交人} 为需求 {编号} 补充了 {N} 个附件」
  - **落地差异（2026-08-19）**：企微 `biz_key` 命名从下划线改为**点分隔**以对齐库内既有同域模板（如 `REQUIREMENT.SUBMITTED`）：`REQUIREMENT.ATTACHMENT_APPENDED` / `REQUIREMENT.SLA_REMIND` / `REQUIREMENT.SLA_ESCALATE` / `REQUIREMENT.TARGET_DATE_WARN`
- 追加**不重置审批级次、不重建快照、不重算节点停留时长**（不得以追加附件刷新 SLA 计时规避催办，见 §10.1）
- 只能追加不能删除（见 §9.6）；外部单（`submit_source=EXTERNAL`）**不支持追加**（无登录主体，且链接已 `USED`）

### 9.5 H5 附件特殊规则

外部免登录提交（公开 H5）的附件能力为**受限开放**，与内部端不同口径：

> **实现落地差异（2026-08-19）**：公开 H5 是**唯一不走前端直传的端**—— 免登录拿不到 STS，把 OSS 写凭证暴露给公网正是本节要防的存储滥用，故保留后端转存：`POST /api/v1/public/requirement/attachment/upload`（multipart：`token` + `file`）后端转存 OSS 后**只返回元信息、不落库**，再随 `/public/requirement/submit` 的 `attachments` 在**同事务**写入；与提交接口**共用同一 token 校验链与 IP 限流计数**。

| 维度 | H5 口径 |
|------|---------|
| 类型 | **仅图片**（`jpg`/`jpeg`/`png`/`webp`）；文档与视频仍不开放 |
| 大小 | 单张 ≤ 5MB，**单次提交总大小 ≤ 15MB** |
| 数量 | 最多 3 张 |
| 提交时机 | 图片随表单**一并提交**，需配合图形验证码校验通过；~~不提供先上传后提交的独立上传接口~~ → **落地为：提供带 token 的转存接口，但元信息随表单一并提交，不存在免验证的独立落库通道** |
| 上传人 | `upload_user_id` 为 NULL，`upload_source=h5`，`upload_user_name` 写外部提交人手填姓名 |
| 内容安全 | ~~**强制过审**（外部渠道风险最高）；`rejected` 后内部详情页不展示~~ → 🚨 **本期不适用**（§9.3 整节不实现）；风险控制退为 token 校验 + 图形验证码 + IP 限流 + 扩展名白名单 |
| 失败降级 | 图片上传失败**不阻塞需求提交**：需求主体先落库，失败图片记 `NOTIFY_FAILED` 同类审计事件，页面提示「需求已提交，部分图片上传失败」|
| IP 限流 | 与公开提交接口共用同一限流计数（§8.4），不单独放宽 |

- 🚨 开放图片后，§8.5 **单向收口口径不变**：外部人仍不可查看已上传附件、不可删除、不可补传（提交即终止）

### 9.6 附件删除

> **实现落地差异（2026-08-19）**：草稿态删除**不做 OSS 异步清理** —— 三种场景统一为**只逻辑删除，不做 OSS 物理移除**（异步清理失败会以「OSS 报错」形态掩盖业务首因），孤儿对象交 Bucket 生命周期规则回收。

| 需求状态 | 删除行为 |
|---------|---------|
| `DRAFT` 草稿 | 提交人可删：置 `deleted_flag=1`；~~**并异步清理 OSS 文件**（未提交无留痕价值）~~ → **落地不清 OSS** |
| 已提交（审批中 / 终态）| **不提供删除入口**；如内容不当需管理员介入，仅置 `deleted_flag=1`，**不从 OSS 物理移除** |
| `REJECTED` 后重提 | 历史附件全部保留且不可删；修改阶段只能新增（保证审批人能看到驳回时的原始材料）|

- 删除一律写 `requirement_event_log`（`ATTACHMENT_DELETED`），记录操作人与文件名
- 需求本体软删（草稿删除）时级联置其全部附件 `deleted_flag=1`
- **元信息随表单全量同步时的删除口径（2026-08-19）**：`SaveReq` / `ExternalSubmitReq` 的 `attachments` 数组在同事务内做全量同步 —— 不在数组里的已有附件**仅 `DRAFT` 态允许软删**，`REJECTED` 重提**只能新增不能删**（与本表第 3 行一致）

## 10. 审批时效与 SLA 管理

解决「需求提上去就没人理」的治理缺口：以可配置阈值驱动自动催办与升级，并把时效沉淀为可计量指标。阈值配置落 `requirement_sla_config`（`data-model.md` §8）。

### 10.1 催办触发

- 审批节点停留时长超过 `remind_hours`（默认 48h）仍未操作，系统自动向**当前级次全部审批人**发送企微催办消息（或签模式下同级多人均收到，任一人处理即停止后续催办）
- **停留时长起算点**：当前轮次（`approval_round`）进入本级的那条流水的 `operated_at`（即上一级通过时间；L1 取提交时间 `submit_at`），与 `requirement_approval_log.duration_minutes` 同源口径
- **自然时间计算**，不扣除周末与法定节假日（阈值本身已含缓冲，引入工作日日历会大幅抬高实现与解释成本）
- 只对**审批中**状态生效：`BU_REVIEWING` / `IMPL_REVIEWING` / `PM_REVIEWING`；`DRAFT` / `SUBMITTED`（瞬时态）/ `PM_SUBMITTED` / `LINKED` / `REJECTED` 均不纳入
- 追加附件、刷新页面、审批人查看详情等行为**均不重置计时**；仅当前级次发生通过 / 驳回 / 撕回才重算

### 10.2 升级触发

- 节点停留超过 `escalate_hours`（默认 72h）仍未操作，系统通知**该审批人的直接上级 + 需求提交人**
- 上级取数：审批人 `sys_user` 所属 `sys_dept` 的部门负责人；取不到上级时**降级通知实施负责人**（L2 审批人）兼作治理兼管人，不得静默丢弃
- 外部单（`submit_source=EXTERNAL`）的「提交人通知」**改推邀约人**（对齐 §6.1 / §8.5 单向收口，不推外部人）
- 升级**不改变审批权限**：上级仅收到知晓消息，**不获得代审权**（代审会穿透审批链快照，与 §4.2 权限校验冲突）；如确需换人走管理员「审批链重建」（§3.4）
- 升级后**仍继续按催办窗口周期性催办**，直至节点被处理（不因已升级而停止催办）

### 10.3 差异化配置

默认阈值矩阵（初始化写入，管理员可在「SLA 配置」页调整）。🚨 **优先级沿用本模块 `P0/P1/P2/P3` 枚举**，不引入第二套命名：

| 优先级 | 语义 | `remind_hours` | `escalate_hours` |
|--------|------|----------------|------------------|
| `P0` | 紧急 | 24 | 48 |
| `P1` | 高 | 48 | 72 |
| `P2` | 中（普通）| 48 | 72 |
| `P3` | 低 | 72 | 120 |

- 三个级次（L1/L2/L3）默认**共用同一套阈值**，但表结构支持按 `approval_level` 单独调整（如 L2 实施归集需更长思考时间可单独放宽）
- `P1` 与 `P2` 默认同口径（普通档）：避免初期档位过细导致审批人无法预期；如后续数据显示 P1 堆积严重再收緊
- 约束：`escalate_hours` 必须 **> `remind_hours`**，且二者均为 1–720 的整数；保存时前后端双校
- 产品线维度必须等值命中，优先级支持 `*` 通配降级（匹配顺序见 `data-model.md` §8）

### 10.4 目标日期预警

- `target_date` 距今 **≤ 7 天**且需求仍处于审批中（**未达 `LINKED`**）时，推送预警给 **L2 实施负责人**（全公司统一归集入口，最有条件协调资源）
- 预警文案：「需求 {编号}「{标题}」目标完成日 {target_date} 仅剩 {N} 天，当前仍在 {当前节点}，尚未关联排期」
- 同一需求在整个预警窗口内（距目标日 7 天内）**每天最多推 1 次**，去重键含自然日
- `target_date` 已过期且仍未 `LINKED` 时**持续日推**，文案改为「已超目标完成日 {N} 天」，直至达 `LINKED` 或 `REJECTED`
- 预警与催办**互不抵消**：两者触发条件与接收人不同，可同时发出
- **落地补充（2026-08-19）**：目标日期预警**同样纳入静默时段延后**（见 §10.7）—— 因为它是日推且去重键含自然日，`00:00–08:00` 命中时延到 `08:00` 那轮仍属同一自然日，当天照发不丢；静默期内只写 `SLA_DEFERRED`（不占去重窗口）

### 10.5 滞留需求看板

- Web 管理端需求列表新增「滞留需求」视角：筛选条件为「**当前级次停留 ≥ `remind_hours` 且未处理**」
- 默认排序：**停留时长倒序**（滞留最久的在最前）
- 可见范围沿用 §4.1 角色口径：业务线负责人只看本业务线滞留单，实施负责人与管理员看全部；**不为本视角放宽任何可见范围**
- 看板行展示：停留时长（天/小时）/ 当前级次与审批人 / 已催办次数 / 是否已升级，支持导出
- 看板提供「手动催办」按钮（管理员 / 实施负责人）：立即发一次催办，**共用 §10.7 去重窗口**（窗口内已催过则提示已催办时间，不重发）
  - 🚨 **落地明确（2026-08-19）**：**手动催办不受静默时段限制**（人在页面上主动点击，抑制发送违背操作意图），只受去重窗口约束

### 10.6 SLA 仪表盘指标

| 指标 | 取数口径 |
|------|---------|
| 各业务线平均审批耗时 | 按 `requirement_approval_log.duration_minutes` 聚合均值，**按 L1/L2/L3 拆分**；可按产品线 / 业务线下钻 |
| 端到端平均周期 | ~~`submit_at`~~ → **首次 `SUBMIT` 流水时间**（见下方落地差异）→ 达 `LINKED` 的时间差均值；未达 `LINKED` 的需求**不入分母**（避免在途单拉低均值）|
| 超时率 | ~~区间内曾触发过催办（停留超 `remind_hours`）的需求数~~ → **区间内 `duration_minutes` 实际超阈值的节点数** ÷ 区间内受理需求数（见下方落地差异）|
| 趋势图 | 上述三项按**周 / 月**聚合；X 轴**按日期正序排列**（最早在左），不用 Top N 排序也不设「其他」汇总柱 |
| **当前滞留条数（实时）** | **落地新增第 4 张卡**（接口字段 `currentStaleCount`）：当前处于审批中且停留 ≥ 命中 `remind_hours` 的条数，**实时值，不受时间区间筛选影响**（区间筛选描述的是历史样本，滞留是「此刻」的治理压力）|

> **实现落地差异（2026-08-19，已随代码实现确认）**：
> 1. **端到端周期的「首次 `submit_at`」取自审批流水**：`MIN(operated_at) WHERE action='SUBMIT'`，而非 `requirement.submit_at` —— 后者在驳回重提时被覆盖，直接用会让端到端周期**系统性偏短**，恰好掩盖本表下一条要求保留的返工成本；流水取不到时 fallback `r.submit_at`。
> 2. 🚨 **超时率按 `approval_log.duration_minutes >= 60 × 命中 remind_hours` 实算**，**不依赖 `SLA_REMINDED` 事件是否存在** —— 否则 Job 上线前的历史数据、静默延后的（§10.7 只写 `SLA_DEFERRED`）、推送失败的都会被误判为「未超时」。
> 3. `overtimeRate` 由**后端格式化为百分数文本**（如 `12.5%`）直接下发，不是 0–1 小数，前端不再二次换算。
> 4. 仪表盘请求体含 `submitSource`（对齐下方「可按 `submit_source` 下钻」，`api-spec.md` §6.2 原字段清单漏写）。

- 统计口径**默认含外部单**（对齐 §8.6），可按 `submit_source` 与 `product_line` 下钻
- 驳回重提的需求：审批耗时**按轮次分开统计**，端到端周期**取首次 `submit_at` 起算**（不因重提而重置，否则会掩盖来回返工成本）
- 与审批链配置页「区块三 · 审批统计」的分工：后者看**单一归属**的受理量/通过率/驳回率，SLA 仪表盘看**跳归属的时效横向对比与趋势**，指标不重复定义

### 10.7 催办去重

> **实现落地差异（2026-08-19，已随代码实现确认）**：
> 1. 🚨 **去重键增加 `approval_round` 段**：`{event_type}_{requirement_id}_{approval_round}_{approval_level}_{remind_window}`。原文推论「驳回重提同理（去重计数自然重算）」**不成立** —— 重提后 `approval_round` 虽 +1，但节点停留时长归零，`remind_window = floor(0 / 24) = 0` 也一并归零，而 `approval_level` 又回到 L1，新一轮前几个窗口的键会与上一轮已落库的键**逐字相同**，导致新一轮催办被永久去重跳过。补 `approval_round` 段后轮次间天然隔离。
> 2. 🚨 **静默时段绝不写 `SLA_REMINDED` / `SLA_ESCALATED`**：静默时段（`22:00–08:00`，见 `job-schedule.md` §3.2）命中催办 / 升级条件时，只写**新增事件类型 `SLA_DEFERRED`**，且 `dedupe_key` **传 null、不参与去重**；静默结束后那一轮按正常流程重新判定并发送。原文「静默期先写事件流水、失败也占用去重窗口」与「积压至 08:00 合并发送」两条**互斥** —— 若静默期写了去重键，`08:00` 那轮必被去重跳过，催办将**永久发不出去**。
> 3. **手动催办不受静默时段限制**（见 §10.5），只受本节去重窗口约束。

- 同一需求同一级次在一个催办窗口内（`remind_window_hours`，默认 **24h**）**仅发送一次**催办，避免逐小时骚扰审批人
- 去重键：~~`{event_type}_{requirement_id}_{approval_level}_{remind_window}`~~ → **落地为 `{event_type}_{requirement_id}_{approval_round}_{approval_level}_{remind_window}`**，其中 `remind_window` = `floor(停留小时数 / remind_window_hours)`，落 `requirement_event_log.dedupe_key`
- 升级消息（`SLA_ESCALATED`）**独立去重**，不与催办共用窗口计数；同一节点升级同样按 24h 窗口去重
- 级次变更（通过进入下一级）后去重计数**自然重算**（`approval_level` 已变）；~~驳回重提同理~~ → **驳回重提靠新增的 `approval_round` 段隔离**（原推论有缺陷，见上方落地差异 1）
- 企微推送失败不重试不回滚，写 `NOTIFY_FAILED` 审计；**失败也占用去重窗口**（否则企微持续异常时会在恢复后瞄击式重发）
  - ⚠️ 此条**仅适用于真实尝试推送的场景**；静默时段属于「根本没尝试推送」，按上方落地差异 2 只写 `SLA_DEFERRED`，**不占用去重窗口**

### 10.8 SLA Job

- **每小时整点**执行一次扫描（cron `0 0 * * * ?`），检查全部审批中需求（`BU_REVIEWING` / `IMPL_REVIEWING` / `PM_REVIEWING`）当前节点的停留时长，对比 SLA 配置触发催办 / 升级
- 同一次扫描一并处理 §10.4 目标日期预警，不另起 Job
- 单机执行、并发度 1；幂等依赖 §10.7 去重键，**重复执行不会重发**
- 触发策略、执行流程、幂等与双跑红线的完整定义见 `job-schedule.md` §3
- 🚨 **Job 不做业务判定外的任何写入**：不改需求状态、不改审批级次、不自动通过也不自动驳回（时效治理只推人，不代人做决策）；小时级扫描意味着**催办最大延迟 1 小时**，属可接受误差

## 11. AI 方案确认（PM 节点 AI 辅助）

解决「方案确认集中在产品经理个人、吞吐受限」的瓶颈：需求进入**产品确认节点（L3）**后，系统为已开启开关的产品经理自动执行方案分析，产出方案草稿、三段式确认摘要与信息缺口清单；产品经理人工确认后系统代为执行通过动作。AI 只做预填与建议，**审批决策权始终在 PM 本人**——与 §10.8「Job 不代人做决策」同一治理哲学。

### 11.1 定位与红线

- AI 产出 = 方案草稿 + 确认摘要 + 信息缺口清单，是审批人的**决策辅助材料**，不构成审批动作本身
- 🚨 **红线一（触达隔离）**：任何 AI 生成内容（方案草稿、补材请求文案、驳回理由草稿）在 PM 人工确认发出前**不得触达提交人**——不发通知、不在提交人可见区域渲染。AI 幻觉直接触达业务方的事故成本远高于多一次人工点击
- 🚨 **红线二（不自动审批）**：系统不自动通过 / 不自动驳回。通过动作必须由 PM 点击「确认并通过」触发，系统仅代为执行：审批流水 `action=APPROVE`、操作人 = PM 本人、审批意见带「【AI方案确认】」前缀（与既有「【AI自动审批】」意见形态对齐）并引用 `ai_plan_id`，审计上可区分「AI 辅助确认」与「纯人工审批」
- 🚨 **红线三（不阻塞人工通道）**：AI 生成中 / 失败 / 任何异常状态下，PM 与其他或签审批人均可照常人工通过 / 驳回，AI 结果自动作废保留只读参考（§11.4）

### 11.2 触发条件

- **触发点**：需求状态进入 `PM_REVIEWING`（L3 产品确认）**且**当前级次审批人快照集合中存在**开启 AI 辅助开关**的产品经理。链上未配置 L3 级次的（专属链为 `{1,2}` 等子集）无方案确认语义，不触发
- 「提交对象是某 PM」**不等于**触发——前置级次（L1/L2）流转期间不触发；或签集合中仅未开启开关的审批人也不触发
- 开关为 **per-PM 配置**（§11.8），按 `pm_user_id` 维度生效，**禁止把具体人员写进代码 / 配置中心常量**
- 每个 `(requirement_id, approval_round)` 自动触发**至多一次**；驳回重提进入新一轮后可再次自动触发；同轮内 PM 可手动「重新生成」（§11.6），版本递增
- 外部提交单同样适用：以默认链 L3 审批人集合中开启开关者为准（§3.4）
- 触发后写 `requirement_ai_plan` 记录（`status=GENERATING`，`trigger_type=AUTO`），数据模型见 `data-model.md` §9

### 11.3 固定分析框架（七步）

「尽可能全面」落成固定清单，每次执行逐项过，保证输出质量不漂移：

| 步骤 | 分析项 | 产出要求 |
|------|--------|---------|
| 1 | 业务诉求还原 | 一句话诉求 + 业务背景 / 痛点 / 期望效果，与提交人原文分离（AI 复述，便于 PM 校对理解偏差） |
| 2 | 存量能力排重 | 对照全模块索引排查是否已有同类 / 可复用模块，命中时给出模块名与差异点，防止重复建设 |
| 3 | 数据源与接口可行性 | 通过 AI 助手 Tool 注册表（业务查询 Tool）**实查验证**关键数据是否可得；查不到的如实标注「未验证」，禁止编造接口结论 |
| 4 | 端型与权限影响 | 涉及端（Web / App / H5）、新增权限点、数据可见范围变化 |
| 5 | 状态机与通知影响 | 对现有单据状态机 / 审批链 / 企微通知的侵入面 |
| 6 | 模块归属与工作量粗估 | 建议归属模块（含新建 vs 并入既有模块判断）与量级粗估（仅分档，不排期） |
| 7 | 信息缺口清单 | 「若业务补充 X，本方案可在 Y 方面更完善」的逐条清单——这是补材请求（§11.6）的预填来源 |

- 执行身份：以开启开关的 PM 本人身份执行数据查询，Tool 权限沿用其 RBAC；查不到的数据在方案中标注「未验证」，**不越权、不借用系统账号**
- 执行过程（模型标识 + Tool 调用轨迹）全量落 `requirement_ai_plan.tool_trace`，供审计回放

### 11.4 执行期间的并发与作废

- 生成期间详情页对**当前级次审批人**展示「AI 方案生成中」标记（提交人不可见，对齐红线一）
- **或签先批作废**：任一级次审批人在 AI 完成前人工通过 / 驳回，进行中的任务置 `OBSOLETED`；已完成的方案保留只读参考，不可再用于「确认并通过」（需求已流转，确认入口随状态关闭）
- **PM 人工直批作废**：PM 不看 AI 结果直接人工通过 / 驳回，同样置 `OBSOLETED`，方案仅留痕
- 需求被撤回 / 删除 / 审批链重建时，在途任务一并 `OBSOLETED`
- **SLA 计时不豁免**：AI 执行为分钟级，远小于催办阈值（默认 24h 起），停留时长照常累计，不设特例（§10.1）

### 11.5 确认摘要与确认并通过

- AI 完成后向该 PM 发企微个人消息（`bizKey=REQUIREMENT.AI_PLAN_READY`，含详情页跳转链接）；**企微消息是单向通知，确认动作必须回到 Web / App 详情页完成**（企微交互按钮回调通道本期不建）
- 详情页「AI 方案」面板展示**三段式确认摘要**（自然语言）：① 业务诉求是什么 ② 本次方案完成了什么 ③ 信息缺口与建议业务补充的内容；方案全文可展开
- PM 点击「确认并通过」：审批意见由 AI 预填（可编辑），提交后系统以 PM 身份执行 L3 通过，意见自动带「【AI方案确认】」前缀；需求按 §2.3 流转，`requirement_ai_plan.status=CONFIRMED`
- 前置校验与人工通过完全一致（§4.2 当前级次审批人校验、§7 幂等）：方案状态非 `READY`、需求已流转、或签已被他人处理时，确认接口返回当前状态而非报错

### 11.6 请求补充材料（第三动作）

现有流程只有「通过 / 驳回」两个动作，追加附件是提交人自发行为（§9.4）。AI 检出信息缺口时缺一个承接动作，故新增：

- AI 判定信息不足时在 `gap_items` 产出补材清单，PM 可编辑后点「**请求补充材料**」
- **PM 确认发出后**才触达提交人（红线一）：企微个人消息通知提交人（`bizKey=REQUIREMENT.MATERIAL_REQUESTED`，文案为 PM 确认后的终稿）+ 详情页对提交人展示补材清单
- 请求补材**不新增需求状态、不改变级次、不重置 SLA 停留计时**（状态保持 `PM_REVIEWING`；不得以补材刷新计时规避催办，口径同 §9.4 追加附件）
- 提交人通过既有「审批中追加附件」（§9.4）与补充说明响应；PM 可在面板「**重新生成方案**」（`trigger_type=MANUAL`，`plan_version` 递增），形成「补材 → 再分析 → 确认」闭环
- 同轮内重新生成与补材请求不设硬次数上限，全量版本留痕；连续多轮补材仍不足时由 PM 人工驳回（驳回理由可由 AI 预填，同样经 PM 确认才发出）

### 11.7 幂等与失败处理

- 任务唯一约束：`(requirement_id, approval_round)` 内 `trigger_type=AUTO` 仅一条；`MANUAL` 按 `plan_version` 递增；唯一性由 Service 层「先查后写 + 行锁」保证，不建 `UNIQUE KEY`（对齐项目软删红线）
- AI 执行失败（模型超时 / Tool 异常 / 配额耗尽）置 `FAILED` 并写事件审计，企微通知 PM「AI 方案生成失败，请人工审批或重试」——**失败只通知 PM，不通知提交人**
- 失败**不自动重试**（避免模型故障期打爆配额），由 PM 在面板手动「重新生成」
- 确认接口幂等：PM 连点 / 重复提交返回当前状态，不重复执行通过动作（对齐 §7 审批接口幂等）

### 11.8 配置：per-PM 开关

- 开关落 `requirement_approval_config.ai_assist_enabled`（`data-model.md` §4）：管理员在「审批链配置」页**先选提交对象（PM）再勾选「AI 辅助方案确认」**，对该 PM 全部专属链行批量置位
- 生效口径：该 PM 存在任一 `status=1` 专属链行且 `ai_assist_enabled=1` 即视为开启；默认链行该列恒为 0（外部单以 L3 配置审批人自己的专属链开关为准，不继承默认链）
- 开关变更**立即生效**（同 SLA 配置，不做快照）：仅影响变更后进入 `PM_REVIEWING` 的需求，在途生成中任务不受影响

### 11.9 审计与统计

- 事件类型新增（落 `requirement_event_log`）：`AI_PLAN_GENERATING` / `AI_PLAN_READY` / `AI_PLAN_FAILED` / `AI_PLAN_CONFIRMED` / `AI_PLAN_OBSOLETED` / `MATERIAL_REQUESTED`
- 审批流水与意见前缀「【AI方案确认】」为「AI 辅助确认」的识别口径，统计时可与纯人工审批区分
- 本期先落事件留痕；AI 辅助率、确认采纳率、补材请求率等指标后续再入 SLA 仪表盘（§10.6），不阻塞上线

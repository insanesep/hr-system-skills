一、这次要做什么（大白话）

需求工单审批全部通过后，产品经理要把它关联到一张「功能排期卡片」上，研发按卡片排期开发。目前按编号搜索时，一张卡片只要被别的需求挂过，就直接报错不让挂——但现实中经常有几条需求说的是同一件事（同类需求），本来就该挂到同一张卡片上。

本次改动三件事：

  1. 一张排期卡片允许挂多条需求，关联弹窗的两种方式（按编号搜索 / 从候选卡片中选择）都不再拦截；
  2. 已被挂过的卡片带上明显标识「已关联 N 条需求」，鼠标放上去能看到这些需求都是谁提的；
  3. 选中这种已挂过的卡片时，多弹一句确认「该卡片已承载 N 条需求，确认将本需求同挂到该卡片？」，防止手滑挂错。
改动后按编号搜索到已挂过的卡片，长这样：
FS-20261008-072已关联 2 条需求
排期日期 2026-10-15 ｜ 开发中 ｜ 开发人：王工 ｜ （悬停标识可见提交人：李儒洲、张琪）

补充说明：按编号搜索时报的「已被其他需求关联」，其实与 2026-09-16 已定稿的产品规格不符——规格早就明确「一张卡片允许被多条需求关联、不做去重拦截」，候选列表方式也已按规格做出标识和确认。本次是把按编号搜索这条漏网之路一并纠正、补齐标识。

二、请业务拍板的 3 个问题

Q1 按「卡片编号」搜索到一张已被挂过的卡片，怎么处理？
A. 放行：照常显示卡片信息 + 「已关联 N 条需求」标识（悬停可见提交人名单），点确认关联时多问一句「确认同挂？」——与「从候选卡片中选择」方式完全同款体验推荐
B. 维持现状直接报错、不允许挂——想同挂只能改用候选列表方式（两种方式体验不一致，不推荐）
Q2 搜索到的卡片是「非需求改动旁路卡」或已删除的卡片，怎么提示？
候选列表方式本来就不展示这两类卡（旁路卡不是业务需求，不该被需求挂）。
A. 提示「卡片不存在、已删除或为非需求改动旁路卡，不可关联」——与候选列表的口径对齐推荐
B. 维持现有「卡片不存在或已删除」文案不变——旁路卡搜出来也能挂（两种方式口径不一，不推荐）
Q3 功能排期卡片那边，要不要反向显示「这张卡已关联 N 条需求」？
A. 不做：排期卡片侧维持现状不展示——卡片与需求是单向关联，本次改动最小推荐
B. 做：功能排期卡片详情/列表也展示已关联的需求清单（需改动功能排期模块，工作量增加）

三、这几件不用拍板，按系统既有规则定（告知）

事项定法
一条需求能挂几张卡仍只能关联一张卡片（不变）；想换卡先解除关联再重新关联
解除关联的影响只影响当前这条需求（状态退回「待关联排期」），同卡的其他需求不受影响
卡片被删除后挂着它的每条需求各自在详情页看到黄色提示「关联卡片已失效，请重新关联」，重新关联即可（现状已如此）
状态流转与通知需求状态机、企微群通知、SLA 统计口径全部不变
涉及端仅 Web 端关联排期弹窗；App 端需求工单本来就只读展示，不动
权限与表结构不新增权限点（沿用「关联排期」按钮权限），不改数据表结构

四、上线前怎么验收

  • 按编号搜索一张已被挂过的卡片 → 不再报错，显示「已关联 N 条需求」标识，确认同挂后关联成功；
  • 从候选列表选一张已挂过的卡片 → 同样有标识、确认后成功（现状规格回归验证）；
  • 同一张卡片挂 2 条需求后，两条需求的详情页都能看到这张卡片；
  • 按编号搜索旁路卡 / 已删除卡 → 提示「不可关联」；
  • 解除其中一条需求的关联 → 另一条需求不受影响。

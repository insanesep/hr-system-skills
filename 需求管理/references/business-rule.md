# 需求管理 · 业务规则

> 本模块通用业务规则真源：流程总览、产品线与角色、缺陷修复分流、审批链配置、通知推送、排期关联与下游承接、操作概要。状态流转见 [state-machine.md](state-machine.md)，权限见 [permission-rules.md](permission-rules.md)，字段定义见 [data.md](data.md)；外链邀约、附件、审批时效与 SLA、AI 方案确认、流程中心接入各有专题文件，入口见 [SKILL.md](../SKILL.md) Prerequisites。数据模型、接口契约与定时任务配置等实现细节以代码仓为准。

## 1. 业务流程总览

需求从提出到进入研发排期共 5 步，前 3 步在本模块内闭环，第 4 步交接产品经理，第 5 步由 [功能排期](../../研发管理/功能排期管理/SKILL.md) 承接。内部提交先选定提交对象（产品经理），按其专属审批链流转（级次由配置决定，1~3 级）；外部提交无提交对象，固定走默认链，匹配规则见 §3。

| 步骤 | 名称 | 执行角色 | 产出 |
|------|------|---------|------|
| 1 | 需求提交 | 业务线员工（内部，先选定提交对象）/ 外部人员（凭外链，无提交对象） | 生成需求单，编号 `REQ-{YYYYMMDD}-{NNN}`，进入审批链第一级待审 |
| 2 | 前置审批 | 链上前置级次审批人（L1 业务线审批 / L2 实施确认；未配置的级次直接跳过） | 判定需求合理性、实施可行性并归集同类需求，通过则流转链上下一级，驳回则回提交人 |
| 3 | 产品确认 | 提交对象（产品经理，L3；外部单为默认链 L3 配置的产品经理） | 终审需求价值与方案，通过则需求进入待关联排期 |
| 4 | 产品提交 | 提交对象（产品经理） | 完成需求打磨并关联排期卡片，需求进入已关联排期终态 |
| 5 | 研发开发 | 研发 | 在功能排期中领取卡片开发，状态回传需求详情页 |

- **缺陷分流**：需求类型为缺陷修复的单据是人工报 bug 的唯一入口，前 3 步审批不变（确认缺陷真伪、责任归属与修复价值），全部审批通过后不走步骤 4、5，自动分流至黑灯工厂，见 §2
- **下游承接**：功能类需求关联排期卡片后，系统按「需求 + 卡片」生成 Qoder 开发会话承接实施，见 §5.2；缺陷单由黑灯工厂承接，不生成开发会话

### 1.1 产品线与业务线

**产品线**为需求的第一层归属维度，固定 2 值，新增需 DBA 与管理员同步维护审批链配置。

| 编码 | 名称 | 业务线取值 | 提交方式 |
|------|------|-----------|---------|
| `SNACK` | 鸣鸣很忙 | 必选 `OPS` / `FIN` / `SCM` / `DIGITAL` 之一 | 仅内部登录用户（Web / App） |
| `YDTJ` | 有点推荐 | 不区分业务线 | 内部登录用户 + 外部人员凭外链免登录 |

**业务线**仅在鸣鸣很忙产品线下生效，固定 4 条，不支持自定义扩展（新增需 DBA 与管理员同步维护审批链配置与企微群映射）。

| 编码 | 名称 | 说明 |
|------|------|------|
| `OPS` | 运营 | 门店营运、店务执行、任务协同相关需求 |
| `FIN` | 财务 | 结算、凭证、对账、税务相关需求 |
| `SCM` | 供应链 | 采购、配送、仓储、库存相关需求 |
| `DIGITAL` | 数字化 | 数据报表、系统集成、硬件与基础能力相关需求 |

- 有点推荐的业务线由系统统一记为「不区分」，不向用户展示也不可选，**不得为它新增业务线枚举值**

### 1.2 角色定义

| 角色 | 职责说明 |
|------|---------|
| 业务线员工 | 需求提出方，负责描述业务背景、痛点与期望效果；可撤回与修改草稿 |
| 外部提交人 | 非系统用户（外部伙伴 / 兼职人员等），凭内部人发放的一次性定向外链提交有点推荐需求；无账号、无草稿、无撤回、不可查进度 |
| 邀约人 | 生成外链的内部用户，对所发放链接产生的需求负溯源责任；可撤销自己生成的链接 |
| 业务线负责人 | 各业务线一名（4 条业务线各自独立），L1 审批人，把关本业务线需求的必要性与优先级 |
| 实施负责人 | 全公司统一入口，L2 审批人（默认链与配置了该级的专属链），负责需求归集、去重与可行性判断 |
| 产品经理 | **提交对象**：内部需求提交时由提交人必选；链上末级（L3 产品确认）审批人，负责需求打磨、方案确认与排期卡片关联；外部单由默认链 L3 配置的产品经理承接 |
| 研发 | 不参与审批，在功能排期侧领取卡片并推进开发状态 |

### 1.3 流程约束

- 需求必须归属唯一产品线，且归属唯一业务线（有点推荐不区分业务线），提交后两者均不可修改，驳回重提时同样只读；如需变更须新建需求
- **内部提交必须选定提交对象（产品经理）**，提交对象随提交记录并作为排期关联责任人；草稿与驳回重提时可更换提交对象，更换后按新对象重新匹配审批链并生成新快照
- 同一提交人对同一业务线可并行提交多条需求，无数量限制
- 优先级由提交人初填，各级审批人在审批通过时可调整，需求最终优先级以末级审批通过时的值为准；外部单优先级的入库口径见 [other-rule-public-link.md §3](../需求外链管理/references/other-rule-public-link.md#3-外部提交字段边界)
- 需求从提交到已关联排期全链路留痕，任意状态变更写入审批流水与事件审计（撤回例外，见 [state-machine.md §5](state-machine.md#5-撤回)）
- **外部提交单直接走默认审批链第一级待审**，不设待受理初筛池（链接为内部人定向发放，来源天然可信）；外部人无登录态不可选提交对象，固定走默认链（§3.2）；仅有点推荐产品线开放外链提交

## 2. 缺陷修复需求分流

需求类型为缺陷修复（`BUGFIX`）的单据是**人工发现 bug 的唯一入口**（内部 Web / App 与外部 H5 均可提交）；黑灯工厂工单不提供手工新建，人工报障一律经本模块审批后分流。建单口径与工单状态以 [黑灯工厂管理](../../运维管理/黑灯工厂工单/SKILL.md) 为准。

- **提交与审批**：表单字段、审批链匹配（§3）、状态流转（[state-machine.md](state-machine.md)）与非缺陷需求完全一致；审批人职责为确认缺陷真伪、责任归属与修复价值
- **自动分流**：末级审批通过（待关联排期）后，系统**自动**调用黑灯工厂建单能力生成工单；缺陷单不开放「关联排期卡片」入口，缺陷修复不占用功能排期
  - 工单幂等键：需求编号（一单一号；驳回重提沿用原编号故不重复建单，重提再次通过后向原未关闭工单追加证据）
  - 工单分类：待判断（`PENDING_JUDGE`）；级别按需求优先级映射（`P0` / `P1` → `P1`、`P2` / `P3` → `P2`）；负责人由黑灯工厂侧按代码归属判定，判不出则待认领
  - 建单失败不阻塞审批结果：失败写事件审计并告警，按幂等键重发安全
- **终态与回传**：建单成功后需求状态置为已关联排期（终态），关联对象为黑灯工厂工单（记关联工单号，不占关联卡片编号）；工单级别、状态、负责人与处理进展在需求详情页**只读回传**（与排期卡片状态同区展示），本模块不回写工单任何字段（单向关联口径同 §5）
- **结果通知**：工单关闭（已解决 / 已忽略）时按 §4.1 个人消息推送提交人与产品经理；忽略类关闭（噪声 / 口径如此 / 三方问题）文案须带关闭原因

## 3. 审批链配置规则

> **驱动模式**：审批链由**提交对象（产品经理）**驱动——提交需求与配置审批链时都**先选定产品经理，再根据其设定审批流程**；「产品线 × 业务线 × 需求类型 × 优先级」四维配置为**默认链**，承接外部提交，鸣鸣很忙默认链作防御性兜底。

### 3.1 条件维度

审批链按 **提交对象 →（产品线 × 业务线 × 需求类型 × 优先级）** 匹配，「提交对象」为第一优先维度。

| 维度 | 取值 | 是否支持降级 |
|------|------|-------------|
| 提交对象 | 具体产品经理；未指定产品经理的配置即**默认链** | 不支持通配，必须等值命中 |
| 产品线 | 见 §1.1 | 不支持，必须等值命中 |
| 业务线 | 见 §1.1（有点推荐不区分） | 不支持，必须等值命中 |
| 需求类型 | 见 [data.md §12](data.md#12-枚举) | 支持通配 |
| 优先级 | `P0` / `P1` / `P2` / `P3` | 支持通配 |

四维降级顺序（在确定提交对象维度后执行）：四维全等值 → 优先级通配 → 需求类型通配 → 需求类型与优先级均通配，命中即止。

### 3.2 专属链与默认链

| 链类型 | 配置特征 | 级次要求 | 承接场景 |
|--------|---------|---------|---------|
| **PM 专属链** | 指定了产品经理 | L1 / L2 / L3 的任意**非空子集**（如仅 L3 产品确认、L2+L3、完整三级） | 内部提交（唯一通道） |
| **默认链** | 未指定产品经理（四维配置） | 有点推荐须配齐 **L1 / L2 / L3** 三级（L3 承接外部提交，见 §3.4）；鸣鸣很忙各业务线配 L1 / L2 作防御性兜底 | ① 外部提交（无提交对象，唯一通道）；② 鸣鸣很忙默认链为防御性兜底，内部单必中专属链，正常不命中 |

- 级次语义固定：`1` 业务线审批、`2` 实施确认、`3` 产品确认；专属链未配置某级即流转时跳过该级
- 配置页操作范式：**先选提交对象（产品经理），再配置其审批流程**（级次勾选 + 各级审批人）；选「默认链」则维护四维配置
- 专属链可按四维再细化（同一产品经理下不同类型 / 优先级走不同级次组合）；不细化即通配
- 默认链 L3 配置的产品经理**仅承接外部提交单**；鸣鸣很忙默认链无需配置 L3，有点推荐默认链必须配齐 L3（缺级时外链生成与外部提交均被拒）
- **提交对象候选集（配置驱动）**：提交页的提交对象候选按「产品线 × 业务线」过滤，**仅包含在该归属下配有启用中专属链的产品经理**（去重，且须为在职有效的系统用户）；内部提交因此必中专属链，默认链不承接内部单。🚨 **配置页的「指定产品经理」选择器不使用该候选集**，走全员人员搜索，否则没配过链的新产品经理永远无法被配置（循环依赖）

### 3.3 各归属默认链

每个「产品线 + 业务线」组合独立配置默认链，差异集中在 L1（负责人不同）；L2 实施负责人为全公司统一入口。

| 产品线 | 业务线 | L1 | L2（实施负责人） | L3（产品经理） |
|--------|--------|----|------------------|----------------|
| 鸣鸣很忙 | 运营 | 运营负责人 | 实施负责人 | 无需配置（内部单全走专属链，默认链仅防御兜底） |
| 鸣鸣很忙 | 财务 | 财务负责人 | 实施负责人 | 无需配置（同上） |
| 鸣鸣很忙 | 供应链 | 供应链负责人 | 实施负责人 | 无需配置（同上） |
| 鸣鸣很忙 | 数字化 | 数字化负责人 | 实施负责人 | 无需配置（同上） |
| 有点推荐 | 不区分 | 有点推荐负责人 | 实施负责人 | 默认承接**外部提交单**的产品经理 |

- 有点推荐默认链只需配一套；内部提交走 PM 专属链，默认链仅承接外部提交

### 3.4 匹配顺序

**内部提交**（提交对象为 P，必选）：

1. **匹配 PM 专属链**：在提交对象为 P 的专属链中按 §3.1 四维降级命中即止，快照级次为专属链配置的级次集合，最大级次为链上最大级次
2. **未命中专属链即提交失败**：候选集仅含本归属有专属链的产品经理（§3.2），正常选人必中专属链；仅当专属链在选人后被停用或删除时才可能未命中，此时提示「当前归属未配置审批链，请联系管理员」，内部单不落默认链

**外部提交**（无提交对象）：按 §3.1 四维降级匹配默认链，L3 取默认链配置的产品经理（或签）；L3 审批通过时将实际通过人记为该需求的产品经理。**未命中配置时不得暴露内部配置信息**：向外部人统一提示「提交暂时不可用，请联系邀约人」，同时向邀约人推送企微告警，见 [other-rule-public-link.md §5](../需求外链管理/references/other-rule-public-link.md#5-单向收口)。

### 3.5 或签模式

- 各级审批均为**或签**：同一级次配置多名审批人时，任一人通过即视为该级通过，其余人待办自动关闭
- 任一人驳回即整单驳回，不等待其他审批人
- 或签的待办聚合与关闭逻辑参考任务中心（文档尚未迁入），本模块不引入全员确认（多签）模式

### 3.6 快照机制

- 提交（含驳回重提）时按 §3.4 匹配，将链上各级审批人写入审批链快照；专属链仅写入其配置的级次（未配置的级次不产生快照）
- 流转过程中只读快照，不再回查配置：配置变更不影响在途需求，避免中途换人导致审批断链
- 审批人离职或调岗时，管理员需更新配置并对在途需求执行「审批链重建」：按需求的提交对象重新走 §3.4 匹配（内部单仅匹配专属链；适用于自研通道单，流程中心通道单按 [other-rule-flow-center.md §5](other-rule-flow-center.md#5-平台语义差异处置) 第 8 条处置），旧快照作废，审批轮次与级次集合保持不变——**重建只替换审批人，不增减级次**，操作写入事件审计

## 4. 通知与企微推送

推送统一在业务事务提交后异步触发，禁止在事务内同步调用；能力复用公共企微消息能力（公共仓尚未迁入，见 SKILL.md Prerequisites）。审批超时催办、升级与目标日期预警见 [other-rule-sla.md](other-rule-sla.md)，审批中追加附件的通知见 [other-rule-attachment.md §4](other-rule-attachment.md#4-审批中追加附件)，AI 方案相关通知见 [other-rule-ai-plan.md](other-rule-ai-plan.md)；流程中心通道单的个人待办与结果通知由流程中心承担，见 [other-rule-flow-center.md §4](other-rule-flow-center.md#4-对接规则)。

### 4.1 双通道推送

- **个人消息**：推送给下一级审批人（待办提醒）或提交人（结果通知），带需求详情页跳转链接；**外部单的「提交人结果通知」改推邀约人**（外部人无企微身份且不回传）
- **业务群消息**：按需求所属产品线 / 业务线路由到对应企微群（运营群 / 财务群 / 供应链群 / 数字化群 / 有点推荐需求群），用于归属内信息同步

### 4.2 群消息推送规则

| 触发事件 | 推送目标群 | 消息内容 |
|---------|-----------|---------|
| 需求提交 | 所属业务线群 | 「{提交人} 提交了新需求：{标题}，优先级 {P0-P3}」；外部单为「{外部提交人}（外部，邀约人：{邀约人}）提交了新需求：{标题}」 |
| L1 审批通过 | 所属业务线群 | 「{需求标题} 已通过业务线审批，流转至实施负责人」 |
| L3 审批通过 | 所属业务线群 | 「{需求标题} 已通过全部审批，进入研发排期」；缺陷修复单为「{需求标题} 已通过全部审批，转黑灯工厂工单处理」 |
| 驳回 | 所属业务线群 | 「{需求标题} 被 {审批人} 驳回，原因：{意见摘要}」 |
| 关联排期 | 所属业务线群 | 「{需求标题} 已关联排期卡片 {卡片编号}，预计 {日期} 开发」 |

- 群消息以企微群机器人方式推送（复用报表群推送体系），产品线 / 业务线与群机器人的映射维护在审批链配置中；新增业务线须同步补齐，否则群消息静默失败（仅记录告警日志，不阻断主流程）
- 驳回意见摘要截取前 50 字，超出以 `…` 省略
- L2 审批通过不推群消息（内部流转节点），仅推个人消息给 L3 产品经理

### 4.3 推送去重与失败处理

- 同一需求同类消息在同一分钟内重复触发只推送一次，防止审批人连点导致重复推送
- 推送失败不回滚业务事务，失败记录写入事件审计供人工重推

## 5. 排期关联规则

- 🚫 **缺陷修复需求不适用本节**：审批通过后按 §2 自动分流黑灯工厂，无排期关联入口
- 关联入口在全部级次审批通过（待关联排期）后开放，仅该需求的产品经理（内部单为提交对象，外部单为 L3 实际通过人）与管理员可操作
- 关联方式二选一：输入卡片编号精确搜索，或从「候选排期卡片列表」中选择
- 关联结果记录卡片编号，需求状态置为已关联排期
- 卡片状态实时展示：详情页实时读取功能排期卡片，展示待开发（`PENDING`）/ 开发中（`IN_PROGRESS`）/ 开发完成（`DONE`）/ 待澄清（`CLARIFYING`）及排期日期，待澄清时排期为空；卡片完成澄清后成为合并卡的子卡，状态随合并卡展示，经卡片详情可到达合并卡；卡片状态口径以 [功能排期 state-machine.md](../../研发管理/功能排期管理/references/state-machine.md) 为准
- **单向关联**：本模块只读取排期卡片信息，不回写卡片任何字段；卡片被删除时需求详情页展示「关联卡片已失效」提示，需重新关联
- 一条需求只能关联一张卡片；一张卡片允许被多条需求关联（同一卡片承载多条同类需求）
- 关联可解除：解除后状态回退至待关联排期，关联卡片编号清空，写入事件审计

### 5.1 候选卡片列表

候选集为全部有效排期卡片（含已关联），支撑「同类需求同挂一张卡片」场景的卡片定位，并提供「开发人 / 需求提交人」双筛选维度。

- **候选集**：全部有效排期卡片（待开发 / 开发中 / 开发完成），**排除非需求改动卡（`NON_FEATURE`）与已删除卡**；含已被其他需求关联的卡片（规则上本就允许一卡多需求）
- **默认过滤**：按排期日所属月份（默认当月）；待排期池与待澄清的卡片（无排期日）不参与月份过滤、不入候选，可按卡片编号精确关联
- **展示字段**：卡片编号 / 标题 / 排期日期 / 开发状态 / 开发人 / 已关联需求数（已关联需求数大于 0 时展示「已关联 N 条需求」角标，附已关联需求的提交人名单）
- **筛选维度**（在月份之上叠加，均为人员选择器单选、可清空）：

| 筛选 | 匹配逻辑 | 空值口径 |
|------|---------|---------|
| 开发人 | 等值匹配卡片开发人（选择器选人后按姓名匹配） | 🚨 待开发卡尚无开发人（领取开发时才记录），**不参与该筛选**；筛选器旁常驻说明「仅已被领取开发 / 已完成的卡片有开发人」 |
| 需求提交人 | 反查命中：该卡片已被选中人提交的需求关联；在本模块内反查关联卡片编号集合后过滤候选，不触碰功能排期侧（单向关联红线不变） | 🚨 **仅内部提交单参与**（外部单无内部提交人、提交人姓名为自由文本，不参与筛选；其姓名仅在卡片「已关联名单」中正常展示） |

- **同挂确认**：选中「已关联 N 条需求」的卡片提交时，弹窗内二次确认「该卡片已承载 N 条需求（提交人：{名单}），确认将本需求同挂到该卡片？」；确认后按常规关联处理
- **排序**：排期日期升序（近期在前），同日期按卡片编号升序；已关联标识仅作展示、不影响排序

### 5.2 Qoder 开发会话

- 需求关联排期卡片成功（已关联排期）后，系统为该需求变更**生成 Qoder 开发会话**承接实施：服务端创建会话并挂载需求上下文（描述与附件、审批结论、关联卡片）与关联卡片所属项目的 harness 工程和代码仓清单；项目映射以功能排期的项目配置为唯一真源，见 [功能排期 business-rule.md §9](../../研发管理/功能排期管理/references/business-rule.md#9-项目归属与配置)
- 会话入口挂在需求详情页（排期关联区内），仅产品经理、管理员与卡片开发人可见；解除关联不回收已生成会话，重新关联时生成新会话并保留旧会话链接备查
- 缺陷修复需求不生成开发会话，其修复实施由黑灯工厂承接（§2）

## 6. 操作概要

| 操作 | 规则 |
|------|------|
| 提交需求 | 创建或提交需求；内部提交必须携带提交对象，按 §3.4 匹配并生成审批链快照；暂存草稿不生成快照 |
| 需求列表 | 分页查询，支持多维筛选与视角切换，筛选项与视角见 [web-ui.md 需求列表页](../需求工单管理/references/web-ui.md#需求列表页) |
| 需求详情 | 展示需求主体、审批链快照、审批流水与关联排期卡片（或黑灯工厂工单）实时状态 |
| 审批通过 | 按当前级次校验审批人，递进至链上下一已配置级次；可同时调整优先级（§1.3）；外部单 L3 通过时将实际通过人记为该需求的产品经理 |
| 驳回 | 校验审批人后置为已驳回，驳回意见必填且不少于 10 字 |
| 撤回 | 仅已提交 / 业务线审批中可撤回，回到草稿并作废快照 |
| 关联排期 | 记录关联卡片并置为已关联排期；支持解除关联回退至待关联排期 |

- 所有操作由服务端二次校验菜单权限与角色可见范围，不依赖前端按钮控制
- 导致状态、级次或关联关系变更的操作，成功后须写入审批流水与事件审计各一条（撤回只写事件审计）
- 审批类操作对同一需求同一级次做幂等控制：重复提交视为已处理，返回当前状态而非报错
- 外部提交与内部提交共用审批、详情、统计能力，仅**提交入口**分离，外部提交入口见 [other-rule-public-link.md §7](../需求外链管理/references/other-rule-public-link.md#7-外链操作)

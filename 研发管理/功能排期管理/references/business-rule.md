# 功能排期 · 业务规则

> 出卡、排期、统计、搜索筛选、待排期池、合并卡、项目归属与配色、非需求改动列表、需求澄清的规则真源。状态流转与守卫见 [state-machine.md](state-machine.md)，字段取值与校验见 [field-rules.md](field-rules.md)，权限见 [permission-rules.md](permission-rules.md)，实体字段见 [data.md](data.md)，页面元素见 [web-ui.md](web-ui.md)，MCP 工具见 [other-rule-mcp.md](other-rule-mcp.md)。

## 1. 出卡规则

### 1.1 自动出卡

- **采集源**：全部启用中项目的 harness 工程仓，只读引用[项目管理消费规则](../../项目管理/references/business-rule.md#consumption)，按稳定仓标识去重；无启用中项目时采集源为空，不产生新卡。
- 采集源仓的每个新 commit 只生成一张待开发卡片，进入待排期池；不按变更路径拆卡，项目归属见 §9，默认值见 field-rules.md §1–§4。

### 1.2 去重与删除

- 「源仓 + 源 commit」唯一，同一 commit 只出一张卡；源 commit 再次触发时返回既有卡片编号，并标识为非首次生成
- 删除为软删除：卡片不再出现在待排期池、各视图与非需求改动列表，写删除流水，源 commit 不会再次出卡
- 删除需二次确认；子卡不可删除（见 state-machine.md §4），删除合并卡按 §8.6 处理
- 删除待澄清卡片时，其澄清记录一并关闭，见 §11.4

### 1.3 手动新建

- 头部「新建卡片」：从采集源仓选仓 → 搜索或浏览 commit → 单选 → 确认建卡，新卡进入待排期池
- 所选 commit 已有卡片时不新增，提示后进入已有卡片的详情页
- 手动新建与自动出卡共用默认值与去重规则

## 2. 排期规则

### 2.1 拖拽

| 起点 | 终点 | 结果 | 流水 |
|------|------|------|------|
| 待排期池 | 日历格 | 排期 | 排期 |
| 日历格 | 另一日历格 | 改期 | 调整排期 |
| 日历格 | 待排期池 | 取消排期 | 取消排期 |
| 任意位置 | 跨月灰显格 | 拒绝 | — |

- 目标日期须满足 field-rules.md §5 的日期约束，早于今天时提示并拒绝；拖回原日期不产生变更
- 区间卡在月视图、周视图仅在排期截止日显示，不在区间覆盖的其他日期重复展示；拖拽区间卡时保持原时长
- 开发完成、待澄清、非需求改动与子卡不可拖拽，见 state-machine.md §4
- 卡片排到某日后又拖回待排期池，生成「排期」「取消排期」两条流水
- +N 日详情中的卡片拖出时，背景遮罩透明且不阻挡日历与待排期池；支持拖回待排期池或拖到可排期日期格，拖拽结束或取消后恢复遮罩，保留日详情与原有筛选

### 2.2 右键快捷改期

- 月历格、待排期池与 +N 日详情中的卡片支持右键菜单：查看详情 / 改期到今天 / 改期到明天 / 移回待排期 / 移入非需求改动 / 转待澄清
- 改期与移回待排期的可用条件与拖拽一致：持有编辑权限且卡片未被 state-machine.md §4 锁定；以服务端结果为准，失败时提示
- 转待澄清的可用条件：卡片为待开发或开发中、非子卡，且持有标记完成权限；选中后打开转待澄清弹窗，规则见 §11.1

### 2.3 详情页排期

- 卡片详情页提供调整排期（起止日期与时长「共 N 天」）与移回待排期；可选日期范围见 field-rules.md §5，锁定规则见 state-machine.md §4

### 2.4 排期写入校验

- 业务对接人为选填，不参与排期写入校验，字段规则见 field-rules.md §7
- 排期日与起止日的联动见 field-rules.md §5

## 3. 发版日

- 点击日历空白处（非卡片、非「+N」、非跨月灰显格）发起切换当日发版日标记，需二次确认：未标记时确认后新增，已标记时确认后取消；取消确认不改变标记
- 同一日期至多一条有效标记
- 发版日仅作视觉标记，不参与卡片状态与延期判定

## 4. 统计口径

- **统计项**：待排期 / 待开发 / 开发中 / 已完成 / 延期，均取真实数据
- **待排期**：当前筛选条件下待排期池的卡片总数，与池当前页码、每页条数无关
- **待开发、开发中、已完成、延期**：当前视图所在月份内已排期的卡片；延期按 state-machine.md §3 判定，延期卡只计入「延期」，不再计入待开发或开发中；非需求改动与待澄清不计入
- **待澄清**：全量待澄清卡数（不含子卡），作为指挥栏「待澄清」入口的计数，不属于本月进度，不随视图月份、筛选、搜索与只看自己变化
- **随筛选变化**：开启「只看自己」时只统计本人卡片；应用项目筛选时按项目归属统计；状态、负责人、skills 仓库、模块筛选与搜索不改变统计数字
- 待排期以外的统计项可点击作为状态快捷筛选，再点取消

## 5. 搜索规则

- **范围**：当前视图所在月份的已排期卡片与待排期池卡片；子卡不在视图中，不单独参与搜索
- **执行**：月历、周视图在已载入的当月经筛卡片中本地匹配；待排期池把关键字并入服务端分页查询，跨池内全部卡片匹配，命中总数随分页结果返回
- **匹配**：输入按英文逗号、中文逗号或空格拆分为多个关键字，关键字之间为 AND；对标题、内容（合并卡含系统合成的子卡清单）、编号、提交人做模糊匹配，大小写不敏感
- **结果**：日历格中命中卡片高亮、未命中卡片淡化；待排期池只展示命中卡片，回到第 1 页，无命中时展示池空态
- 待排期池关键字变化后回到第 1 页；切月后关键字保留；按 Esc 清空；搜索与筛选相互独立，清空筛选不清除搜索词
- 搜索词为页面临时状态，不落库、不写入页面地址，刷新或关闭页签后重置；从卡片详情页返回工作台时保留进入前的关键字与池页码
- 「更多 → 非需求改动」列表与待澄清列表不参与搜索，搜索词不影响这两个列表

## 6. 筛选规则

### 6.1 通用

- **维度**：只看自己、状态、负责人、skills 仓库、项目、模块
- **状态选项**：待开发、开发中、开发完成与前端派生的延期；不含待澄清与非需求改动，二者不进月历与待排期池，分别在待澄清列表与非需求改动列表呈现
- **筛选(N)**：N 为偏离默认值的条件数；skills 仓库非全选、项目非全选、状态、负责人、模块各计 1，只看自己开启计 1；搜索词与「全部」默认值不计入
- **草稿与应用**：复选组修改只写入草稿，「确定」后才应用并刷新视图；「取消」、关闭或 Esc 放弃草稿；「重置」立即清空全部筛选并生效，抽屉保持打开，搜索词不受影响；只看自己即时生效
- **分页联动**：筛选、搜索或只看自己变化后，待排期池回到第 1 页；若处于多选态，退出多选态并清空已选
- **生效范围**：月历格、待排期池与 +N 日详情；状态、负责人、模块同样作用于待排期池，由服务端过滤并分页，池总数与统计同口径；选中「延期」状态时不命中待排期池卡片
- 筛选或搜索生效且视图零命中时，提示「当前筛选/搜索条件下暂无任务」，并提供清空筛选、清除搜索
- 筛选为页面临时状态，不落库，刷新后恢复默认；从卡片详情页返回工作台时保留进入前的筛选

### 6.2 只看自己

- 默认关闭；开启后只显示负责人、开发人或创建人为当前用户的卡片；合并卡按合并卡自身的负责人判断，不看子卡
- 作用于月历格、待排期池与 +N 日详情；非需求改动列表不受影响
- 月历格中非本人卡片不显示，日期格保留；待排期池不显示非本人卡片；全空时池内提示「没有由你提交的卡片 / 关闭『只看自己』可查看全部」
- 可切月查看历史各月本人卡片及其领取、完成状态

### 6.3 skills 仓库

- 选项为「全部」与 §1.1 所述采集源仓；默认全选，等价不过滤
- 按卡片源仓过滤，由服务端执行：全选或全不选视为全部展示，仅选中严格子集时按仓过滤；可与只看自己叠加
- 合并卡无源仓，按子卡源仓判定：任一子卡源仓命中勾选范围即保留

### 6.4 项目

- 选项为「全部」、[项目真源](../../项目管理/references/business-rule.md#source)中的各启用中项目与「未归属项目」；默认全选，等价不过滤；停用项目即时退出选项，其卡片按 §9 回落到未归属项目。
- 按 §9 计算卡片当前所属项目后筛选，不读取变更路径或目录层级；每张卡片至多归属一个项目。
- 与 skills 仓库、状态、负责人、模块条件取交集；作用于月历、待排期池与统计，总数按卡片编号去重。
- 合并卡只有全部子卡同属一个启用中项目时才命中该项目；跨项目、含未归属子卡或无子卡时只命中「未归属项目」，不能因任一子卡命中项目而保留合并卡。

### 6.5 负责人

- 选项为当前卡片集合中负责人与开发人的并集；卡片负责人、开发人或创建人任一命中勾选即保留。账号匹配沿用公共系统用户规则，创建人未匹配账号时仅按负责人或开发人命中；同名无法唯一匹配时保留原作者，不取首人或用项目配置覆盖作者。
- 显示与报告人员映射引用[项目成员身份](../../项目管理/references/business-rule.md#identity)。新分配的账号候选仍为公共有效系统用户，领取沿用当前系统用户与本模块权限，不要求预先进入项目成员名单；成员退出统计范围不删除已有卡片和流水。
- 作用于月历格、待排期池与 +N 日详情；不改变统计数字。

## 7. 待排期池

- 收纳未排期、非非需求改动、非待澄清、非子卡的卡片；完成或撤回澄清的卡片回到待排期池，见 §11
- **分页**：服务端分页，页码从 1 开始；默认每页 10 张，可切换 10 / 20 / 50；总数取当前筛选条件下的池内全量，不随页码或每页条数变化
- **排序**：创建时间倒序，创建时间相同按卡片编号倒序，保证翻页不重不漏
- **页码复位**：搜索、筛选或只看自己变化后回到第 1 页；移除卡片后刷新当前页，当前页为空且不是第 1 页时回退上一页
- **页码记忆**：页码与每页条数不写入页面地址，刷新页面回到第 1 页；从卡片详情页返回时恢复进入前的页码与每页条数
- **跨页多选**：切换页码不清空已选，勾选跨页累计；筛选、搜索或只看自己变化时退出多选态并清空已选；合并或批量移入完成后退出多选态，刷新当前页并按页码复位规则回退
- **拖入排期与移回**：卡片从池内拖入日历后从池中移除；日历卡片拖回池或移回待排期后，池回到第 1 页并按池排序展示
- 相对时间以卡片创建时间与浏览器当前时间之差计算，页面保持打开超过 24 小时建议刷新；呈现见 web-ui.md B2
- **批量移入非需求改动**：进入多选态后勾选卡片，二次确认后逐卡移入，单卡失败不影响其他卡，结束后提示成功与失败数；适用于文档类卡片批量清理；与合并多选态互斥，Esc 退出

## 8. 合并卡

### 8.1 发起方式

- **多选合并**：「更多 → 合并卡片」进入多选态，月历格、待排期池与 +N 日详情中的卡片可勾选；待排期池支持跨页勾选，已选集合跨页保留；首张勾选后锁定其来源模块，不满足 §8.2 的卡片不可勾选，满足后确认并填写合并卡标题生成；Esc 或「取消」退出多选态
- **拖拽合并**：非多选态下把一张卡片拖到另一张满足合并条件的同模块卡片上（月历、周历、待排期池、+N 日详情均支持），持续悬停 600 毫秒后显示「松开合并」，此时放下打开合并标题弹窗；移出目标卡片即取消合并提示。未出现提示时放下，按所在日期格执行排期或改期，不触发合并；跨模块、开发完成、待澄清、非需求改动与子卡不作为合并落点，仍可将未锁定的源卡排到目标日期。已排期卡片拖到待排期池内卡片上始终视为取消排期，不触发合并
- 合并卡由 PM 主动创建，不由 commit 触发，不占用 commit 出卡的唯一性约束

### 8.2 前置校验

服务端强校验，前端预校验：

- 至少选中 2 张卡片
- 所有选中卡片来源模块一致，已有合并卡按其模块计
- 选中卡片仅允许待开发、开发中；开发完成、待澄清、非需求改动拒绝
- 任一选中卡片已是其他合并卡的子卡时拒绝，需先解散其合并卡，或整张选中该合并卡参与嵌套合并
- 完成澄清时的自动合并不经本节校验，按 §11.3 执行

### 8.3 合并卡生成

| 属性 | 取值 |
|------|------|
| 卡片编号 | 编号规则与序号见 field-rules.md §1 |
| 标题 | 用户输入，校验见 field-rules.md §2 |
| 内容 | 系统合成：首行「合并自 N 张子卡：」，其后逐行「- {子卡编号} {子卡标题}」 |
| 负责人 | 当前操作人，不取任一子卡的负责人 |
| 状态 | 待开发 |
| 排期日 | 子卡中最早的非空排期日；均未排期时为空，进入待排期池 |
| 源仓、源 commit | 合并卡专用标识，源 commit 按合并卡编号生成，不与 commit 出卡的唯一性冲突 |
| 来源模块 | 子卡共同的来源模块 |
| 所属项目 | 查询投影，不存卡片字段；全部子卡同属一个启用中项目时归属该项目，否则为「未归属项目」，见 §9 |
| 合并标识、父合并卡 | 是；无 |
| 需求性质、业务对接人 | 业务功能、空；不继承子卡，按普通卡维护 |
| 硬件管理标记 | 置空，不继承子卡 |

- 流水：合并卡写创建卡片「合并自 N 张：{编号1}, {编号2}, …」，子卡超过 20 张时只列前 20 个编号并注明「等 N 张」；每张子卡写编辑「并入合并卡 {合并卡编号}」

### 8.4 子卡主从

- 合并成功时：为每张子卡记录合并明细，保存其进入合并前的状态、排期日与开发人信息快照；子卡的父合并卡指向本合并卡；子卡的状态、排期日与开发人信息覆盖为合并卡当前值
- 合并卡的领取、释放、标记完成、回退与编辑（排期、标题、内容、负责人）成功后，同步写入全部子卡，同成同败；不为子卡单独写流水，合并卡流水注明「扩散至 N 张子卡」；子卡合并前的独立流水保留
- 子卡锁定规则见 state-machine.md §4；待排期池、各视图与非需求改动列表均不展示子卡，子卡仅在合并卡明细中可见

### 8.5 嵌套合并扁平化

选中卡片包含已有合并卡时：

1. 取该合并卡下的全部原始子卡，与本次其他选中卡一起挂到新合并卡
2. 原始子卡沿用最初的合并前快照（首次进入合并前的独立态），不以旧合并卡的当前状态为准，保证解散新合并卡时回到最初独立态
3. 原始子卡的合并明细整体迁移到新合并卡，新选中卡新增明细
4. 旧合并卡软删除，写删除流水「被合并至 {新合并卡编号}」
5. 最终只有一层合并卡与扁平子卡集合，查询与解散均无需递归

### 8.6 解散与删除

- **解散**：合并卡详情页「更多操作 → 解散合并」，二次确认后执行；仅合并卡可解散，开发完成与待澄清的合并卡不可解散（见 state-machine.md §4）
- 解散时：按快照恢复每张子卡的状态、排期日与开发人信息，解除父合并卡归属；恢复后排期日早于今天的强制清空，子卡回到待排期池，流水注明「快照日期已过期，已回待排期池」；随后删除全部合并明细，合并卡软删除
- 流水：合并卡写删除「解散合并，子卡恢复独立（N 张）」；每张子卡写编辑「从合并 {合并卡编号} 解散恢复」
- **删除合并卡** = 解散后删除合并卡，与解散同一路径

## 9. 项目归属与配置

- **基础真源**：[项目管理](../../项目管理/SKILL.md)是人工项目、Git 仓库、环境信息与项目成员的唯一维护入口；项目来源见[项目真源](../../项目管理/references/business-rule.md#source)，harness 工程与代码服务仓映射见[执行映射](../../项目管理/references/business-rule.md#execution-mapping)。本模块只维护卡片、回执及流程事实，不提供配置表单。
- **项目模型**：项目配置、来源与启停只读引用[项目管理规则](../../项目管理/references/business-rule.md#source)，本模块不复制配置字段和校验。
- **归属解析**：按[项目消费口径](../../项目管理/references/business-rule.md#consumption)，查询时以卡片源仓匹配启用中项目的 harness 工程仓，命中则归属该项目；代码服务仓不参与归属。卡片不存项目事实，不按变更路径或一级目录限定范围，不存在一卡多项目。
- **合并卡归属**：全部子卡同属一个启用中项目时归属该项目；跨项目、含未归属子卡或无子卡时为「未归属项目」。不得对子卡项目取并集或以任一子卡命中代表合并卡归属；解散后每张子卡按自己的源仓重新解析。
- **未归属项目**：源仓未匹配启用项目时使用此查询、筛选和统计兜底项，它不是实体项目；项目停用后原归属卡片回落到此项，不删除卡片。
- **映射变更**：项目改名、改仓或启停后重新计算卡片项目名称、归属、标签、筛选与统计投影；不回写卡片源仓、源 commit、负责人、状态、排期、回执或既有流水，也不重写已归档报告。读取失败不视为配置已清空或项目已停用。
- **配置入口**：项目、Git 仓库、环境信息及成员配置统一从研发管理菜单的[项目管理](../../项目管理/references/web-ui.md#pages)进入；排期更多菜单不提供这些配置入口，也不提供项目管理替代快捷入口。配置权限由[项目管理](../../项目管理/references/permission-rules.md#boundaries)独立校验，不继承排期编辑权限。
- **项目成员**：显示名、别名与报告映射引用[成员身份](../../项目管理/references/business-rule.md#identity)；[成员关系](../../项目管理/references/business-rule.md#membership)只在选定项目的「成员管理」维护，已有成员跨项目复用，使用唯一稳定成员 ID，可兼任 PRODUCT、DEVELOPER、DESIGN、ARCHITECT 多角色。报告有效成员须同时满足项目启用、成员全局启用与项目成员关系启用，见[生命周期](../../项目管理/references/business-rule.md#lifecycle)；不在排期或报告配置重复维护人员名单，不替代公共 Portal 身份与排期权限，不新增外部仓库授权。
- **项目标识色**：项目创建时按蓝、青、紫、金、品红、橙红六色顺序循环分配并固定；由项目管理提供，不能按首次出现在排期的顺序重分配。停用不释放颜色，重新启用沿用原色，新增项目顺延；所有视图、筛选与详情使用同色，颜色只表达归属，不表达状态。未归属项目固定灰色，不占用调色板。
- **完成回执范围**：只从卡片当前归属项目的代码服务仓选择，按稳定仓去重；合并卡不取子卡代码仓并集。未归属项目或项目未配置代码服务仓时无候选，仍可不关联 commit 直接完成；提交校验见 field-rules.md §8。
- **仓库来源与读取**：项目可选仓为云效 Codeup 目录与启用的通用 Git 配置，按来源类型和稳定仓标识区分，不以名称相同认定同仓；通用 Git 名称、地址、账号、加密凭据、连接测试及引用保护由项目管理维护，见[仓库定义](../../项目管理/references/data.md#repositories)。分支与提交仍以远端仓为准，临时缓存可重建，不影响卡片、回执和采集水位；查询失败明确反馈，不作为零提交、来源删除或改写归属的依据。

## 10. 非需求改动列表

- 收纳状态为非需求改动、非子卡的卡片；入口为「更多 → 非需求改动」，菜单角标与弹层总数均取全量，不随当前页码或每页条数变化
- **分页**：服务端分页，页码从 1 开始；默认每页 10 条，可切换 10 / 20 / 50
- **弹层尺寸**：宽度 600；高度固定为 640px，视口不足时按可用高度收缩；列表区在固定高度内滚动，分页条固定在弹层底部，不随页码或每页条数变化
- **排序**：创建时间倒序，创建时间相同按卡片编号倒序，保证翻页不重不漏
- **页码复位**：每次打开弹层从第 1 页开始，关闭后丢弃页码；恢复为待开发后卡片退出列表，下次打开按最新总数展示
- 列表不受「只看自己」影响；卡片可进入详情页，返回工作台后弹层不自动重开
- 卡片以项目色标签标识归属，配色规则见 §9

## 11. 需求澄清

### 11.1 发起澄清

- **场景**：研发识别或评审需求时发现缺失、矛盾、歧义、不可验收或不可行，无法直接开发，需要产品修订需求文档
- **范围**：待开发（含待排期池中未排期的卡片）与开发中的非子卡；合并卡发起时状态与排期变化扩散至全部子卡；开发完成需先回退，非需求改动不可发起
- **必填问题**：发起时必须填写澄清问题，取值与校验见 field-rules.md §10
- **效果**：卡片转为待澄清，移出月历与待排期池；排期清空，开发人信息保留；生成一条澄清记录，保存澄清前状态与原排期，轮次按卡片累计
- **唯一性**：卡片处于待澄清时不可再次发起；完成或撤回后可再次发起，形成新一轮澄清记录
- **渠道**：PC 与 MCP 适用同一规则，澄清记录注明发起渠道；MCP 工具见 [other-rule-mcp.md](other-rule-mcp.md)
- 通知见 §11.5

### 11.2 澄清方式

- 澄清不是文字答复：产品修订卡片所属 harness 工程中的需求文档并提交，修订 commit 即澄清结果
- 修订提交后，由产品在 PC 端或经 MCP 以修订 commit 完成澄清，见 §11.3
- 确认无需修订文档时，由发起人或持有编辑权限者撤回澄清，见 §11.4

### 11.3 完成澄清与自动合并

- **修订 commit**：至少 1 条，取自卡片的 harness 工程（普通卡为其源仓，合并卡为其子卡的源仓），取值与校验见 field-rules.md §11
- **处理的轮次**：完成澄清针对操作时看到的那一轮澄清；该轮已被完成、撤回或卡片已重新发起澄清时拒绝，提示「澄清已变化，请刷新后重试」
- **修订卡**：修订 commit 已出卡时沿用该卡；尚未出卡时按 §1.3 手动新建规则当场出卡。修订卡已删除、已是其他合并卡的子卡、开发完成或待澄清时拒绝；非需求改动卡允许并入。完成澄清期间原卡与全部修订卡一并锁定，修订卡已被其他操作并入别的合并卡或状态变化时拒绝
- **自动合并**：原卡与全部修订卡按 §8 合并，原卡为合并卡时按 §8.5 扁平化；以下取值不同于 §8.2、§8.3：
  - 不校验来源模块一致，来源模块取原卡
  - 标题、负责人、需求性质与业务对接人取原卡，无需填写合并卡标题
  - 状态与开发人信息恢复为原卡澄清前的状态：开发中保留开发人与领取时间，待开发无开发人
  - 排期为空，进入待排期池，由 PM 重新排期
  - 原卡的合并前快照记录澄清前状态、空排期与开发人信息，解散后不会回到待澄清
- **编号**：完成后卡片以新合并卡编号继续流转，原卡成为子卡，详情页提示其隶属的合并卡；澄清记录、通知与 MCP 结果均注明新合并卡编号；已关联原卡的需求单仍指向原卡
- **多轮澄清**：合并卡再次澄清并完成时，上一轮生成的合并卡按 §8.5 并入新合并卡；中间合并卡编号仍可打开，自动跳转到最新合并卡并提示；澄清来源由早到晚列出全部前序卡片编号，澄清记录展示整个澄清链路上的全部轮次
- **流水**：原卡写澄清完成；新合并卡写创建卡片「澄清完成，合并自 N 张：{编号1}, {编号2}, …」；每张修订卡写编辑「并入合并卡 {编号}（澄清修订）」，当场出卡的修订卡另有创建卡片流水
- **澄清记录**：置为已澄清，记录处理人、处理时间与渠道、合并后卡片，以及修订 commit 快照（修订卡编号、仓库、hash、提交说明首行、作者与提交时间）；快照不随修订卡此后的合并扩散或编辑变化
- **完成 commit**：完成澄清生成的合并卡按 §9 解析唯一归属项目，开发完成时从该项目的代码服务仓关联回执；全部子卡不能同属一个启用项目时为未归属项目，无候选仓仍可不关联直接完成。

### 11.4 撤回澄清

- 发起人本人或持有编辑权限者可撤回；是否为发起人按实际撤回的那一轮判定，该轮已变化时拒绝并提示「澄清已变化，请刷新后重试」；撤回理由选填，规则见 field-rules.md §12
- 撤回后卡片恢复澄清前的状态，排期为空，进入待排期池，开发人信息不变；澄清记录置为已撤回
- 删除待澄清卡片时，澄清记录一并置为已撤回，理由记「卡片已删除」

### 11.5 通知

- 经企微个人消息推送，在操作成功后异步发送，发送失败不影响操作结果；消息附卡片详情链接
- 转待澄清：通知卡片负责人，内容含发起人与问题摘要
- 完成澄清：通知发起人，内容含修订 commit 与新合并卡编号
- 撤回澄清：发起人撤回时通知负责人，其他人撤回时通知发起人，内容含撤回理由
- 接收人为操作人本人，或负责人未匹配系统用户时不发送

### 11.6 待澄清列表

- 入口为指挥栏「待澄清」，计数口径见 §4
- 收纳状态为待澄清的非子卡；分栏「全部 / 我负责的 / 我发起的」：我负责的指负责人是当前用户，我发起的指当前澄清记录的发起人是当前用户
- 排序按发起时间正序，等待最久的在前；发起时间相同按卡片编号倒序
- 服务端分页，默认每页 10 条，可切换 10 / 20 / 50；每次打开回到「全部」第 1 页
- 不受工作台筛选、搜索与只看自己影响
- 等待时长为发起至今的时长，超过 2 天为警示样式

### 11.7 对下游的影响

- 待澄清卡没有排期，不进入按排期周期统计的研发报告；完成澄清后的合并卡重新排期后按常规统计
- 需求单可关联待澄清卡并实时展示其状态，见 [需求管理 business-rule §5](../../../需求管理/references/business-rule.md#5-排期关联规则)

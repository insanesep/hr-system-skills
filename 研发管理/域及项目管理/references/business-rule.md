# 域及项目管理 · 业务规则

<a id="source"></a>
## 1. 清单与唯一身份

域对应代码仓，项目对应该域主仓版本树中的一级目录。域、项目列表均从已批准接入范围的代码仓结构同步取得，不允许人工新增、删除对象或手填未存在的目录；同步范围不随个人选人或模型搜索扩大。

- 一个稳定代码仓只对应一个域；仓名、域显示名及远端地址均不是唯一身份。云效与其他已接入托管来源按各自稳定仓标识区分，不凭同名归并。
- 同一域内一个一级目录只对应一个项目；不同域可有同名目录。一级目录树条目整体作为同步来源，不以名称猜测业务属性或任意剔除普通技术目录；根文件不是项目，Git 内部信息不是远端版本树目录。
- 域名称和项目目录名称随成功结构同步回显，只读；备注、业务启停、负责人和实现映射属于本功能维护，不反写仓名或目录。
- 同步新增对象默认停用。新结构不会自动任命负责人、启用业务、开通仓权限或开启报告与巡检。
- 来源存在性、业务启停与读取新鲜度分别判定，见[状态规则](state-machine.md#states)；读取失败不等于来源删除，更不清空上次有效结构。
- 完整读取、目录更名与消失处理遵守[同步规则](other-rule-sync.md#sync)，不通过本页删除远端仓库或目录。

<a id="responsibility"></a>
## 2. 责任归属与上下级

负责人候选来自[产研人员管理](../../产研人员管理/references/business-rule.md#identity)中的有效业务身份。任命是责任事实，不自动授予功能管理、合并、发布或仓库管理权限。

- 每个启用域必须且只能有一名负责人；每个启用项目至少一名负责人，可有多人，记录其本项目职责。
- 普通域负责人可选具有有效产研角色的人员。对应 `busyming-skills-common` 的域负责人必须具有架构角色；对应 `busyming-skills-design` 的域负责人必须具有研发或设计角色。角色并存时满足对应条件即可。
- 特殊域规则绑定已核对的稳定仓身份；同步首次按远端精确仓名识别并核对，重名或身份不明时阻断任命和启用。不得按任意名字包含 common、design 放行，更名后仍保留原稳定身份规则。
- 项目负责人只对其负责项目取得责任关系。项目负责人对应上级为所属域负责人，一人跨域任命时按项目逐条显示，可有多个责任上级。
- 域负责人兼任其子项目负责人时显示本人兼管，不建立自我汇报关系；域负责人与其他域负责人的上级不由本功能推定。
- 人员页只读展示责任关系。修改域负责人、项目负责人统一在本功能完成，不维护另一份直属上级名单，不覆盖人资组织关系。
- 修改负责人对新的业务责任分派生效；存量审批链快照、卡片经办、工单处理人与历史报告保持原事实，在途交接由所属业务模块执行。
- 移除、禁用或删除负责人前校验有效任命；域必须替换唯一负责人，项目应保留至少一名有效负责人或先停用。人员角色变更后不满足特殊资格时同样阻断继续任职，不能凭旧任命继续使用。

<a id="execution-mapping"></a>
## 3. 项目执行映射

本功能唯一维护项目的需求目录与实现代码仓、已核验实现路径之间的对应关系。域主仓按项目一级目录提供文档或代码事实；域和仓用途不得凭仓名推定。

- 项目可引用多个实现仓；一个实现仓可服务多个项目，关系按项目、稳定仓标识及已确认实现范围登记，不继续使用一仓只能属于一个启用项目的旧约束。
- 实现仓从同步域清单选择，目录或仓级范围从已读取结构核对；全仓映射只在确认该项目确需完整仓事实时使用。未知实现范围不冒充已确认映射。
- 共用实现仓按仓稳定标识去重读取和同步成员；不能将每个关联项目都累加一份仓成员、仓用量或提交数。
- 仓权限目标只按[产品授权规则](../../产研人员管理/references/other-rule-authorization.md#policy)计算，引用实现映射不自动扩权到其他仓。
- 默认分支、分支和提交以托管来源为准；凭据沿用已接入公共机制，不写在本功能规则、备注或模型会话中。
- 映射增改是基础资料动作，不改变排期卡状态、审批结果、完成回执、巡检执行或发布许可。

<a id="consumption"></a>
## 4. 产研消费口径

本功能提供域、项目、主仓、一级目录、实现映射、当前业务启停及负责人；消费方只存稳定引用与其自身业务证据，不复制维护清单。域和项目不是需求管理产品线、业务线或云服务 SLS Project 的别名，这些原有对象保持各自语义。

- 排期源仓按域去重采集；一条源仓 commit 只产生一张卡，按实际变更文件落入的一级目录关联一个或多个项目，来源模块标题不作为项目归属依据。
- 跨一级目录提交保留项目集合；根文件或无法对应项目的变更归域级范围，项目读取未取得时标记待核对，不猜测并不丢失卡片。合并卡由子卡的域项目集合取并集。
- 项目列表可展示与其有关的同一卡片；域及全量总数按卡片稳定编号去重，不能叠加各项目计数。提交及行数同样按仓、commit和实际路径去重。
- 项目实现仓的提交只按确认路径或明确交付关联纳入项目。无法细分的共用仓事实保留域级或待归属范围，不将全仓提交重复计入全部项目。
- 报告域范围为主仓整体及已确认执行映射的去重集合；项目范围为其一级目录及本项目确认实现范围。报告 key、基准分支、触发和历史归档归报告配置。
- 需求接收、审批和 SLA 只能在已有明确域项目关联时消费责任层级，不通过人名或部门猜测归属，不自动改变已冻结审批链。
- 运维按有效实现范围组织执行，同仓跨项目取证去重；巡检、自动修复、通知与发布开关继续由各自功能管理，不因域项目启用自动开启。
- 共用设计和公共资料仍按各功能现有依赖与评估政策消费；域清单包含 common/design 不等于健康度报告取消其既有评估排除规则。

<a id="history"></a>
## 5. 业务启停与引用保护

业务启停和来源状态遵守[状态规则](state-machine.md#states)。域停用使其子项目暂不参与新的业务归属、人员授权和生成范围，项目原业务配置保留；重新启用域后，子项目仍按自身状态、来源和负责人资格逐一判定。

停止新业务不删除历史。负责人、参与关系、报告扩展与历史证据保留稳定关联；域或项目来源确认消失后停止新的业务消费并触发人员授权目标重算，不能擅自删除审批、排期、报告与工单记录。同步更名不会静默迁移历史责任到另一个目录。

## 适用性说明

本仓库是鸣鸣很忙产研领域的 **SKILL.md 结构化资产仓库**，不包含任何可执行代码。根 `AGENTS.md` 的「内容红线」明确禁止在文档中写入伪代码、SQL、接口报文等实现级内容，所有实现细节以链接指向代码仓或外部文档。因此，仓库内不存在实际的错误类型定义、异常传播链、中间件或 panic/recover 策略；本节仅归纳文档中对错误处理的业务约定与约束。

## 错误处理体系概览

错误日志管理围绕「采集 → 指纹归一化 → 聚合落库 → 阈值告警 → 人工标记闭环」构建，错误本身既是输入（ERROR/FATAL 日志），也是输出（报表项 + 告警）。

### 1. 错误来源与采集

- 数据来源为日志平台的应用日志，每日凌晨定时任务扫描前一自然日全部 `ERROR`（含 `FATAL`，按 ERROR 处理）日志
- 时间窗以日志原始时间戳为准，按本地时区切日；任务延迟至少 30 分钟启动，防止日志写入丢数据
- 多应用/多日志库通过配置列表枚举接入，默认按「应用名-环境」定位日志库

### 2. 指纹归一化（同类折叠）

指纹由「应用名 + 异常类名 + 归一化异常消息 + 顶层堆栈行」生成固定长度摘要，用于把同一类报错折叠为一条异常分组。

归一化规则：
- 异常消息中的数字、UUID、时间戳、IP、十六进制串统一替换为占位符
- 堆栈仅取最顶层非框架行（过滤 JDK 与框架包）
- 归一化规则字典以代码仓为准，新增规则需回归验证

唯一键为「日期 + 应用名 + 指纹」三元组，作为落库业务主键。

### 3. 静默丢数据防控（强制约束）

`SKILL.md` 业务规则第 7 条明确规定：**查询失败、解析失败、落库失败均必须打 ERROR 日志并标记任务失败，严禁吞异常**。这是该模块对错误处理的最强约束。

### 4. 状态机与人工处置

报表项的状态机：
```
待处理 ──标记已处理──▶ 已处理 ──撤销──▶ 待处理
待处理 ──忽略──▶ 已忽略
```

- 「已忽略」表示噪声不再统计告警，但记录保留
- 处理快照（状态 / 处理人 / 处理时间 / 处理备注）独立存储，重跑幂等时不被覆盖
- 重跑只更新统计字段（出现次数、首次/最后发生时间等），不覆盖处理状态

### 5. 告警与失败兜底

触发条件（见 `references/wecom-alert.md`）：
- 单个报表项出现次数 ≥ 告警阈值（默认 50，以配置中心生效值为准）
- 同一报表项一天只发一次，发送记录本地留存去重
- 全局开关控制，默认关闭

失败兜底：
- 企微推送失败不阻断主任务
- 推送失败时发送记录标记为失败，下次任务执行时由独立补偿任务重试 3 次

### 6. 可观测性与审计

- 任务每次执行留痕：拉取条数 / 聚合数 / 落库数 / 耗时
- 操作日志覆盖标记 / 撤销 / 忽略 / 重跑四个动作
- traceId 样例最多保留前 5 个，用于跳转日志控制台定位

### 7. 反模式（明确禁止）

`SKILL.md` 末尾列出反模式清单：
- ❌ 在接口层循环查日志平台（必须由任务落库后查库）
- ❌ 把状态字段写进唯一键（导致重跑覆盖处理状态）
- ❌ 吞异常不处理、不上报（静默丢数据）
- ❌ 自起文件上传实现导出（必须接统一导出中心）
- ❌ 文档内嵌 SQL / 代码片段 / 接口报文

## 与其他子域的关联

- 黑灯工厂管理：需求管理缺陷分流建单时，自动关联错误日志中的异常分组进行问题分级分类
- 服务器监控：错误及黑灯工厂关联快照，形成运维证据链
- 报告配置：报告触发配置支持「失败重试」，与错误日志管理的重跑机制同构

## 结论

本仓库对错误处理的描述集中在「运维管理/错误日志管理」子域，以 SKILL.md 的业务规则形式表达，核心约定包括：指纹归一化折叠、静默丢数据零容忍、状态机驱动的人工处置、企微告警 + 补偿重试、以及明确的反模式禁令。实际代码实现不在本仓库，需跳转到对应代码仓查阅。

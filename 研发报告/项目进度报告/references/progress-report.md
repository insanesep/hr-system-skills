# progress-report / 项目进度报告生成

> 一句话定位：每个统计周期只生成一份项目进度总报告，采集全部启用项目组的研发周报核心进展、团队人员、功能排期、Git 提交、Qoder 用量与产品文档健康度，在报告内按项目组及仓库分组展示。服务端生成会话的产出回传服务端直接落库归档；外部会话产出推送至 devops 研发报告模块（旁路通道）。

## When to Use

- 用户说「生成项目进度报告 / 项目周报 / 项目月报」
- 在一份周期报告中按项目组查看项目核心进展、团队人员、功能排期、代码提交与 Qoder 使用，并按仓库查看 harness 文档健康度

## When Not to Use

- 需要定时自动跑 → 由研发报告模块「报告触发配置」承担定时调度，本 skill 只描述单次生成会话的执行
- 研发周报（人员维度）/ 一致性检查 → 分别由人员产出报告、文档一致性报告模块的生成 skill 承载

## 参数解析

| 参数 | 取值 | 默认 |
|------|------|------|
| 报告范围 | 固定 `_all`：全部已配置启用域/项目组的去重并集 | 服务端与外部会话均不得按组拆分生成 |
| 统计周期 | 周 / 月 | 服务端会话由触发配置的类型参数给定；外部会话默认周 |
| 代码工作区 | 绝对路径 | 服务端会话由服务端注入；外部会话读取 config.yaml 的 `workspace_dir` 并解析为绝对路径 |
| 推送 | 服务端会话固定「不推送，产出回传服务端」；外部会话默认生成后推送，用户说「仅生成」则跳过 | 按会话类型 |

**单份周期报告**：每个统计周期仅生成一份报告，周报每个自然周一份，月报每个自然月一份。`_all` 是唯一新生成报告项与文件名标识，不再按项目组创建生成任务、触发配置或归档报告；同周期重复生成或补传只递增该报告的版本。

**范围真源**：项目组展示与统计范围只读采用 [报告配置](../../报告配置/SKILL.md) 中全部已配置启用的报告范围类型、稳定引用与生效配置；key 同源；项目进度 Git 分支固定为 `master + feature/*`，不随 `branch_policy` 收窄为单分支。外部 `projects.<key>` 仅传递同一范围快照，不另建实体或猜测归属。各组统计边界采用项目管理配置的 harness 工程与代码服务仓快照，不按一级目录拆分项目；未配置仓及跨项目同名实现不混入。卡片归属采用功能排期按源仓与启用项目映射得到的查询投影。新范围配置齐备并启用后加入下一份周期报告的分组，停用后从后续报告移除，不删历史归档。

**人员范围**：只读采用 [项目管理 · 项目成员](../../../研发管理/项目管理/references/business-rule.md#membership) 的配置，不维护第二份人员名单。人员在每个项目内独立维护，同一稳定人员可属于多个项目；当前项目的成员关系和对应稳定人员均为启用（ENABLED）时，才进入该项目的生成名单。配置成员快照只作为候选名单，项目组人数取与研发周报同源的 Git 作者识别和程序校验结果，仅纳入统计窗口内有本项目有效提交的人员；不因中文姓名、英文名、拼音或邮箱未与别名完全一致而提前删除作者，不从 Git 创建或自动迁移成员归属。产品人数、研发人数、架构人数按快照角色及人员稳定 ID 分别去重计数，并在人员明细中按角色展示对应人员姓名；角色内按姓名、人员稳定 ID 排序，同人多角色在对应角色各展示一次，跨项目全量并集仅计一人，各角色的全量人数与人员明细也分别按稳定 ID 去重。来源成功且确认项目无配置成员时人数均为 0、人员明细为「无」；成员关系、稳定人员记录或角色来源未取得时，对应人数、人员明细及依赖的人均指标标「未取得」，不使用组织全员或其它项目名单兜底。

**人员快照**：报告项目取报告扩展已配置启用的范围；任务同时携带这些项目各自的启用成员关系、启用稳定人员身份、姓名与角色，以及按人员稳定 ID 去重的全局并集，随报告版本留档，生成与历史查阅不改用实时名单。人员稳定 ID 与姓名映射同时供 Web 详情的人员周报查看及 PNG 工作明细附录使用，附录仅保留经提交过滤后进入团队明细的人员；Markdown 原件与 Web 正文中的人员明细仅保留姓名文本，不写入私有链接协议。人员产出周报、日报仍使用配置成员的全局去重并集，不按本报告的项目组重复生成人员产出；该并集为空或人员真源未取得时拒绝生成人员产出报告。项目进度报告中已确认的空项目名单不拒绝生成，团队人数记 0、人员明细记「无」，人均功能数和对应角色的人均提交行数记「—」。

**汇总与分组**：取全部可生成项目范围及人员并集，先按项目、卡片、人员稳定 ID 及源仓稳定 ID + commit SHA 去重后汇总，不叠加重复源事实；项目组人员取各项目配置成员快照并按窗口有效提交过滤，全量仅保留任一参与项目有有效提交的人员并按人员稳定 ID 去重，不从 Git 作者创建成员或自动迁移归属。代码提交与 Qoder 使用按产品、研发、架构角色分别统计；同人多角色时，其提交或用量在对应角色分别完整展示，角色指标之间不可相加。Qoder 个人用量在参与的每个项目完整展示，属于人员维度而非仓库分配；`_all` 在各角色内按人员稳定 ID、自然日及来源快照去重，同一用量在同一角色只计一次，禁止累加项目行。各章节仅用一个表格，项目核心进展、团队人员、功能排期、代码提交与 Qoder 使用按项目 key 字典序列项目组，harness 文档健康度按仓库名字典序列仓库且不设项目组列；功能排期、代码提交与 Qoder 使用末行以加粗的「全量汇总」展示，团队人员末行以加粗的「全量汇总(去重)」展示，项目核心进展与 harness 文档健康度不设全量汇总；明细不直接相加为总数，完成率、延期率与人均指标由去重后的汇总分子、分母重新计算，不对各组百分比或人均值取平均，也不得对各组人均值求和；全量人均功能数 = 全量功能排期数 ÷ 全量有提交去重研发人数，产品 / 研发 / 架构全量人均提交行数 = 对应角色全量新增与删除行数合计 ÷ 对应角色全量有提交去重人数，产品 / 研发 / 架构 Qoder 人均指标 = 对应角色全量去重 Credits 或请求次数 ÷ 对应角色全量去重活跃成员数。历史单组报告保留原归档，新报告标题统一为「项目进度报告 - {yyyy-MM-dd}」，文件名统一为 `progress_yyyyMMdd__all.md`。

**统计窗口**：

- 周：最近一个以周日收尾的周一~周日（今天是周日则含今天，否则不含）
- 月：上一自然月

## 执行流程

### Step 1 读配置、定工作区

按会话类型取配置（服务端注入 / 外部会话读 config.yaml），确定：工作区绝对路径 `WS`、输出目录、报告扩展已配置启用的全部项目组映射、各项目启用成员关系及启用稳定人员的身份、姓名与角色快照、全局去重成员并集。两类会话均消费同一配置快照，不以 Git 采集结果重建名单。

🚨 **工作区硬约束（违反将产出错误结论）**：一切文件操作只能以 `WS` 为基准，目标仓库都是其子目录（`$WS/<repo>/`）。机器上其它位置存在同名仓库的**开发者副本**（过时、分支不同、缺最新提交），严禁用于搜索、读取或作为结论依据。Glob / Grep / Read / Bash 的路径参数必须落在 `WS` 内；工具结果中出现 `WS` 之外的路径一律忽略并重查。

### Step 2 同步仓库

- **外部会话**：对项目映射 `code_repos` 与 `harness_repo` 下每个仓库，仓库缺失时按会话配置 `codeup` 凭证浅克隆（命令不内嵌，按生成环境约定执行）。
- **服务端生成会话**：复用研发周报的确定性 Git 采集程序，在任务工作区外同步冻结范围中的云效仓和基础 Git 仓，按统计窗口采集提交与行数。采集凭据只供程序使用，不进入作者识别或最终正文会话；模型不执行克隆、同步、分支切换或重新计数。

所有项目组固定统计 `master + feature/*` 分支，与研发周报口径一致；`branch_policy` 不再把项目进度收窄为 master 或 release 单分支。只在 `WS` 内的工作区仓库采集，严禁碰开发目录；`wt/*` 不单独纳入，release 不另作统计分支。跨分支按 commit SHA 全局去重，剔除 merge，避免同一提交被重复计数

### Step 3 采集数据

- **功能排期卡片**：外部会话走 MCP 工具（`busyming_feature_schedule`，调用口径、字段与容错见 [`data-source-api.md`](../../报告配置/references/data-source-api.md)），服务端会话由调用方在会话数据中直接提供。采集统计窗口内排期卡、完成时间与排期截止日，并通过卡片操作流水识别窗口内移入非需求改动的卡片；卡片项目归属采用功能排期当前源仓映射的查询投影，一张卡至多归属一个启用项目；合并卡全部子卡同属一个启用项目才归属该项目，否则为未归属项目，不重复分配到各组。`_all` 总计只汇总参与生成项目范围内的卡片并按稳定卡片 ID 去重
- **Git 提交**：外部会话以计数脚本按产品、研发、架构角色输出的提交次数、新增行数与删除行数为权威结果（按映射 `harness_repo` + `code_repos` 的 `master + feature/*` 分支），直接引用，**严禁自己再跑 git log 重新计数**；服务端会话与研发周报共用程序采集、独立作者识别及校验链路；保留全部真实作者，由独立识别阶段依据姓名、邮箱和候选成员别名给出映射，程序校验重复、遗漏和名单外映射并按稳定人员、项目关系及角色汇总。所有提交按 SHA 全局去重、剔除合并、窗口过滤，逐提交计算增删行且排除二进制；各仓小计与角色合计必须打平。最终正文只引用程序权威统计，不重新识别作者或计数。每个角色仅保留已验证到当前项目该角色配置成员的贡献；同人多角色时，其贡献在对应角色分别完整展示，角色指标不可相加。名单外或身份未匹配作者不计入分角色指标、不点名，不从 Git 创建人员或自动迁移项目归属
- **团队人员**：任务中的项目成员关系及稳定人员快照只作为候选名单，校验两者均启用后，按窗口内项目映射仓的有效提交与角色身份过滤；无提交成员从团队人数与人员明细排除，同人多角色分别展示，全量仅保留任一参与项目有有效提交的人员并按稳定 ID 去重。过滤后无人时各角色人数为 0、人员明细为「无」；成员来源或 Git 采集来源未取得时对应团队指标标「未取得」，不使用组织全员或其它项目名单兜底
- **Qoder 用量**：先取当前项目配置成员快照，再通过稳定身份映射取得这些成员在统计窗口内的自然日快照，按产品、研发、架构角色分别汇总 Credits 与请求次数；服务端会话由调用方注入，外部会话按既定用量接口取数。个人窗口用量在其参与的每个项目及每个已配置角色完整展示，不按仓库分配或推测分摊，角色指标不可相加；全量在各角色内按人员稳定 ID、自然日及来源快照去重，不累加项目行。活跃成员在同一项目、同一角色配置成员集合内沿用 Qoder 用量分析的正 Credits 记录口径并按稳定 ID 去重；已确认空名单时对应角色总量与活跃成员数为 0，已确认 Qoder 账号的成员在自然日无快照记录时按无用量明确补 0；无账号、身份未匹配、记录非法或来源查询失败时标「未取得」，部分成员未匹配时保留已匹配成员数据，展示已匹配/总人数与未匹配名单，合计明确标为已匹配成员非全量，仅未匹配成员标「未取得」，不冒充完整项目或角色总量或清空全部用量
- **项目核心进展**：取 [人员产出报告 · 研发周报](../../人员产出报告/references/weekly-report.md) 的「AI 分析总结 → 核心进展」，优先读取已存在的当前项目 key 周报；不存在时回退读取无项目维度的总人员产出周报，只提取可明确对应当前项目的核心进展，不把总周报全文复制到每个项目组。不能明确归属时该组标「未取得」。按 key 读取仅兼容已有产物，不新增分项目周报触发配置；新人员产出周报仍无项目维度。周报取相同统计窗口；月报合并窗口内各周报并去重，不改用 Git 提交或排期卡片推测替代
- **harness 文档健康度**：只读引用 [产品文档健康度报告](../../产品文档健康度报告/references/health-report.md) 的归档结果，不触发评估或重跑检查。本周为报告统计窗口截止日所在自然周，上周为其上一自然周，周报与月报均按这两个自然周取数；分别读取各周同仓库最新归档版本「仓库综合评分与环比」中的综合分 R 作为本周、上周健康度得分，各期得分缺失或不可比时以「-」省略。较上期 = 本周综合分 − 上周综合分，保留 1 位小数，正数带 `+`、零为 `0.0`；任一期缺失或不可比时标「—」。同一仓库同一周只有一份归档结果时采用；存在多份时仅采用域整仓结果，仍无法唯一确定时对应分数以「-」省略、差值标「—」，不挑选、不平均。操作使用本周报告的标准详情链接，本周报告缺失或无法唯一确定时显示「—」。仓库按仓库名字典序排列，沿用健康度报告排除 common/design 的范围，不将项目组分数相加

### Step 4 生成报告

- 按下文章节规范与输出模板生成；全文中文
- 报告标题：`项目进度报告 - {yyyy-MM-dd}`（生成当天日期）

### Step 5 写文件 + 落库 / 推送

- 写入输出目录，文件名严格遵循：`progress_yyyyMMdd__all.md`；新报告不得使用单项目组 key 命名，服务端按文件名解析类型与日期
- **服务端生成会话**：产出文件回传服务端，由服务端校验、渲染并直接落库（版本递增、周索引），本 skill 不调用推送接口
- **外部会话（旁路）**：推送契约（multipart 表单 + 鉴权头，幂等）见 [`data-source-api.md`](../../报告配置/references/data-source-api.md)；推送后把 `reportId / versionNo / duplicated` 回告用户；推送失败不删本地文件，把错误信息告知用户

## 章节规范

固定章节（顺序不可调换）：项目核心进展 / 团队人员 / 功能排期 / 代码提交 / Qoder 使用 / harness文档健康度。正文首部必须以引用块声明统计区间（归档侧解析元信息用；周期为月时不带括号注释）。每份报告包含全部启用项目组及健康度归档仓库，每个章节仅使用一个表格；前五章第一列为「项目组」，表体按项目 key 字典序展示项目组明细，harness文档健康度第一列为「仓库」并按仓库名字典序排列。功能排期、代码提交与 Qoder 使用末行为加粗的「全量汇总」汇总行，团队人员末行为加粗的「全量汇总(去重)」汇总行，项目核心进展与 harness文档健康度不设全量汇总，不得按组拆成多个表格或单组报告。

1. **项目核心进展**：展示当前项目组在统计窗口内的核心进展，只来自已存在的对应项目 key 周报或总人员产出周报；回退时仅提取明确归属当前项目的内容，来源缺失或无法明确归属标「未取得」，不复制全局进展或编造本项目进展。
2. **团队人员**：按项目成员关系及稳定人员均启用的任务快照，按人员稳定 ID 和角色分别去重展示产品人数、研发人数与架构人数，并在人员明细中按角色展示具体人员姓名，仅保留统计窗口内在项目映射仓有有效提交且身份匹配对应角色的成员，无提交成员从团队人数与人员明细排除。人员明细角色内按姓名、人员稳定 ID 排序；同人多角色在对应角色各计一次并各展示一次，同人多项目可在各组出现，全量仅保留任一参与项目有有效提交的人员，各角色人数与人员明细按全局成员并集分别去重，汇总行标签固定为「全量汇总(去重)」。源成功且确认空名单或过滤后无提交成员时各人数为 0、人员明细为「无」，成员来源未取得时对应人数与人员明细标「未取得」，不使用组织全员或其它项目名单兜底。
3. **功能排期**：展示功能排期数、非需求功能数、完成功能数、完成率、延期功能数、延期率、人均功能数。
   - 功能排期数：排期日落在统计窗口内的去重功能卡数，口径与功能排期管理一致，不含非需求改动、待澄清与子卡。
   - 非需求功能数：统计窗口内发生「移入非需求改动」的去重卡片数，按卡片操作流水认定，不计入功能排期数及完成率、延期率、人均功能数的分子或分母。
   - 完成功能数：上述功能排期卡中完成时间落在统计窗口内的卡片数；完成率 = 完成功能数 ÷ 功能排期数 × 100%。
   - 延期功能数：上述功能排期卡中，统计截止时仍未完成且排期截止日不晚于统计截止日的卡片数；延期率 = 延期功能数 ÷ 功能排期数 × 100%。
   - 人均功能数 = 功能排期数 ÷ 项目窗口内有有效提交的去重研发人数。功能排期数为 0 时完成率与延期率计 0%；研发人数为 0 时人均功能数显示「—」。
4. **代码提交**：按产品、研发、架构分别展示提交次数、提交行数（新增 / 删除）与人均提交行数。各角色提交次数及总行数按项目映射 `harness_repo` + `code_repos` 统计，仅保留身份匹配该项目该角色配置成员的贡献；同人多角色时其贡献在对应角色分别完整展示，角色指标不可相加，名单外或身份未匹配作者不计入分角色指标。提交行数按新增行数与删除行数分别展示；产品 / 研发 / 架构人均提交行数 = 对应角色（新增行数 + 删除行数）÷ 项目窗口内该角色有有效提交的去重人数，对应角色人数为 0 时显示「—」。
5. **Qoder 使用**：仅统计上述项目配置成员，按产品、研发、架构分别展示总使用量、人均使用量、总请求次数与人均请求次数。各角色总使用量与总请求次数为该角色配置成员窗口合计，同人个人用量完整展示于参与的每个项目及每个已配置角色，不按仓库分配，角色指标不可相加；全量在各角色内按人员稳定 ID、自然日及来源快照去重，禁止对项目行求和。产品 / 研发 / 架构人均使用量 = 对应角色总使用量 ÷ 该角色 Qoder 活跃成员数，产品 / 研发 / 架构人均请求次数 = 对应角色总请求次数 ÷ 该角色 Qoder 活跃成员数，活跃成员在项目该角色配置成员集合内沿用 Qoder 用量分析的正 Credits 记录口径并去重。配置成员已确认空时对应角色总量及活跃成员数为 0；对应角色活跃成员数为 0 时人均指标显示「—」，成员来源或用量未取得时标「未取得」。
6. **harness文档健康度**：按仓库展示上周健康度得分、本周健康度得分、较上期与操作。本周为报告统计窗口截止日所在自然周，上周为上一自然周；两周分别取同仓库最新归档产品文档健康度报告的仓库综合分 R，保留 1 位小数，缺失或不可比时以「-」省略。较上期 = 本周得分 − 上周得分，正数带 `+`、零为 `0.0`，任一期缺失或不可比时为「—」。同仓多份结果只采用可唯一确定的域整仓结果，无法唯一确定时不挑选、不平均。操作列展示「查看报告」并链接本周健康度报告详情；无唯一本周报告时为「—」。本章不设全量汇总，不重跑健康度检查，不纳入 common/design。

比率与人均值保留 1 位小数；Credits 按 Qoder 用量分析口径整数展示。成员来源成功且确认空名单时，团队人数、人员明细、Qoder 总量及活跃成员数按上述规则处理，人均指标为「—」。其余数据源缺失或拉取失败时，仅将依赖该源的指标标「未取得」（健康度得分按前条以「-」省略），不得以 0 或推测值代替；只有数据源成功且明确返回零值才计 0，Git 来源失败时团队人数与人员明细标「未取得」，Qoder 来源失败不改变已取得的团队人数与人员明细。

## 硬约束汇总

1. 单份报告红线：每个周期只创建一个生成会话、产出一份 `_all` 报告，不按项目组拆分任务或文件
2. 项目组边界红线：只统计映射内仓库、卡片与人员事实，跨项目搜到同名实现不混入
3. 计数纪律：外部会话分角色提交次数与行数以约定计数脚本输出为唯一权威（脚本由生成环境提供，不随仓维护）；服务端会话复用研发周报的程序采集、作者识别与校验链路（固定 `master + feature/*`、SHA 去重、剔 merge、窗口过滤、逐提交 numstat、二进制排除、小计与角色合计打平），正文仅引用程序权威统计
4. 工作区硬约束：只操作 `WS` 内路径（见 Step 1）
5. 人员口径：项目组人员以该项目成员关系及稳定人员均启用的任务快照为候选，仅保留统计窗口内在项目映射仓有有效提交且身份匹配对应角色的成员，无提交成员从团队人数、人员明细与相关人均分母排除；角色人数与姓名明细分别按稳定 ID 去重，同人多角色分别计数与展示、跨项目全量并集去重，不从 Git 创建或自动迁移成员。代码提交按产品、研发、架构角色过滤项目 `harness_repo` + `code_repos` 中身份匹配的贡献，Qoder 同样按角色过滤该项目配置成员；同人多角色的贡献在对应角色分别完整展示，角色指标不可相加。个人用量在参与项目完整展示，`_all` 在各角色内按人员稳定 ID、自然日及来源快照去重，不按仓库分配、不累加项目行，不使用组织全员或自建归属关系
6. 核心进展口径：只引用研发周报既有内容，不从其他数据源推测补写
7. 健康度口径：只读产品文档健康度归档的仓库综合分 R，按统计截止周与上一自然周取数；不重跑评估、不叠加多范围结果，「查看报告」只使用本周报告标准详情链接
8. 数据容错：任一数据源失败将对应指标标「未取得」（健康度得分以「-」省略），严禁编造数字；部分人员或日期快照不得冒充完整项目组总量
9. token 只从会话配置（服务端会话数据或 config.yaml）读取使用，禁止写进报告或 skill 文件

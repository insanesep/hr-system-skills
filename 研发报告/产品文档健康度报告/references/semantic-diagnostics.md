# AI 辅助诊断 · 需求闭环与跨文档一致性

> 本规范是 AI 语义诊断唯一真源。诊断用于发现客观规则难以覆盖的需求闭环缺口和语义冲突，**不参与健康分、仓库综合分、健康等级或硬门禁**，不修改业务仓文档。

## 1. 诊断边界

### 检查

- 当前快照内已纳入模块评估的 SKILL.md、AGENTS.md 及被引用的 references、UI 文档与原型可见内容
- 业务流程、逆向流程、状态机、数据、页面操作、跨域与验收六类闭环
- 状态、字段、规则、权限、页面、跨域、公共引用与核验状态八类一致性

### 不检查

- 代码是否实现、生产环境行为与真实线上验收
- 原型视觉美观、业务决策本身是否合理
- 无原文证据的猜测、常识补写或产品经理未确认的业务规则
- 客观评分子项的重复计算；AI 新发现不得直接转为分数或门禁

## 2. 诊断前建立需求事实表

每个模块先抽取事实，并保留文件与章节锚点：

| 事实类型 | 抽取内容 |
| --- | --- |
| 角色 | 使用者、审核者、异常处理者、数据权限范围 |
| 业务对象 | 单据、任务、商品、门店、库存等核心实体 |
| 业务动作 | 创建、提交、审核、支付、取消、作废、导出等 |
| 状态与流转 | 状态全集、初始终态、触发动作、前置条件、后置结果与副作用 |
| 业务规则 | 阈值、公式、判定顺序、限制、时间窗口 |
| 数据字段 | 含义、必填、默认值、取值范围、校验、读写归属 |
| 页面交互 | 入口、按钮、反馈、结果展示、返回与后续导航 |
| 异常处理 | 重复、冲突、超时、部分失败、重试与补偿 |
| 跨域协作 | 上游输入、下游输出、事实真源、完成判据 |
| 核验状态 | 已核验、待确认、预留、停用、外域未核验 |

事实真源按文档职责确定：SKILL 负责模块边界与导航，business-rule 负责业务规则，state-machine 负责状态，data-model/data 负责数据语义，UI 文档负责交互，consistency-spec 负责跨域与核验边界。冲突时不采用“多数文档投票”。

## 3. 六类需求闭环检查

### 3.1 业务流程

核对“发起人 → 前置条件 → 校验 → 业务结果 → 后续处理 → 最终完成”。缺任一关键环节且影响执行或验收时，记录覆盖缺失。

### 3.2 逆向流程

核对取消、驳回、作废、退回的适用阶段、数据后果与后续处理。只有正向创建与完成、没有应有逆向路径时，记录缺逆向流程。

### 3.3 状态机

逐状态检查入口、出口、可达性、终止状态、失败停留、非法跳转与重复副作用；区分单据、执行、支付、同步等不同状态，不得以“已支付”代替“已签收”、以“同步受理”代替“下游成功”。

### 3.4 数据

检查页面与规则所需字段是否定义，必填、默认值与校验是否一致，状态字段是否支撑状态全集，数据读写归属是否明确，汇总能否追溯明细，数量与成本变化是否保留事实或凭证。

### 3.5 页面操作

每个动作核对“入口 → 操作 → 校验 → 反馈 → 结果 → 后续去向”，识别文档有按钮无规则、规则允许无入口、只有成功无失败、状态变化无展示等问题。

### 3.6 跨域与验收

核对上游输入、下游输出、事实真源、部分失败、重试补偿、人工介入与完成判据；关键规则应能形成“前置条件 → 用户动作 → 系统结果 → 状态/数据变化 → 可见反馈”的验收场景。

每个主流程只能得出以下一种闭环结论：`已形成闭环` / `缺逆向流程` / `缺异常处理` / `缺数据后果` / `缺跨域完成判据` / `缺验收条件` / `信息不足，无法判断`。

## 4. 八类跨文档一致性检查

| 主题 | 比对位置与要点 |
| --- | --- |
| 状态名称与流转 | business-rule、state-machine、data-model、UI、原型中的状态含义、枚举与合法动作 |
| 字段与枚举 | data-model、business-rule、UI、原型中的必填、默认值、取值范围与枚举全集 |
| 数值与公式 | business-rule、专项 rules、UI 中的阈值、公式、判定顺序、排序与时间窗口 |
| 角色与权限 | permission-rules、business-rule、UI 中的操作可见性、数据范围与执行资格 |
| 页面与动作 | SKILL、UI、business-rule、assets 中的页面、按钮、反馈与导航 |
| 跨域职责 | consistency-spec 与相关模块规则中的事实归属、完成判据、失败补偿 |
| 公共能力引用 | Prerequisites 与模块说明是否同源，是否引用后又复制不同定义 |
| 核验与实现状态 | SKILL、consistency-spec、UI 是否一边写已支持、另一边写未核验或预留 |

端面、角色或权限造成的合理差异不属于冲突，但必须在对应文档中明确声明；文字不完全相同不等于不一致，业务语义互斥才是明确冲突。

## 5. 问题分类与严重程度

### 问题类型

- **明确冲突**：两处以上文档对同一事实给出互斥描述，并有双方原文证据
- **覆盖缺失**：按文档职责应当覆盖但实际未覆盖；“没提到”本身不能直接判冲突
- **表述歧义**：同一描述存在两种以上合理理解，无法确定唯一业务含义
- **无法核验**：缺少来源或证据，不能判断对错

### 严重程度

- **A**：核心状态、权限、公式、数据后果冲突，可能阻断研发或验收
- **B**：缺异常、缺页面反馈、文档与原型不一致，影响设计或验收
- **C**：措辞、命名、说明清晰度问题

严重程度只用于修复排序，不折算分数。

## 6. 单条诊断输出

每条诊断必须包含：

| 字段 | 要求 |
| --- | --- |
| 模块身份 | 仓库名 + 模块相对目录 |
| 诊断域与问题类型 | 使用本规范固定枚举 |
| 严重程度 | A / B / C |
| 真源文件及章节 | 权威来源与原文摘要 |
| 相关文件及章节 | 冲突、缺失或歧义位置与原文摘要 |
| 诊断结论 | 只陈述证据支持的结论 |
| 修复建议 | 指定建议修改的唯一真源及同步范围 |
| 复核点 | 修复后如何确认闭环或一致 |

没有原文锚点不得输出问题结论；无法找到证据时标记“无法核验”，不得将猜测写成问题事实。

## 7. 报告汇总

- 仓库摘要只列最重要的 A/B 级问题，完整诊断按模块归集
- 可展示诊断数量及环比变化，但不据此计算健康分、仓库分或质量升降
- 修复建议只供仓库负责人执行，评估系统不自动修改、删除或移动文档
- AI 无法完成语义诊断时，保留客观检查结果并登记“AI 诊断未完成”，不得降级为无依据结论

# health-report / 产品文档健康度报告生成

> 一句话定位：按项目对需求仓执行每周全量、只读的文档健康评估，读取上一发报日归档明细形成环比，产出可供下次基线读取的标准报告。检查规范以 [`health-check.md`](health-check.md) 为唯一真源，AI 诊断以 [`semantic-diagnostics.md`](semantic-diagnostics.md) 为唯一真源。

## When to Use

- 用户说「生成产品文档健康度报告 / 评估需求文档质量 / 文档健康评分」
- 周期性比较同一项目需求文档与仓库治理质量变化

## When Not to Use

- 需要定时自动跑 → 由报告配置模块「报告触发配置」承担，本 skill 只描述单次生成会话
- 需要校验文档与代码实现一致性 → 使用文档一致性报告生成 skill
- 需要修改、清理或迁移业务仓文档 → 本 skill 全程只读，不执行治理动作

## 参数解析

| 参数 | 取值 | 默认 |
| --- | --- | --- |
| 项目 | 报告范围配置中的 key（域/项目类型+稳定实体引用） | 服务端会话必传；外部会话由用户指定 |
| 计划发报日 | `yyyy-MM-dd` | 服务端任务给定；外部会话默认生成当天 |
| 规则版本 | 客观检查与 profile 的统一版本 | 由生成环境注入，禁止各仓自行变更 |
| 工作区 | 独立只读快照根目录 | 服务端注入；外部会话读取生成环境约定的配置 |
| 上期报告 | 同报告项上一发报日最新归档版本 | 服务端按归档数据提供；首次评估为空 |
| 推送 | 服务端固定不推送；外部会话默认推送 | 用户说「仅生成」时外部会话跳过推送 |

**范围边界**：基础实体与 N:N 执行映射只读引用 [项目管理](../../../研发管理/项目管理/SKILL.md)，key / 分支策略取报告范围配置；服务端和外部会话均携带类型（域/项目）+ 稳定实体引用及确认快照，不维护第二份范围。域检查整个主仓及确认映射中的需求文档，项目只检查主仓一级目录及该项目确认映射中的需求文档，根文件不计入项目；遵守 [#consumption](../../../研发管理/项目管理/references/business-rule.md#consumption)，跨范围汇总按稳定标识去重，不叠加域和子项目评分。固定排除 `busyming-skills-common`、`busyming-skills-design`，不建立其评估快照或计分，只检查业务仓对其引用；其他评分与完整性口径不变。

新范围仅自动成行，key / 分支策略齐备启用才生成；真源停用或远端确认缺失停止生成、不删归档。旧整体项目报告只能显式核对到对应域，保留原 key / 文件名，不猜测或复制到各项目；不同类型范围不直接混作同口径环比。不纳入范围外仓库、开发者副本或本地未提交改动。以上为已确认产品目标，不表示生产已上线。

## 执行流程

### Step 1 读取配置并建立只读快照

1. 确定项目、计划发报日、规则版本、输出目录与上期报告
2. 从需求仓清单排除 `busyming-skills-common` 与 `busyming-skills-design`，再按分支策略为其余业务需求仓建立独立只读快照，记录完整 commit；扫描期间不得修改快照内容
3. 仓库缺失或同步失败时标记该仓检查失败，继续其他仓，不使用仓外同名副本

### Step 2 应用 profile 并建立文件清单

按 [`health-check.md`](health-check.md) §3 确定每仓 profile，建立完整文件清单、排除项与特殊对象清单。再按 §4 建立 AGENTS、SKILL、references、HTML 引用关系，并将每个文件归入唯一分类。

### Step 3 客观检查与评分

1. 枚举各仓纳入评分的模块，执行 D1～D6 子项检查与 G1～G8 门禁
2. 计算模块原始健康分、健康等级、仓库模块子分 M、治理子分 G 与综合分 R
3. 对结构外候选文件只做客观计分；内容角色可由 AI 辅助标注，但不改变分数
4. 为每个确认问题生成证据、影响、修复对象、修复动作、优先级与复核点

### Step 4 AI 辅助诊断

按 [`semantic-diagnostics.md`](semantic-diagnostics.md) 建立需求事实表，执行六类闭环与八类跨文档一致性检查。每条诊断必须附原文锚点；无法完成时登记未覆盖范围，不得影响客观评分或中断其他模块。

### Step 5 读取上期基线并计算环比

1. 读取上期报告中的「仓库评分表」与「模块评分明细表」，不使用 AI 文字作为分数来源
2. 校验上期发报日、版本、规则版本与表格列；不可比时明确标记
3. 按仓库名 + 模块相对目录匹配身份，必要时参考 git 重命名记录；无法确认按移除 + 新增
4. 计算当前全量结果、两期同模块可比结果、新增/持续/已消除问题及仓库治理变化
5. 新增硬门禁直接判质量下降；分数差 ≥+5 为提升、≤-5 为下降，其余为持平；口径变化不直接下升降结论

### Step 6 生成报告并完整性自校

- 全文中文，标题：`产品文档健康度报告（{项目名}） - {yyyy-MM-dd}`
- 固定章节与表格见下方模板；仓库评分表和模块评分明细表列名不得改动
- 每仓文件分类合计必须等于文件总数；模块报告覆盖数必须等于枚举数
- 自校不通过时先补齐；仍无法补齐则在报告头部明确“全量自校未通过”及缺口，不得宣称全量完成

### Step 7 写文件、落库或推送

- 文件名：`doc_health_yyyyMMdd_<项目key>.md`
- **服务端生成会话**：产出回传服务端，由服务端校验、渲染并直接落库（版本递增、周索引），本 skill 不调用推送接口
- **外部会话旁路**：推送契约见 [`../../报告配置/references/data-source-api.md`](../../报告配置/references/data-source-api.md)；推送后回告 `reportId / versionNo / duplicated`，失败保留本地文件并说明错误

## 硬约束汇总

1. 业务仓只读，不自动修复，不提交或推送业务仓变更
2. 客观评分与 AI 诊断严格分离，未知项不扣分
3. 上期基线只取上一发报日最新归档版本，同发报日版本不算新评估
4. 固定表格列不得改动，文件与模块覆盖必须自校
5. 令牌与仓库凭证只从生成环境读取，禁止写入报告或本 skill

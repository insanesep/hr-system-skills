# 报告配置 业务规则字典

> 本文件为研发报告子域的规则真源：报告类型与命名、周期归属、触发生成入库、版本、渲染、权限、异常场景，以及本模块承载的报告范围配置与报告触发配置。各报告模块 SKILL.md 仅做导航，规则细节全部在此。

---

## 1. 报告类型与文件命名

子域固定承接五类报告，类型枚举不变。**范围集合不写死**：范围类报告由「报告范围配置」生效数据驱动（见 §3）。以下历史「项目维度/项目标识/项目key」命名为报告兼容标识，不再代表独立项目实体；实际归属必须关联范围类型（域/项目）与稳定实体引用，文件名继续使用现有 key，不能据 key 或名称猜测范围类型。故障报告仍为人工事件闭环，不新增为第六类自动报告。

| 类型编码 | 报告名称 | 项目维度 | 标准文件命名 | 内容梗概 |
|---------|---------|---------|-------------|---------|
| `WEEKLY_DEV` | 研发周报 | 无 | `weekly_dev_{yyyyMMdd}.md` | 提交统计、AI 分析总结、按人员分析、功能进展追踪、仓库分布、功能使用量（数据可得时）、MCP 工具用量（数据可得时） |
| `DAILY_DEV` | 研发日报 | 无 | `daily_dev_{yyyyMMdd}.md` | 前一自然日产出摘要：提交统计（次数与行数）、按人员分析、功能排期卡片流转、Qoder 用量（统计日自然日快照） |
| `CONSISTENCY` | 文档一致性校验 | 有（项目 key） | `consistency_{yyyyMMdd}_{项目key}.md` | 按项目校验全模块文档与代码对齐 |
| `DOC_HEALTH` | 产品文档健康度 | 有（项目 key） | `doc_health_{yyyyMMdd}_{项目key}.md` | 全量评估需求文档质量、仓库治理、环比与修复建议 |
| `PROJECT_PROGRESS` | 项目进度报告 | 无（固定 `_all`，项目组仅作正文分组） | `progress_{yyyyMMdd}__all.md` | 单份周期报告，按组展示功能排期、代码提交、团队人员、Qoder 使用与核心进展 |

**固定标识 `_all`**：仅 `PROJECT_PROGRESS` 使用，是其唯一新生成报告项，不对应域/项目基础实体；实际范围为全部可生成域/项目组的去重并集（§3.2）。真实 key 不含下划线，不可占用 `_all`；`_all` 本身不命中范围扩展，但必须核验全部参与范围，空范围不生成。历史单组报告仍可查阅，不再按组生成新报告。

**文件命名判定规则：**

- `yyyyMMdd` 为**发报日**（报告生成日期），非统计区间
- 服务端生成落库时，报告类型、项目标识与发报日由生成任务直接给定，文件名按上表规范生成
- 推送上报与手动补传入库时按文件名解析类型、项目与发报日；范围类报告的项目 key 必须命中「报告范围配置」生效数据，`PROJECT_PROGRESS` 则必须命中固定标识 `_all`，未命中或文件名不符合上述模式时按「无法识别」处理，需人工指定（见 §5.4）
- 历史遗留命名 `consistency_{yyyyMMdd}.md`（无项目后缀）按「无法识别」处理，人工指定类型与项目后兼容入库

## 2. 周期归属与周索引

| 概念 | 定义 | 用途 |
|------|------|------|
| 报告项 | 报告类型 + 项目标识（无项目维度的类型一项即一类） | 触发配置与齐全度统计的最小单位 |
| 发报日 | 报告生成日期 | 报告的唯一日期身份 |
| 所属周 | 发报日所在的**自然周**（周一 00:00 ~ 周日 24:00，东八区） | 周索引分组的唯一依据 |
| 所属日 | 发报日当日（东八区） | 日索引分组的唯一依据（仅 `DAILY_DEV`） |
| 统计区间 | 仅 `WEEKLY_DEV`、`DAILY_DEV` 与 `PROJECT_PROGRESS` 有：报告正文首部声明的统计窗口 | 详情页元信息展示，不参与分组 |

规则：

1. 周索引 = 按「所属周」倒序分组；组内先按类型固定顺序排列：`WEEKLY_DEV` → `CONSISTENCY` → `DOC_HEALTH` → `PROJECT_PROGRESS`，其中 `PROJECT_PROGRESS` 每周最多一条 `_all` 报告，不再按项目组排列；`DAILY_DEV` 不入周索引，走日索引 = 按「所属日」倒序逐日成行，当日行固定置顶（未入库也成行）
2. 每周齐全度 = 该周启用触发配置的报告项中已入库份数 / 应入库份数；某报告项缺失时该周标记「待补」，缺口展示快捷入口（立即生成 / 补传，仅 Web 且受按钮权限控制；`DOC_HEALTH` 仅提供立即生成）；日报齐全度按日统计 = 当日已入库 `1/1`，当日未入库展示 `0/1` 但不标「待补」，昨日及更早缺失日标 `0/1 待补`
3. 周标签格式：`2026 年第 36 周（08-31 ~ 09-06）`，周序号按 ISO 8601 周历计算；日索引行标签格式：`2026-10-20 周二`
4. 本周行仅周日（东八区）当天起展示：发报日为周日，周中（周一 ~ 周六）窗口上界收敛为上周，避免「待补」进行态噪音；周中已提前入库的本周报告随周日到来自然可见。日报不收敛：当日行始终置顶展示，无论是否已入库都提供「立即生成 / 补传」快捷入口（受按钮权限与触发配置启停约束；当日快照可持续刷新，重复入库走版本递增）；未入库时灰显「未入库」，齐全度只显示 `0/1` 不标「待补」（当日数据持续产生中）；昨日及更早缺失日灰显「待补」+ 快捷入口
5. 研发周报与项目进度报告的统计区间从 md 正文首部引用块解析（`统计区间：YYYY-MM-DD（周一）~ YYYY-MM-DD（周日）`）；研发日报统计区间为前一自然日全天（`统计区间：YYYY-MM-DD 00:00 ~ 24:00`，起止同日，报告日期即统计日）；解析失败时元信息降级为「—」，不阻断入库
6. 月周期的项目进度报告按发报日归入所属自然周，统计区间在元信息中原样展示

## 3. 报告范围配置

### 3.1 职责边界

| 数据 | 真源 | 本模块职责 |
|------|------|-----------|
| 域/项目清单、状态与稳定实体 | [域及项目管理：来源](../../../研发管理/域及项目管理/references/business-rule.md#source)、[实体](../../../研发管理/域及项目管理/references/data.md#entities) | 只读引用；域=仓、项目=一级目录，清单同步获得，不手工增删 |
| 项目到实现仓与路径的 N:N 映射 | [执行映射](../../../研发管理/域及项目管理/references/business-rule.md#execution-mapping) | 只消费确认结果，不在报告维护映射 |
| 人员身份、角色、参与关系、自动报告范围 | [产研人员管理](../../../研发管理/产研人员管理/SKILL.md) | 只读消费，不建人员实体或名单 |
| 排期卡片与流水 | [功能排期管理](../../../研发管理/功能排期管理/SKILL.md) | 消费事实，不迁移排期职责 |
| 全局 key、分支策略、报告扩展启停 | 本模块「报告范围配置」生效数据 | 维护报告专属扩展 |

### 3.2 扩展规则

1. 范围由**类型（域/项目）+ 稳定实体引用**确定，仅从启用有效域/项目派生扩展并自动成行，不另建基础实体，不手工新增或删除行。新行仅为待配置，不表示已经可以报告
2. **key**：范围类报告的文件命名与报告项标识；小写字母 / 数字 / 连字符，全局唯一，**首次保存后锁定**。项目进度报告仅使用固定 `_all`，各组 key 只用于正文分组排序与范围引用，不再生成单组文件
3. **分支策略**：统计基准分支，二选一：`master` / 最近 `release/*` 且防回退落后主干。key 与分支策略均齐备且扩展启用后，才联动对应报告触发配置
4. **范围消费**：遵守 [#consumption](../../../研发管理/域及项目管理/references/business-rule.md#consumption)。域范围为整个主仓及确认的执行映射；项目范围为主仓对应一级目录及该项目确认的执行映射。项目不把主仓根文件或其他项目目录算入自身；引用根导航不等于根文件进入项目指标。跨项目同名实现不混入
5. 生成入参包含范围类型、稳定引用、真源快照与确认映射，以及报告扩展 key、分支策略。域/项目停用或远端确认缺失即停止生成并同步停用关联触发，不删除扩展、报告或历史版本；恢复后保留原 key 与归档，核验后再启用
6. 历史旧「整体项目」报告只能经显式核对关联为对应域级范围；未核对保留历史与待核对状态，不猜测对应，不复制到各子项目，不更改原 key、文件名或版本。域级与项目级范围不同，不直接混作同口径环比
7. `_all` 取全部有效且扩展已配置启用范围的并集，在同一报告内先按域稳定 ID、卡片稳定 ID、人员稳定 ID、源仓稳定 ID 与 commit SHA 去重，再计算全量汇总；域与其子项目重叠数据只计一次。共享执行仓与跨项目提交按真源消费规则归属，各组明细不直接相加为总计，比率与人均指标按汇总分子、分母重算
8. 新范围不增加报告种类；产品文档健康度仍排除 common/design，其余类型继续保留各自生成、计数与查阅口径。以上是已确认产品目标，不表示生产上线完成

### 3.3 统计人员范围

统计范围唯一引用 [产研人员管理 #report-scope](../../../研发管理/产研人员管理/references/business-rule.md#report-scope)，身份与冲突裁决引用 [#identity](../../../研发管理/产研人员管理/references/business-rule.md#identity)，参与域/项目引用 [#membership](../../../研发管理/产研人员管理/references/business-rule.md#membership)；报告不复制归一算法、冲突规则或维护字段，不按名单顺序取第一人。

- 周报、日报、项目进度报告、外部会话和 Qoder 数据包采用真源自动名单的同一生成快照，保留历史；新增研发/产品/架构/设计角色不按角色重建名单，同一门户稳定 ID 多角色仅计一人。项目进度报告按项目组参与关系过滤，产品与研发人数按生成时当前有效角色分别计数；角色专项分析只归对应职责证据，不将同人的全部贡献混算到每个角色
- Git、卡片及 Qoder 人员维度只计快照名单内人员；名单外不计入、不点名。需求吞吐与范围内仓库清单保持各自全量口径，其中名单外姓名显示「—」
- 空名单或人员真源未取得时拒绝生成人员产出报告并提示核验真源；Qoder 团队范围返回空并标明原因，组织「全部成员」不作为报告兜底名单
- Qoder 无账号、映射未取得、自然日快照缺失或源失败均标「未取得」，不伪造 0 用量；只有源成功且明确零值才计 0，不把部分成员有数标为完整团队总量
- 功能使用量与 MCP 工具用量仅有聚合值，不做人员名单过滤，不在按人员章节点名；外部会话提交时关联采用的名单快照，归档不按当前名单重新过滤历史

## 4. 报告触发配置

### 4.1 配置项

每个报告项维护一条触发配置，真源为本模块「报告触发配置」页生效数据（变更留痕可溯），不引用仓库内或本机配置文件：

| 配置项 | 说明 |
|--------|------|
| 报告项 | 报告类型 + 项目标识（`WEEKLY_DEV` / `DAILY_DEV` 无项目维度） |
| 触发方式 | 定时 / 手动，至少启用一种，可同时启用 |
| 定时规则 | 周期（每日 / 每周 / 每月）+ 星期或号（每日无需）+ 时间（东八区）；到点自动创建生成任务。计划点短暂不可用时，恢复后在下一计划点之前补跑最近一次，补跑报告的发报日与统计窗口仍按原计划点计算 |
| 类型参数 | 文档一致性校验：回看天数（增量划定检查范围）；产品文档健康度：无类型参数（每周全量评估）；项目进度报告：统计周期（周 / 月） |
| 启停 | 停用即不再定时触发，手动触发同步禁用；历史报告与生成记录保留可查 |

### 4.2 联动规则

项目维度报告类型（`CONSISTENCY` / `DOC_HEALTH`）的配置行随「报告范围配置」联动——扩展启用即按类型各生成一条配置行（默认定时每周），扩展停用同步停用；该类配置行不可手工新增或删除，仅可编辑规则、参数与启停。`WEEKLY_DEV` 与 `DAILY_DEV` 配置行各内置唯一，不随扩展联动；`PROJECT_PROGRESS` 仅内置一条 `_all` 配置行（默认定时每周），不随项目组扩展新增配置行、不可删除，仅可编辑统计周期、规则与启停。

### 4.3 立即生成与失败重试

- 「立即生成」手动触发创建生成任务，成功反馈后跳转生成记录；同一报告项存在进行中任务时提示并拒绝（见 §5.2）
- 生成记录按配置行归集：触发来源 / 状态 / 统计窗口 / 耗时 / 失败原因 / 产出版本；失败任务可「重试」，重试即新建任务并关联原任务

## 5. 触发、生成与入库

### 5.1 触发入口

触发入口为 §4 触发配置（定时到点或 Web 端「立即生成」），触发配置生效数据是生成流程的输入。

### 5.2 服务端生成（主通道）

1. 触发（定时到点，或 Web 端「立即生成」手动触发）创建生成任务，入参包含报告项、计划发报日、统计窗口、类型参数、范围类型与稳定实体引用、确认映射快照；人员产出报告与项目进度报告另带产研人员管理的生成名单快照。`PROJECT_PROGRESS` 每次触发只创建一个任务，携带全部启用项目组的范围快照与人员名单，按 §3.2 去重后生成一份按组展示的报告
2. 服务端通过 Qoder SDK 创建生成会话，工作区挂载报告类型对应的生成 skill（研发周报：[`../人员产出报告/references/dev-report.md`](../../人员产出报告/references/dev-report.md)；研发日报：[`../人员产出报告/references/daily-report.md`](../../人员产出报告/references/daily-report.md)；一致性校验：[`../文档一致性报告/references/consistency-report.md`](../../文档一致性报告/references/consistency-report.md)；产品文档健康度：[`../产品文档健康度报告/references/health-report.md`](../../产品文档健康度报告/references/health-report.md)；项目进度报告：[`../项目进度报告/references/progress-report.md`](../../项目进度报告/references/progress-report.md)，各为该类报告生成逻辑唯一真源）；生成所需配置（工作区、项目映射、数据源基址与令牌）由服务端注入
3. 会话产出报告文件由服务端直接落库：校验命名 → 解析标题与统计区间 → 渲染 HTML 并提取大纲（§6）→ 版本递增入库（§5.5）
4. 任务状态机：`生成中 → 成功（关联产出版本）/ 失败（记录失败原因）`；失败任务可在生成记录中重试，重试即新建任务并关联原任务
5. 同一报告项同时刻仅允许一个进行中任务：定时到点时上一任务未完成则本次不并发，后续扫描在宽限窗口内继续尝试；手动触发遇进行中任务时提示并拒绝
6. 生成耗时超上限（2 小时）判定失败，不产出报告版本

### 5.3 推送上报（旁路通道）

外部生成会话（如本地排障重跑）产出的报告经推送上报入库：

- 携带：md 文件、报告类型、发报日（项目类报告带项目标识）
- 服务端按 §1 命名规则二次校验类型与发报日，不一致时**以文件名为准**并记录告警日志
- 幂等：同报告项同发报日同内容（文件哈希一致）重复上报不产生新版本，直接返回已有报告；`PROJECT_PROGRESS` 按统计周期判重，同周期重复上报进入同一报告项的版本流程
- 鉴权失败：401（token 不匹配）/ 403（服务端未配置 token，fail-closed）

### 5.4 手动补传（兜底通道）

- 仅 Web 端开放，权限 `devhubReportUpload`；`DOC_HEALTH` 不开放手动补传，缺失报告通过立即生成或外部生成会话推送上报入库
- 上传时系统按文件名自动识别类型与发报日；识别失败时由用户在表单中手动指定
- 手动补传记录上传人，来源标记为「手动补传」

### 5.5 版本规则

- 唯一键 =（报告类型 + 项目标识 + 发报日）；`PROJECT_PROGRESS` 例外为（报告类型 + `_all` + 统计周期类型 + 统计区间），每个自然周或自然月仅一条报告项，同周期重复入库 → 版本号递增，旧版本保留可查
- 列表与详情默认展示**最新版本**；详情页可切换历史版本（只读）
- 版本内记录：文件名、文件哈希、来源（服务端生成 / 推送上报 / 手动补传）、入库时间、操作人
- 报告**不允许删除**（审计留痕）；错误入库的报告以新版本修正

### 5.6 文件约束

| 约束项 | 规则 | 超限处理 |
|--------|------|---------|
| 格式 | 仅 `.md`（UTF-8） | 拒绝入库，提示「仅支持 Markdown 文件」 |
| 大小 | ≤ 2MB | 拒绝入库，提示压缩图片或拆分 |
| 标题 | md 首个 `#` 一级标题作为报告标题 | 缺失时以「类型名 + 发报日」兜底 |

## 6. Markdown 渲染规则

1. **渲染时机**：入库时一次性渲染为 HTML 并随版本持久化，Web 详情页与 App WebView 均消费服务端产物，页面仅提供排版样式，不重新渲染原始 Markdown；评分摘要等结构化内容可从原始报告提取，不替代正文渲染。大纲与图片移除口径由同一服务端渲染管线生成，避免端间分叉。
2. **大纲提取**：从渲染产物的 `h2` / `h3` 标题提取锚点目录，详情页侧边（Web）/ 抽屉（App）展示，点击滚动定位
3. **安全**：渲染产物必须经 XSS 白名单过滤（仅保留排版标签与表格 / 代码块 / 列表），剥离 `<script>`、内联事件与外部资源引用；md 中的图片若为外链直接丢弃并占位「[图片已移除]」
4. **表格与代码块**：表格横向滚动容器包裹；代码块保留语言标记与等宽字体，不换行
5. 重新渲染仅发生在管理端「重新渲染」运维动作（如渲染器升级），不产生新版本号

## 9. 异常与边界场景

| 场景 | 处理 |
|------|------|
| 某周部分报告项未入库 | 周分组正常展示已入库报告，缺失项灰显「未入库」+ 立即生成 / 补传入口（Web，受按钮权限控制；`DOC_HEALTH` 仅提供立即生成） |
| 日报当日未入库 | 当日行始终置顶展示为「未入库」+ `0/1`（不标「待补」，当日行统计窗口为当日 00:00 ~ 24:00，数据持续产生中），提供立即生成 / 补传入口；昨日及更早缺失日灰显「未入库」+ `0/1 待补` + 立即生成 / 补传入口 |
| 日报当日已入库需刷新 | 当日行保留立即生成 / 补传入口；重新生成或补传按版本递增产生新版本，索引默认展示最新版本 |
| 生成任务失败 | 任务标记失败并记录原因，不产生报告版本；生成记录中可重试 |
| 定时到点时同报告项存在进行中任务 | 本次不并发，后续分钟继续尝试；超过该计划点的下一计划点后不再补跑 |
| 调度服务在计划点短暂不可用 | 恢复后在下一计划点前补跑最近一次，报告按原计划发报日归档；不回溯多个周期 |
| 触发配置在计划点之后变更 | 本周期不补跑，变更从下一个计划点起生效 |
| 触发配置停用 | 不再定时触发且手动生成禁用；历史报告与生成记录保留可查 |
| 同步获得新增启用有效域/项目 | 报告范围扩展自动成行，key / 分支策略待补（标「待配置」），不立即生成报告 |
| key 重复或格式非法 | 拒绝保存并提示；首次保存后不可改 |
| 人员身份存在冲突 | 按人员真源 #identity 裁决；报告不按名单顺序归人 |
| 自动统计范围为空或真源未取得 | 人员产出报告拒绝生成，提示核验产研人员管理；Qoder 团队范围返回空并标明原因，不扩大为组织全量 |
| 名单内人员无 Qoder 账号或用量源缺失 | 标「未取得」，不补 0；部分用量不得冒充完整团队总量 |
| 域/项目停用或远端确认缺失 | 扩展及关联触发同步停用并停止生成；历史归档和 key 保留 |
| 历史旧整体项目范围未核对 | 只保留原归档，不猜测域对应、不复制到各项目；显式核对后按对应域关联 |
| 扩展停用 | 关联触发配置行同步停用（不再定时触发且手动禁用）；历史报告与生成记录保留可查 |
| 发报日落在未来 | 拒绝入库（防文件名笔误），提示「发报日不可晚于今天」 |
| 补传 / 推送项目进度报告文件标识为 `_all` | 按唯一周期总报告入库，不校验单组 key；其他类型使用 `_all` 或项目进度报告使用单组 key 均按「无法识别」处理，历史单组归档除外 |
| 同一周出现两个不同发报日的同报告项报告（如周一补发） | 一般报告视为两条独立报告，均归入各自发报日所属周；`PROJECT_PROGRESS` 不按发报日拆分，同统计周期只保留一条报告项并递增版本 |
| md 正文为空或仅标题 | 允许入库，详情页展示空态提示「报告内容为空」 |
| 服务端生成、推送上报与手动补传并发同唯一键 | 以先落库者为当前版本，后到的递增为新版本，不报错 |
| 时区 | 全部日期口径为东八区；周归属、发报日均按东八区零点切分 |

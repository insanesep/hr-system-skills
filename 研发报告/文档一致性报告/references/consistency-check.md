# 一致性检查规范

检查 SKILL/references/assets 三件套一致性，并分析代码实现是否完整覆盖 SKILL 需求。
**每个项目（业务线）单独一份报告**，跨项目混比会产生假缺失。

## 多项目作用域

项目集合不写死：检查哪些项目、各项目的 SKILL 仓库 / 扫描根目录 / 代码仓清单，一律以「项目映射配置」生效数据（外部会话为会话配置 `projects`）为准。**项目边界红线：**

1. 扫描 SKILL 只进入本项目 SKILL 仓库的 `skill_roots` 目录，其他仓库/项目目录的 SKILL 不得计入
2. 查找功能实现只在本项目代码仓库内搜索；**严禁**因在别的项目仓库搜到同名类/目录就判定「已实现」
3. 本项目代码仓库内确实找不到实现时按「缺失」判定，并说明已搜索的仓库与关键词

## 检查范围划定（lookback_days 语义）

`lookback_days` **仅用于划定「本次检查哪些模块」**，依据是 **SKILL 仓库中的变更模块**，不是限制代码检查时间窗口。

| lookback_days | 含义 |
|---------------|------|
| `> 0`（默认 7） | 仅检查最近 N 天内 SKILL 仓库发生变更的模块（变更过的 SKILL.md / references/ / assets/ 所属模块目录） |
| `0` / 负数 | 全量扫描所有 SKILL 模块 |

关键澄清：

1. 被圈定的模块，其 SKILL.md、references/、assets/、对应代码都按**当前最新状态全量对比**，不只看近 N 天 diff
2. 变更识别以 SKILL 仓库 `git log` 为准
3. 报告头部须呈现本次「划定范围」来源，列出入选模块名及触发其入选的变更文件

## 执行步骤

### 第一步：划定检查范围

增量模式（默认，lookback=7）：

对每个变更文件向上找到含 SKILL.md 的模块目录，去重后即为检查范围。若无变更，输出「最近 N 天 SKILL 仓库无变更，无需检查」并结束本项目。

全量模式（lookback≤0）：

每个 SKILL.md 所在目录为一个检查模块。

### 第二步：逐模块检查

对每个模块执行以下 5 个维度：

**1. 文档三件套对齐（结构检查）**

| 检查项 | 规则 |
|--------|------|
| SKILL.md 存在 | 必须存在，是检查入口 |
| references/ 目录 | 必须存在，包含技术实现文档 |
| assets/ 目录 | 可选；SKILL 引用了原型/截图则必须存在 |
| references 文档命名 | 应含 data-model.md / implementation-steps.md 等标准文档 |
| 交叉引用 | SKILL.md 中引用的 references 文件必须存在 |

**2. 代码实现完整性（逻辑判定）**

从 SKILL.md 提取功能点，在本项目代码仓库中按模块名定位 package/目录、按功能关键词 grep Controller/Service/View、读取关键代码片段后判定：

- **完整**：代码中有明确的接口/逻辑对应功能点
- **部分**：有相关实现但不完整
- **缺失**：完全未找到对应代码实现

**3. SKILL.md 与 references 重复/冗余检查**

识别重复模式：完整 DDL 与字段说明、Java/Vue 代码片段、详细 Request/Response 表、与 business-rule.md 同粒度的计算公式/枚举。
区分「合理摘要+相对路径链接」（合理）与「同等粒度技术细节拷贝」（冗余，风险项中给出重复块行号区间）。

**4. SKILL.md 长度检查**

`wc -l` 统计实际行数：≤100 行正常；101-150 行「建议关注」；>150 行风险项强提示并给出拆分方向（数据模型→data-model.md、实现步骤→implementation-steps.md、业务规则→business-rule.md）。

**5. 代码 → 文档反向偏差检查（最关键）**

正常链路是 SKILL → assets → references → 代码 单向生成；本维度反向比对，从代码出发逐层回看：

| 比对 | 要点 |
|------|------|
| 代码 vs references/data-model.md | 实体字段、列名、类型、长度、索引、唯一键（重点关注 `deleted_flag` 红线） |
| 代码 vs references/implementation-steps.md | Controller/Service 方法签名、包路径、类名、依赖（Job/MQ/缓存/外部 API） |
| 代码 vs references/api-spec.md | URL、HTTP Method、Request/Response DTO 字段、必填/可选、错误码 |
| 代码 vs references/business-rule.md | 计算公式、枚举值、阈值常量、代码有而文档无的分支逻辑 |
| 代码 vs assets/ | 前端 .vue 页面字段、按钮、表格列、交互流程 vs 原型截图/HTML Demo |
| 代码 vs SKILL.md | 代码已实现但 SKILL 未提及 / SKILL 已描述但代码走样 / 业务规则被静默修改 |

偏差分级：

| 等级 | 定义 | 处理建议 |
|------|------|----------|
| 🔴 严重 | 字段/接口契约/业务规则不一致，影响数据正确性或对外协议 | 立即修复，二选一对齐 |
| 🟡 中等 | 代码新增文档未提及的字段/分支，或文档描述超前于代码 | 回写文档或裁剪代码 |
| 🟢 轻微 | 命名差异、注释缺失、可选字段顺序差异 | 建议同步 |

每个偏差项必须给出：偏差位置（代码文件路径+行号区间 / 文档章节锚点）、偏差类型、当前实现（代码关键片段）、文档期望、修复方向（明确「改代码对齐文档」or「改文档回写代码」+ 文件路径）。

### 第三步：生成报告

按下文模板输出完整 Markdown。标题：`一致性检查报告（{项目名}） - {yyyy-MM-dd}`（生成当天日期）。

### 第四步：完整性自校（必须执行）

1. 统计报告实际包含的模块数，与第一步枚举/划定的模块总数比对
2. 不一致则补齐缺失模块（哪怕一行摘要），直到两数相等
3. 总体摘要中明确写出「枚举模块总数: X / 报告覆盖模块数: X」

## 硬约束

1. **完整性红线**：报告覆盖模块数必须与枚举/划定范围内模块总数一致，严禁遗漏；禁止「其余模块省略」「检查结果类似」等跳过性描述；模块过多时对无问题模块用一行紧凑格式，但不得省略
2. **项目边界红线**：跨项目比对一律无效
3. 容错：单个模块分析失败降级为仅结构检查，不中断其它模块
4. 所有检索、读取、比对工作在本会话内直接完成，可批量并行调用读取/搜索工具提速

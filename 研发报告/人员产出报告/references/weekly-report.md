# 周报生成规范

综合 Git 提交、功能排期、Qoder 用量、功能使用量、MCP 工具用量五项数据源，生成按人分组的综合研发周报。

源失败或拉取失败标「未取得」，不得以 0 或推测值代替；Qoder 无账号、身份关联失败、记录非法或来源查询失败同样处理。已确认 Qoder 账号的成员在自然日无快照记录时按无用量明确补 0，不把无事件日期误判为来源缺失；部分成员身份或来源失败不冒充完整团队总量。以下为已确认产品目标，不表示数据源或生产迁移已完成。

## 数据源说明

| 数据源 | 来源 | 反映维度 |
|--------|------|----------|
| Git 提交记录 | 程序采集完整窗口全部作者，引用人员真源身份结果后由程序校验并汇总；正文使用选后统计与提交说明，不执行克隆或计数 | 实际编码产出（次数与新增 / 删除行数）、变更的模块和仓库 |
| 功能排期卡片 | 外部会话：busyming MCP `busyming_feature_schedule`；服务端会话：调用方会话数据提供（排期日、领取或完成任一落在窗口内的卡片，含领取 / 完成时间） | 任务计划、完成状态、窗口内流转、紧迫度 |
| Qoder 用量 | 服务端会话由调用方直接注入按名单过滤后的成员用量、请求次数与模型分布（窗口内各自然日快照合计）；外部会话调用用量 API 时固定研发团队范围 | AI 辅助工具使用程度（Credits、折算金额、请求次数、次均消耗） |
| 功能使用量 | devops 使用情况报表 API | 各功能**页面路由**的实际点击量与活跃用户 |
| MCP 工具用量 | foundation MCP 工具统计 API | 团队通过 **AI 客户端**调用后端能力的程度 |

> 「功能使用量」与「MCP 工具用量」是两个不同口径：前者是人在管理后台点页面，
> 后者是人在 AI 客户端（Claude / Qoder / Cursor）里让模型调工具，不要合并统计或互相推算。

## 计数纪律（必须遵守）

> Git 按「程序全作者采集、引用人员真源身份结果作者、程序校验并汇总、正文模型生成报告」执行，具体流程见 [`dev-report.md`](dev-report.md) Step 3。正文只引用程序提供的选后统计，不重新计数或凭印象估算。

1. 采集覆盖完整统计窗口内 master 与 feature/* 分支的全部作者，不统计 tag，不按名单姓名或已登记别名提前删除作者。程序按提交 SHA 全局去重、剔除合并提交；跨仓/项目归属只采用项目管理 #consumption 的确认结果，域和子项目重叠数据不叠加。
2. 程序逐提交取得 numstat 新增 / 删除行数，二进制文件不计行数。作者识别模型不得修改已采集提交或行数；映射校验通过后由程序按选中作者重新汇总总计、各仓与各人数字，提交数及行数均须打平。
3. 「各仓库提交分布」必须覆盖成功采集的每个仓库，含选后 0 提交仓；采集失败的仓库不补 0。项目分组只采用冻结仓库边界，重叠或冲突事实须标明且不相加；总计必须等于稳定标识去重后的选中提交集合，不把共享仓全量重复计入各项目。
4. 正文模型只使用程序提供的选中成员、选后数字与提交说明，不重新筛选作者、改写映射、自行克隆仓库、运行 Git 计数或根据代表性主题条目推算数量。定性合并工作内容不改变任何计数。
5. 作者映射的重复、遗漏或非法结果须使生成失败，不能按名单顺序强行归人，也不能作为数据源缺失省略。

## 人员范围（强制）

- 数据包与外部会话统一引用 [项目管理 #report-scope](../../../研发管理/项目管理/references/business-rule.md#report-scope) 的生成名单快照，不自行维护或增减；空名单或真源未取得拒绝生成，名单外负责人、开发人与 Qoder 成员不计入、不点名
- Git、Qoder 与卡片的身份归一和冲突裁决只引用 [#identity](../../../研发管理/项目管理/references/business-rule.md#identity)，不复制算法、不按名单首人归属，不由模型自主认定别名；程序只接受已验证到门户稳定 ID 的映射，正文不改映射、重计或扩大事实集合
- 同人多角色去重，不按研发/产品/架构/设计重建名单；专项分析不混算职责，参与域/项目只读引用 [#membership](../../../研发管理/项目管理/references/business-rule.md#membership)
- 「参与人数」仍为名单内有选中提交人数，不等于自动名单人数；无产出仅在各源成功确认后才认定，Qoder 未取得不是无用量。名单快照及映射依据随归档保留，不因当前角色或姓名变化改写历史
- 功能排期卡片只统计负责人或开发人确定命中名单的卡片；Qoder 用量只使用数据包提供的名单内数据，不自行扩大范围
- 项目级数据（需求吞吐、仓库清单）保持全量；其中需求提交人等人员姓名按名单脱敏，名单外显示「—」
- 功能使用量、MCP 工具用量只有聚合值，不返回人员明细，不做名单过滤，也不在按人员章节中点名
- **筛选依据**：完整选中及排除映射与理由保存在任务工作区审计 JSON。报告附录只引用程序提供的选中作者姓名、邮箱、对应名单成员及理由；名单外或未选中作者不展示姓名、邮箱或逐人排除理由，仅展示排除作者数量

## 仓库归属分组

服务端与外部会话统一采用 [项目管理 #consumption](../../../研发管理/项目管理/references/business-rule.md#consumption) 的生成快照范围与归属结果；报告 key 与分支策略来自报告范围配置，不以外部项目清单另建实体或猜测归属。

- **项目范围**：生成快照中的 harness 工程及代码服务仓，同项目重复仓按稳定仓标识去重；不按主仓一级目录创建项目或推定归属
- commit 与卡片按原有稳定标识口径去重，跨项目重复事实不得累加。个人总计与其项目、未归属明细采用同一选中提交集合；个人项目明细须同时满足冻结成员关系与仓库边界
- 文档/SKILL 产出与代码产出分别分析；未归属数据按真源消费结果注明，不从工作区任意纳入仓库。真源停用或远端确认缺失停止对应范围生成

## 输出格式规范

报告按以下章节顺序输出，源未取得的指标标「未取得」，不补 0；标题格式：`研发周报 - {yyyy-MM-dd}`（生成当天日期）。标题下须声明统计区间（`统计区间：YYYY-MM-DD（周一）~ YYYY-MM-DD（周日）`，取数据包统计区间，保证可解析入库）。

### 1. 统计摘要

- 统计范围：研发团队名单（N 人）
- 本周总提交数（含新增 / 删除行数）/ 参与开发人数 / 涉及仓库数量（均按名单内作者统计）
- 功能排期任务总数 / 已完成 / 进行中 / 待开发，窗口内领取数 / 完成数（按名单内人员统计）
- Qoder 团队总用量 (Credits) / 折算金额（元）/ 总请求次数 / 次均消耗（名单内成员合计；源未取得标「未取得」，仅完整且明确零值才计 0）

### 2. AI 分析总结

- 核心进展（最重要的 3-5 个功能/模块推进情况）
- 潜在风险（从提交模式、功能排期进度判断的风险信号）
- 下周建议

### 3. 按人员综合分析（核心章节）

对名单内每位有数据的成员综合输出：

- **代码产出**：保留本周个人提交次数与新增 / 删除行数总计；多项目人员在此项内按项目展示对应次数、行数、主要工作、关键功能点及涉及仓库和模块，同功能多次提交只在同一项目内合并；单项目人员保持简洁展示。项目数字和提交归属只引用程序基于生成快照的结果，未归属、缺少快照与部分采集按[业务规则](business-rule.md)分别呈现
- **三项结构**：代码产出、功能排期任务与 Qoder 用量保持个人层级；项目小节只细分代码产出，不把卡片或 Qoder 拆成重复项目统计，不按项目分摊用量或金额
- **功能排期任务**：任务总数、完成数、进行中、待开始；完成率；窗口内领取 / 完成的卡片；各任务详情（标题、负责人、领取开发人、排期/领取/完成时间）；时间分析（排期→领取响应速度、领取→完成开发耗时）
- **Qoder 使用情况**：本周 Credits 与折算金额（Credits × 0.15 元，即 Credits ÷ 2000 × 300）、请求次数、次均消耗；团队占比；**主要模型分布**（来自 model-pivot）（源未取得标「未取得」，仅完整且明确零值才计 0）
- **综合评价**：功能排期实际进展 vs 计划；Qoder 使用量与产出的关联分析（Qoder 数据缺失时不写关联分析）

人员默认按客观产出贡献度从高到低排序：依次比较窗口内完成的功能排期卡片数、提交次数、新增行数、Qoder Credits 用量，前一项并列再比较后一项，四项均并列时按统计人员名单顺序；某项数据源整体缺失时跳过该比较项，不按 0 补齐。不计算或展示贡献度分值与名次。

人员名称跨数据源可能不一致；Git 作者只按程序验证后的选中映射归入名单姓名，排期与 Qoder 沿用代码的确定匹配结果。正文不再自行推断别名或维护固定映射表。

### 4. 功能进展追踪

从 commit message 和功能排期卡片提取功能关键词，汇总为表格：`| 功能点 | 负责人 | 状态 | 涉及仓库 |`

状态判定：含 feat/新增/实现 → 开发中；fix/修复/bugfix → 修复中；refactor/重构/优化 → 优化中；docs/文档 → 文档完善。

### 5. 各仓库提交分布

按**项目（业务线）分组**统计各仓库**名单内作者**的提交次数与新增 / 删除行数（含 0 提交仓，标注 0），给出每个项目的提交与行数小计，标注热点模块；名单外提交不计入，各仓小计与总计必须打平。

### 6. 功能使用情况（独立章节，无数据则整节省略）

将功能排期卡片中本周完成/在开发中的功能，与功能使用量报表中的路由关联分析：

- 主表格：功能名称 / 对应路由 / 完成或领取日期 / 该日期使用量 / 本周总点击 / 负责人
- 重点交付但未触发（inactive）的功能独立高亮提示风险
- 热点路由（点击占比靠前）标注出来

### 7. MCP 工具使用情况（独立章节，无数据则整节省略）

- **KPI 汇总**：总调用次数 / 使用人数 / 被用工具数占注册总数 / 成功率 / 平均耗时
- **业务域分布**：哪些业务域的 AI 能力真被用起来了
- **工具排行**：调用量 TOP 工具（使用人数、成功率、平均耗时）
- **零调用工具风险**：已注册但本周无人调用的工具，需推广或确认工具描述是否让模型看不懂

硬约束：

1. 工具名与业务域直接用接口返回的中文名（`toolNameCn` / `scopeCn`），不要自行翻译、改写或补全英文名
2. 本章节「使用人数」是去重聚合值，接口不返回具体人名，**不要**把 MCP 工具使用摄到「按人员综合分析」里点名，也不要猜是谁在用
3. 不要把 MCP 调用量与 Qoder Credits 或页面点击量相互推算——三者计量口径完全不同
4. 数据源未取得时标「未取得」，不伪造指标或人员归属；源确认完整且无记录与源缺失分开处理

### 8. 口径说明

- 统计区间为最近一个以周日收尾的自然周周一 00:00 至周日 24:00（东八区）
- 提交次数与新增 / 删除行数为程序按验证后选中映射汇总的同一提交集合（master 与 feature/* 分支、不统计 tag、SHA 全局去重、剔 merge、逐提交 numstat，二进制文件不计行数）
- Qoder 用量、请求次数、次均消耗为窗口内各自然日快照合计；折算金额 = Credits 用量 × 0.15 元

### 9. 附录：Git 作者筛选依据

置于口径说明之后、报告生成时间之前。Git 成功采集时，引用程序提供的选中作者姓名、邮箱、对应名单成员与判断理由，并展示排除作者数量；选中为空时不补作者，只引用排除数量。完整映射与逐人排除依据仅保存在任务工作区审计 JSON，名单外或未选中作者的姓名、邮箱不出报告。正文不得改写已验证的映射或理由。

### 10. 章节输出模板

> 模板以多项目人员为例；单项目人员保留个人总计、主要工作与涉及仓库，无需重复项目小计。存在未归属提交时追加「未归属项目」明细；项目部分采集时标「已采集小计」并列出未取得仓库。附录按上一节要求追加。源缺失时相应指标标「未取得」，不生成伪造数值或关联分析。

## 分组与降噪规则

1. **按人员分组**：只按程序验证后的选中 Git 作者映射归入名单成员，与排期、Qoder 的代码确定匹配结果合并；未选中作者不出现
2. **合并同功能提交**：同一成员在同一项目内连续多次提交到同一模块，可合并为一条功能描述；跨项目即使功能同名也分开描述，不改变提交次数或行数
3. **去除噪音**：合并提交已由程序剔除；正文定性分析可省略仅改动 .gitignore/.idea 等非业务主题，但不得从权威提交次数或行数中扣减这些记录
4. **中文输出**：所有描述使用中文

## SKILL/文档类仓库额外规则

分析各项目的 SKILL 仓库（以「报告范围配置」生效数据为准）时：

- 从文件路径提取模块名（如 `<项目扫描根目录>/<业务大类>/xxx/SKILL.md` → 模块 xxx）
- 项目归属仅采用生成快照的仓库映射；文件路径只用于提取项目内模块，不据此创建或改分项目

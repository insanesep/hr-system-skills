# 周报生成规范

综合 Git 提交、功能排期、Qoder 用量、功能使用量、MCP 工具用量五项数据源，生成按人分组的综合研发周报。

任一数据源无数据或拉取失败时，对应章节、指标条目与人员字段直接省略，不在报告中写「无数据」「拉取失败」等说明，也不得以 0 或推测值代替。

## 数据源说明

| 数据源 | 来源 | 反映维度 |
|--------|------|----------|
| Git 提交记录 | 外部会话：`scripts/collect_commits.sh` 输出（权威计数）；服务端会话：agent 按调用方提供的仓库清单与云效凭证自行克隆采集（纪律相同） | 实际编码产出（次数与新增 / 删除行数）、变更的模块和仓库 |
| 功能排期卡片 | 外部会话：busyming MCP `busyming_feature_schedule`；服务端会话：调用方会话数据提供（排期日、领取或完成任一落在窗口内的卡片，含领取 / 完成时间） | 任务计划、完成状态、窗口内流转、紧迫度 |
| Qoder 用量 | 服务端会话由调用方直接注入按名单过滤后的成员用量、请求次数与模型分布（窗口内各自然日快照合计）；外部会话调用用量 API 时固定研发团队范围 | AI 辅助工具使用程度（Credits、折算金额、请求次数、次均消耗） |
| 功能使用量 | devops 使用情况报表 API | 各功能**页面路由**的实际点击量与活跃用户 |
| MCP 工具用量 | foundation MCP 工具统计 API | 团队通过 **AI 客户端**调用后端能力的程度 |

> 「功能使用量」与「MCP 工具用量」是两个不同口径：前者是人在管理后台点页面，
> 后者是人在 AI 客户端（Claude / Qoder / Cursor）里让模型调工具，不要合并统计或互相推算。

## 计数纪律（必须遵守）

> 服务端生成会话没有 `collect_commits.sh`：以下「脚本输出」对服务端会话指 **agent 在工作区内自行采集的结果**，
> 采集纪律相同（全分支 `git log --all`、SHA 全局去重、`--no-merges` 剔 merge、`--since/--until` 窗口过滤），
> 自采后按下述规则自检打平，不得凭印象估算。

1. `collect_commits.sh` 给出的总提交数、各仓库提交数、各人提交数**已按「全分支 + SHA 去重 + 剔除 merge」算准，直接引用**。
2. **严禁自己再跑 `git log` 重新计数**（服务端会话相反：必须由 agent 按上述纪律自采），也不要凭代表性主题条目的多少去推算数量——自行逐仓计数会把仓库数字张冠李戴、逐仓小计与总数打不平。
3. 「各仓库提交分布」必须覆盖仓库清单的**每一个**仓库（含 0 提交的，标注 0），各项目小计必须等于其成员仓库之和，总计必须等于总提交数。
4. 只有在需要理解「某次提交具体做了什么」时，才可以进入仓库查看代码或 commit 详情；那属于定性解读，不改变任何计数。
5. 新增 / 删除行数口径同日报：在同一名单内提交集合上统计（与提交次数同一 SHA 集合，剔 merge），各人、各仓与总计行数必须打平；二进制文件不计行数。

## 人员范围（强制）

- 数据包「统计人员范围」是唯一人员口径：只统计名单内人员，名单外的 git 作者、功能排期卡片负责人/开发人、Qoder 成员一律不计入任何人员维度，也不在报告中出现
- 匹配规则：姓名或别名去掉空白、忽略大小写、忽略括号内职级后缀后完全相等即视为同一人；同一提交命中多名人员时按名单顺序归入第一个命中人员，避免重复计数
- **提交统计必须按名单过滤**：服务端会话逐仓采集 `%H|%an|%ae`（全分支、SHA 去重、剔 merge、窗口过滤），用名单姓名/别名匹配作者名或邮箱，仅保留命中记录；总提交数 = 名单内 SHA 并集，各人提交数 = 各自命中 SHA 数，各仓库分布 = 名单内 SHA 分仓计数，三者必须打平
- 「参与人数」只计名单内有提交的人；名单内无提交/无卡片/无 Qoder 用量的人不单独出章节
- 功能排期卡片只统计负责人或开发人命中名单的卡片；Qoder 用量只使用数据包提供的名单内数据，不自行扩大范围
- 项目级数据（需求吞吐、仓库清单）保持全量；其中需求提交人等人员姓名按名单脱敏，名单外显示「—」
- 功能使用量、MCP 工具用量只有聚合值，不返回人员明细，不做名单过滤，也不在按人员章节中点名

## 仓库归属分组

按会话配置 `projects` 分组（项目集合与代码仓归属以「报告项目配置」生效数据（基础映射引用功能排期项目配置）为准，不要自行猜测归属；服务端会话直接采用会话数据「代码仓库清单」中的项目归属分组）：

- **各启用项目**：该项目的 SKILL 仓库（扫描配置的 skill_roots）+ 配置的代码仓清单
- **文档/SKILL 类仓库**（未挂项目的纯文档仓，仅统计提交，不含业务代码）
- 工作区内未归类的仓库列作「未归类仓库」

## 输出格式规范

报告按以下章节顺序输出，数据不可得的章节整节省略；标题格式：`研发周报 - {yyyy-MM-dd}`（生成当天日期）。标题下须声明统计区间（`统计区间：YYYY-MM-DD（周一）~ YYYY-MM-DD（周日）`，取数据包统计区间，保证可解析入库）。

### 1. 统计摘要

- 统计范围：研发团队名单（N 人）
- 本周总提交数（含新增 / 删除行数）/ 参与开发人数 / 涉及仓库数量（均按名单内作者统计）
- 功能排期任务总数 / 已完成 / 进行中 / 待开发，窗口内领取数 / 完成数（按名单内人员统计）
- Qoder 团队总用量 (Credits) / 折算金额（元）/ 总请求次数 / 次均消耗（名单内成员合计；无数据则省略本条）

### 2. AI 分析总结

- 核心进展（最重要的 3-5 个功能/模块推进情况）
- 潜在风险（从提交模式、功能排期进度判断的风险信号）
- 下周建议

### 3. 按人员综合分析（核心章节）

对名单内每位有数据的成员综合输出：

- **代码产出**：本周提交次数与新增 / 删除行数；主要工作内容（合并同一功能的多次提交为一条描述）；关键功能点列表；涉及仓库和模块
- **功能排期任务**：任务总数、完成数、进行中、待开始；完成率；窗口内领取 / 完成的卡片；各任务详情（标题、负责人、领取开发人、排期/领取/完成时间）；时间分析（排期→领取响应速度、领取→完成开发耗时）
- **Qoder 使用情况**：本周 Credits 与折算金额（Credits × 0.15 元，即 Credits ÷ 2000 × 300）、请求次数、次均消耗；团队占比；**主要模型分布**（来自 model-pivot）（无数据则省略本条）
- **综合评价**：功能排期实际进展 vs 计划；Qoder 使用量与产出的关联分析（Qoder 数据缺失时不写关联分析）

人员默认按客观产出贡献度从高到低排序：依次比较窗口内完成的功能排期卡片数、提交次数、新增行数、Qoder Credits 用量，前一项并列再比较后一项，四项均并列时按统计人员名单顺序；某项数据源整体缺失时跳过该比较项，不按 0 补齐。不计算或展示贡献度分值与名次。

人员名称跨数据源可能不一致（git 英文名 vs 排期中文名），以数据包「统计人员范围」的姓名与别名映射为准合并，不再维护固定映射表。

### 4. 功能进展追踪

从 commit message 和功能排期卡片提取功能关键词，汇总为表格：`| 功能点 | 负责人 | 状态 | 涉及仓库 |`

状态判定：含 feat/新增/实现 → 开发中；fix/修复/bugfix → 修复中；refactor/重构/优化 → 优化中；docs/文档 → 文档完善。

### 5. 各仓库提交分布

按**项目（业务线）分组**统计各仓库**名单内作者**的提交次数与新增 / 删除行数（含 0 提交仓，标注 0），给出每个项目的提交与行数小计，标注热点模块；名单外提交不计入，各仓小计与总计必须打平。

### 6. 功能使用情况（独立章节，无数据则整节省略）

将功能排期卡片中本周完成/在开发中的功能，与功能使用量报表中的路由关联分析：

- 主表格：功能名称 / 对应路由 / 完成或领取日期 / 该日期使用量 / 本周总点击 / 负责人
- 重点交付但未触发（inactive）的功能独立高亮提示风险
- 热点路由（点击占比靠前）标注出来

### 7. MCP 工具使用情况（独立章节，无数据则整节省略）

- **KPI 汇总**：总调用次数 / 使用人数 / 被用工具数占注册总数 / 成功率 / 平均耗时
- **业务域分布**：哪些业务域的 AI 能力真被用起来了
- **工具排行**：调用量 TOP 工具（使用人数、成功率、平均耗时）
- **零调用工具风险**：已注册但本周无人调用的工具，需推广或确认工具描述是否让模型看不懂

硬约束：

1. 工具名与业务域直接用接口返回的中文名（`toolNameCn` / `scopeCn`），不要自行翻译、改写或补全英文名
2. 本章节「使用人数」是去重聚合值，接口不返回具体人名，**不要**把 MCP 工具使用摄到「按人员综合分析」里点名，也不要猜是谁在用
3. 不要把 MCP 调用量与 Qoder Credits 或页面点击量相互推算——三者计量口径完全不同
4. 若数据源无数据 / 拉取失败，直接省略本章节，不写缺失或失败说明，严禁编造数字

### 8. 口径说明

- 统计区间为最近一个以周日收尾的自然周周一 00:00 至周日 24:00（东八区）
- 提交次数与新增 / 删除行数为同一名单内提交集合（全分支、SHA 去重、剔 merge）
- Qoder 用量、请求次数、次均消耗为窗口内各自然日快照合计；折算金额 = Credits 用量 × 0.15 元

### 9. 章节输出模板

> 模板为数据齐全时的完整形态；任一数据源缺失时，对应章节、条目与人员字段整体不输出。

## 分组与降噪规则

1. **按人员分组**：只对名单内 git author 分组，与功能排期卡片负责人、Qoder 用量成员名按名单别名匹配合并；名单外作者不出现
2. **合并同功能提交**：同一作者连续多次提交到同一模块，合并为一条功能描述
3. **去除噪音**：过滤 merge commit（脚本已处理）、仅改动 .gitignore/.idea 等非业务提交
4. **中文输出**：所有描述使用中文

## SKILL/文档类仓库额外规则

分析各项目的 SKILL 仓库（以「报告项目配置」生效数据为准）时：

- 从文件路径提取模块名（如 `<项目扫描根目录>/<业务大类>/xxx/SKILL.md` → 模块 xxx）
- 按项目配置的首层目录区分业务线归属，模块名前标注所属项目
- 关注 SKILL.md 变更（新增/修改需求）与 reference(s)/ 变更（技术方案落地）
- 标注负责人（从 commit author 推断）
- 这类仓库不含业务代码，按「文档/需求产出」维度统计，不要因缺少 Controller/Service 判为异常
